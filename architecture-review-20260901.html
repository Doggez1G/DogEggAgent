候选 1：拆分 app.tsx 上帝组件

Strong

涉及文件

ui/src/webui/app/app.tsx (581 行，6 个内联组件 + ~15 个 useState + 110 行 onMessage if 链)

问题

app.tsx 违反项目其他所有组件遵循的 module=folder 约定。内联了 SettingsModal、PermissionBanner、ConfirmModal、HelpModal、FsBrowserModal 五个组件。onMessage effect 是 ~110 行 if 链管理 ~15 个 useState，与 shared reducer 平行但不可测。这是项目中最大的未测试逻辑集中点。

方案

5 个内联 modal 各拆为独立组件文件夹。面板状态管理抽取为 custom hook（如 usePanelState），把 contextState/systemState/logState/toolCalls/filesTouched 的设置和请求逻辑集中到可测试函数中。App 只负责布局组合和顶层状态。

收益

  • Locality：面板状态集中到 hook，修改不需要在 110 行 if 链里找
  • Leverage：usePanelState 可独立测试
  • 一致性：所有组件遵循 module=folder 约定

候选 2：为 reducer.ts 补测试

Strong

涉及文件

ui/src/shared/reducer.ts (195 行，标记 ★可单测，零测试)

问题

reducer 是 shared 重构核心——把 AgentToUiMessage 转换为 UI Block，包括流式文本累积、思考块落盘、工具块配对、历史重建。重构设计文档明确承诺测试但从未实现。最近 8 次提交中 6 次修 thinking 对齐 bug——全部发生在这个从未测试的纯函数里。

方案

编写 ui/test/shared/reducer.test.ts，覆盖：text_delta/thought_delta 流式累积与 flush、tool_start+tool_end 配对、session_ready 重建（含 thinking 对齐：空/非空/混合）、compaction 通知块、error/cancelled 时 flush partial、history_cleared 清空。纯函数，零 mock。

收益

  • Leverage：reducer 的 interface 就是测试面——测试穿越同一个 seam
  • Locality：thinking 对齐 bug 集中在一个可测函数里，修一次测一次
  • 回归保护：未来修改有测试网兜底

候选 3：LoopDeps 回调包耦合

Worth exploring

涉及文件

agent/src/loop/types.ts (LoopDeps 21 字段) · agent/src/core/agent.ts · agent/src/loop/run.ts

问题

LoopDeps 是 21 字段结构体，包含 trans/emit/requestPermission/checkCancelled/summarize 等 agent 方法作为回调。这是重构设计文档预警过的"thin scattered context object"——loop 不和 agent 解耦，只是通过 struct 传递方法。修改 agent 方法签名都要同步改 LoopDeps。测试 runLoop 需要构造完整 21 字段 mock。

方案

设计文档明确选择不拆 agent.ts，预警了这个权衡。可考虑将 LoopDeps 回调分组为更少接口（如 LoopCallbacks { trans, emit } + LoopServices { requestPermission, checkCancelled, summarize }），或保持现状但加 JSDoc。不建议大改。

候选 4：强制 barrel import 规则

Worth exploring

涉及文件

bridge/test/architecture.test.ts · agent/src/loop/run.ts (违规 import ../shared/errors) · agent/src/core/agent.ts (违规 import ../shared/id)

问题

设计文档 §9 承诺"跨模块 import 只指向 index.ts"，但架构测试未强制。已有两处违规：run.ts 直接 import ../shared/errors，agent.ts 直接 import ../shared/id，绕过 barrel。

方案

(1) architecture.test.ts 新增规则：import 路径指向非 index.ts 的相对路径则失败。(2) 修正现有违规。(3) 确保 shared/index.ts 导出 errors 和 id。

候选 5：移除 SSE uiPort 死代码

Speculative

涉及文件

server/src/channel/sse.ts (uiPort 返回但无人使用)

问题

createSseChannel() 返回 { agentPort, uiPort, sseHandler, postHandler }，但 main-web.ts 只解构 { agentPort, sseHandler, postHandler }，startServer 不接受 uiPort。uiPort.onMessage 是空函数，uiPort.post 复制了 postHandler 逻辑。SSE 传输天生不对称，不存在对称 uiPort。

方案

从 createSseChannel() 返回类型中移除 uiPort。

候选 6：消除跨 UI 逻辑重复

Speculative

涉及文件

getToolConfigPerm (app.tsx) · getToolPermission (info-panel) · onCommandFeedback (InputBar + CommandPalette 各一份) · STATUS_LABELS (top-bar / info-panel / TUI 三份)

问题

权限分类逻辑在 agent 端和 WebUI 端各实现一份（不能跨包 import 是被迫的）。但 WebUI 内部两份完全相同可合并。STATUS_LABELS 和 onCommandFeedback 也是纯展示逻辑重复——shared 重构的目标是消除重复，但这些留在 shared 之外。

方案

将 getToolConfigPerm、STATUS_LABELS、onCommandFeedback 映射移到 ui/src/shared/ 中作为纯函数/常量，WebUI 和 TUI 都从 shared 导入。

首要推荐

候选 2（为 reducer.ts 补测试）最高优先级。纯函数、零 mock、投入产出比极高。最近 8 次提交 6 次修这里的 thinking 对齐 bug。有了测试后候选 1 的拆分也有了回归保护。

候选 1（拆分 app.tsx）第二优先级。项目中最大的未测试逻辑集中点。

候选 4（强制 barrel import）成本最低。加一条测试规则 + 修两处违规即可。
