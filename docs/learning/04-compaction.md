# 04 · 压缩：全量交接总结

> 上下文窗口有限，对话越来越长怎么办？——到了窗口的 80%，把**整个 context** 交给模型总结成一份
> 「任务交接文档」，用它替换全部历史。没有保留尾巴、没有淘汰、没有硬丢弃。
> 本章讲这个语义为什么这样定、机制在哪、以及提示词为什么是核心。

## 策略/机制分离（本域最重要的设计决策，不变）

- **策略**（policy）：纯函数——何时压（`shouldCompact`，80% 阈值）、分段估算（breakdown）。
  无 LLM、无事件，可穷举测试 → 归 `context/`；
- **机制**（mechanism）：编排——真的去调 LLM 做总结、替换 context、发 compaction 事件、处理失败
  → 归 `turn/`（Compactor + summarizeHistory）。

## 压缩语义：全量交接总结（ADR-0011）

```
循环开头估算 context，超窗口 80% → compacting 态
  → 把【整个 context】交给模型总结（无 keep=N 保留尾巴、无淘汰、无硬丢弃）
  → context 替换为一条消息：[对话已压缩——以下是此前上下文的结构化摘要]（user 角色）
  → history 纹丝不动（R1：原文档案永远在）；emit compaction { before, after, source }
  → 失败（LLM 出错 / 摘要为空）→ 异常上抛 → 轮次以 error 收尾（诚实失败）
```

**为什么没有保留尾巴（旧版 keep=4 已废）**：消息级切分可能正好落在 assistant(tool_calls) 与它的
tool 结果之间——拆散配对下次 API 调用直接 400。全量替换后不存在切缝，顺带消灭了这个隐患。

**为什么没有淘汰/硬丢弃（旧版 enforceContextLimit 已废）**：淘汰是**确定丢**信息，且模型在不知情的
情况下失忆；总结**可能**丢，但摘要的质量可以靠提示词改善——两害相权，选可改善的那个。
失败时诚实报错（通知 + 轮次错误），由用户决定 /compact 重试或 /new，而不是悄悄丢上下文继续跑。

**无叠加劣化**：下次压缩是对 [摘要_v1 + 新对话] 的**重新完整总结**——每代摘要都基于完整可见信息，
不是"摘要的摘要"的层层有损。

## 摘要提示词：任务交接文档（本域核心学习点）

摘要将作为模型继续工作的**唯一上下文**，所以提示词按结构化交接设计（`turn/summarize.ts` 的
HANDOVER_PROMPT）而非单纯"缩写"：逐项保留任务目标 / 已完成步骤 / 涉及文件路径 / 重要决策及理由 /
未完成事项 / 用户偏好，中文条目、不编造、maxOutput 2000。「可能丢信息」的 mitigation 全在这份
提示词的质量里。

## R1 保护：结构上安全的有损

Compactor 的签名只接收 context、返回新 context——结构上碰不到 history（有专门测试验证传入数组
不被原地修改）。淘汰式方案在 R1 下做不到这一点：任何"从 context 删东西"的操作都会让模型侧与
history 侧产生不可查的偏差。全量总结下，原文仍在 history/session 文件里供人查阅。

## 手动 /compact 与自动触发

同一条全量总结路径，仅 force 参数不同（手动跳过阈值检查）。编排差异在 `turn/turn-runner.ts`：
自动压缩在 loop 内（compacting 态可感知），手动压缩独立占闸门。两者失败语义一致——异常上抛、
轮次错误收尾、通知用户。

## 与其他机制的关系

- **usage（07 章）**：API 返回的真实用量与会话累计在 /context 与估算并排展示——估算器的校准误差
  从此可见；
- **仪表盘**：`context_state` 携带 breakdown（system/用户/助手/工具输出/schema 五段）+ 上轮实际 +
  会话累计 + 压缩次数，TUI/WebUI 同一份契约渲染。
