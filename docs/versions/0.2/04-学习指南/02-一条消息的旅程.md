# 02-一条消息的旅程（核心章）

本章沿「用户在 TUI 输入 `列出 src 下的文件` 并回车」走完全链路。每一站都给出真实函数与文件，建议开着源码对照读。文中行号为撰写时参考，以当前代码为准。

## 第 1 站：前端提交（ui → port）

`ui/src/tui/app/app.tsx` 的 `handleSubmit()`：先做联想拦截（`matchPathToken`/`matchCommands`），再把普通文本走 `parseCommand()`（`ui/src/shared/commands.ts`）——非斜杠文本解析为 `{ kind: 'user' }`，随后两件事：`dispatch({ type: 'local_user', text })` 让用户消息**本地立即显示**（不等后端回声），以及 `port.post({ type: 'submit', text })`。

port 是 `bridge/src/channel/port.ts` 定义的 `UiPort`。TUI 模式下它是 `bridge/src/channel/in-memory.ts` 的 `uiPort`——`post()` 就是同步 `forEach` 调所有监听器，**发后即达**（这也是 TUI 里「命令响应可能立刻改变视图、必须 suppressEnter」的根源）。

## 第 2 站：门面路由（agent.ts 的 send）

构造时 `agent/src/agent.ts` 就自订阅了 port（第 133 行 `this.port.onMessage((msg) => { this.send(msg).catch(() => {}) })`）。`send()` 是一个巨型 switch（第 595 行起）：

- `submit`：先 `isConfigured()` 检查（定义在 `bridge/src/contract/config.ts`），未配置发 notice；已配置则先 `awaitMcpRebuildSettled()` 等在飞的 MCP 重建收敛（重建中开轮会让工具清单中途漂移、在飞 MCP 工具被断连），再经 `runTrackedTurn()` 登记 `turnRunner.submit(cmd.text, this.resolveTurnParams())`。
- `resolveTurnParams()` 在**命令时刻**解析出 `{ client, model, maxOutput, maxRetries, reasoning, windowTokens }`（`turn/turn-runner.ts` 的 `TurnParams` 接口）——派生值不进共享上下文，这是「所有权立法」的一部分（见 `agent/src/ctx.ts` 注释）。

## 第 3 站：轮次执行器与闸门（turn-runner）

`agent/src/turn/turn-runner.ts` 的 `runTurn()`（第 152 行）：

1. `this.deps.ctx.gate.enter()` —— `agent/src/shared/gate.ts` 的 `BusyGate`：置 running、新建 `AbortController`。这是 R2 并发立法的落地：**同一时刻只允许一个动 context 的操作**，期间再来的 submit/会话/配置编辑类命令都会被 `gate.busy` 挡下并发 notice。
2. `conversation.pushUserMessage(text)` —— `agent/src/session/conversation.ts` 的 R1 双写：同一条 user 消息**同时**进 `history`（完整原文，永不压缩）与 `context`（发给模型，可压缩）。
3. `emit({ type: 'message', role: 'user', id })` 告知 UI。
4. `await this.deps.loop.run({...})`，传入 systemPrompt（`ctx.assembler.systemPrompt()`）、context、permission、maxIterations、cwd、signal 等（接口见 `agent/src/turn/types.ts` 的 `TurnInput`）。

## 第 4 站：状态机 idle → thinking

`agent/src/turn/state.ts` 是 10 态状态机的全部：`TransitionInput` 联合、`VALID_FROM` 合法来源表、`transition()` 纯函数、`StateMachine` 类。`loop.run()` 开头 `trans({ kind: 'submit', reasoning })`——推理模型迁到 `thinking`，普通模型迁到 `responding`。**立法**：`(input, 当前态)` 不在 VALID_FROM 中的组合原地不动，防止逻辑错误导致非法状态序列；全项目只有 `ctx.machine` 一台状态机（loop 轮内 fire，门面 `emitState` 轮外 fire）。

状态变化经 `loop.ts` 的 `trans()` → `emit({ type: 'state', from, to })` 到 UI；`agent.ts` 的 `emitState()` 还会顺带推 `status_state`（带最新 token 估算），驱动状态栏实时刷新。

## 第 5 站：LLM 流式调用（llm/）

`loop.ts` 第 140 行 `turn.client.chat(req, turn.signal, onEvent)`。client 由 `agent/src/llm/client-for.ts` 的 `clientFor(protocol, conn)` 分派——当前唯一实现是 `agent/src/llm/provider/openai/openai-client.ts` 的 `OpenAiClient`：原生 fetch + 手写 SSE 解析（`stream.ts`），外面包 `retry.ts` 的 `withRetry`（AbortError 不重试）。

流事件类型见 `agent/src/llm/types.ts` 的 `LlmStreamEvent`。loop 在 onEvent 回调里做四件事：`text_delta` → 转 responding 并 `emit text_delta`；`thought_delta` → `emit thought_delta`；`stream_reset` → 请求层重试从零重发增量，`emit stream_reset`（UI 据此清空 partial）；`tool_call_start` → `emit tool_pending`（模型正在流式生成工具参数——大参数期间 UI 原本无反馈，这个消息填补空窗）。

## 第 6 站：tool_calls 到达，进入工具循环

`chat()` 返回后（`ChatResult.message` 是组装好的 assistant 消息），loop 把它 push 进 `context` 和 `newMessages`，`emit({ type: 'message', role: 'assistant' })`。若 `tool_calls` 为空：`trans({ kind: 'final_answer' })` → `finished` 态，`emit finished`（带本轮真实 usage），返回 `LoopResult`。否则 `trans({ kind: 'tool_calls' })` 进 `tool_calling`，**串行**执行每个 call（多工具并发的复杂性刻意不引入）。

## 第 7 站：权限网关（本旅程最重要的一站）

每个 tool_call 进入 `agent/src/turn/tool-executor.ts` 的 `ToolExecutor.execute()`（第 34 行）：

1. **未知工具**：查 `registry.get()`，没有 → 回填 `未知工具 X` 的 tool 消息（也发带 error 的 `tool_end`），迁移 `reject`/`tool_done`。
2. **参数校验**：`tool.schema.parse(JSON.parse(arguments))`（zod）失败 → 回填 `参数校验失败`。
3. **权限判定**：`this.services.permission.classify(tool.name, args, ctx.cwd)`。实现在 `agent/src/permission/manager.ts`：先把 args 里的 path 归一成 **realpath 绝对 posix 路径**（`realTargetPath`，防符号链接逃逸）、把配置规则按锚点归一（`normalizePattern`），再调 `bridge/src/contract/permission.ts` 的纯函数 `classifyPermission`。判定优先级立法：`reject > sessionRules（会话提升）> ask 规则 > allow 规则 > 默认 ask`（详见 06-权限系统）。
4. **ask 分支**：`trans({ kind: 'tool_needs_permission' })` 进 `waiting_permission`，然后 `await this.services.requestPermission(tool, args)`——即 `agent/src/agent.ts` 第 463 行的 `requestPermission()`：`deriveAlwaysScope()`（`agent/src/permission/derive.ts`）推导「对此范围不再询问」的模式，`pending.add(id, {resolve, reject, scopePattern})` 挂起一个 Promise，`emit({ type: 'permission_request', id, tool, input, alwaysScope })`。**loop 就在这里挂起**，直到：
   - 用户在 UI 决议 → TUI 权限 overlay（`ui/src/tui/features/permission/keys.ts`）→ `port.post({ type: 'permission_decision', id, decision })` → `send()` 里 `pending.resolve(cmd.id, cmd.decision)`；或
   - 用户 cancel → `pending.rejectAll(new CancelledError())`。
5. **决议落地**：`permission.apply(tool.name, decision, scopePattern, cwd)` 把 `allow_always`（整工具）/`allow_always_scoped`（范围模式）写进会话提升表；`reject` 则回填明确话术「请勿再次尝试同一工具」（防模型循环重试）。
6. **allow 分支**：`trans({ kind: 'tool_auto' })` 直接执行。

## 第 8 站：执行与回填

`ToolExecutor.runAndEmit()`（第 104 行）：`emit tool_start` → `await tool.execute(args, ctx)`（`ToolContext` 带 cwd/signal/shellProgram，见 `agent/src/tools/types.ts`）→ 结果经 `truncate()`（`agent/src/context/truncate.ts`，8000 字符 cap）→ `emit tool_end` → 返回 `{ role: 'tool', tool_call_id, content }`。异常用 try/catch 兜底，**保证 tool_start 总有配对的 tool_end**。

回填后 `state = trans(step.transitionInput)`：`isLast` 时 `result_back`/`reject`（按 reasoning 回 thinking/responding，重新请求模型），否则 `tool_done` 回 `tool_calling` 执行下一个。循环继续，直到无 tool_calls 或 `maxIterations` 上限。

## 第 9 站：收尾——落盘与标题

`runTurn()` 拿到 `LoopResult` 后 `conversation.applyTurnResult(result)`（`conversation.ts` 第 76 行）：替换 context、append newMessages 到 history、累积 thinking/usage/compactions。`finally` 里 `gate.leave()` + 清空轮中实时快照 + `emitState({ kind: 'reset' })` 回 idle + `saveOrNotice()` 落盘（详见 10-会话与持久化）。标题生成分两个触发点：本会话首条 assistant 在**轮中**出现即 fire-and-forget 生成中文短标题（`agent/src/turn/title.ts`，长任务不必整轮顶着「未命名」），轮末未生成再补一次；手动 /rename 优先，且 busy 期间只写内存不落盘（防检查点回退，见 turn-runner 注释立法）。

## 错误与取消的形状

- **取消**：`BusyGate.cancel()` 同时置标志 + abort signal。loop 双路消费——`checkCancelled()` 协作检查点（保证逻辑一致：补全未配对的 tool_calls）与 `signal` 在飞中断（fetch/工具立即 AbortError）。补齐逻辑是契约级纯函数 `patchUnpairedToolCalls`（已下沉 `bridge/src/contract/message-pairing.ts`，loop/turn-runner/conversation 三处同源引用）：loop 的 catch 路径用它补齐并返回部分结果；轮中检查点落盘前与会话加载兜底（见 10-会话与持久化）复用同一规则。取消返回**部分结果**（`cancelled: true`），已完成的工作不丢。
- **错误**：loop catch 后返回 `error: message` 的部分结果，turn-runner `emitState({ kind: 'error' })` + `emit error`——统一「部分结果」形状是本层最重要的健壮性设计。
