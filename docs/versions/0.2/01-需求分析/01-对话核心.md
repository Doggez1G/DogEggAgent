# R-DLG 对话核心

> 与 LLM 的多轮对话循环是产品核心：用户提交一条消息，agent 驱动模型思考、调用工具、观察结果、继续思考，直到产出最终回复。本域定义循环本身的机制——状态机、R1/R2 双写立法、压缩管线、工具循环、取消语义、标题生成与状态广播。工具、权限、MCP、技能等功能域都是这条循环的参与者，各自在独立篇章定义。

## 域机制概览

**消息通道与门面。** Agent 是后端对外的唯一入口（门面类），只有「消息」一个进出通道：UI 发来的每条消息（`submit`/`cancel`/`compact_request`/各类查询）经 AgentPort 路由到 `send()` 分发；agent 产出的每条出站消息（`state`/`text_delta`/`tool_start`/`compaction`…）统一经 `emit()`（= port.post + 按类型分 scope 的日志埋点）广播。TUI 与 WebUI 不各自实现协议，只是同一套 bridge 消息契约（`agent-to-ui.ts`）的两个消费者。

**一轮对话的完整数据流。** 用户提交文本 → TurnRunner 先检查并发闸门（BusyGate），再 `conversation.pushUserMessage(text)` 把消息**同时**写入 history 与 context（R1 双写）→ 广播 `message: user` → AgentLoop 拿着本轮参数（提交时刻从 config 解析出的 client/model/maxOutput/maxRetries/reasoning/windowTokens，外加 systemPrompt、context 引用、permission、maxIterations、cwd、AbortSignal）进入循环。循环每迭代一次就是一次 LLM 请求：估算 context token、必要时压缩（见 R-DLG-04）；调用 `client.chat()` 流式接收，assistant 消息 push 进 context 并收集进 `newMessages`；有 tool_calls 则经 ToolExecutor 串行执行并把结果作为 tool 消息回填，继续下一迭代；无 tool_calls 则 `final_answer` → 广播 `finished`（携带本轮真实 usage）。轮次收尾时 loop 返回 `{ context, newMessages, thinking, usage, compactions, cancelled?, error? }`，Conversation 用 `applyTurnResult` 把 context 替换为 loop 产物、newMessages 追加进 history、thinking 累积、用量与压缩计数累加，最后落盘会话。

**R1/R2 双立法。** R1（双写分离）：history 是「发生过什么」的完整档案，永不淘汰、永不压缩；context 是「发给模型的消息视图」，压缩只重写 context。loop 内部只操作 context，本轮新增消息收集在 newMessages 里由外层同步——这保证压缩、取消、错误任何路径下 history 都不被污染。R2（单飞闸门）：同一时刻只允许一个「动 context」的操作在飞（轮次或手动压缩），BusyGate 用一个布尔标志 + 一个 AbortController 实现；运行中收到 submit/compact/会话管理类命令一律发 `notice: 运行中，请稍候` 不静默丢弃，纯查询类（status/context/tools/skills/mcp 列表）始终放行。

**状态机是唯一的轮次事实源。** 全项目只有一台 StateMachine（住在 ctx.machine），loop 在轮内 fire，门面在轮外 fire；每次迁移先查 VALID_FROM 合法来源表，`(input, 当前态)` 非法组合原地不动（返回原态），防止逻辑错误导致非法状态序列；状态变化且仅变化时广播 `state { from, to }`，并附带一条 `status_state`（最新 token 估算、provider/model、cwd、用量），让状态栏在每次状态变化时实时刷新。

```
idle/finished/cancelled/error --submit--> thinking（推理模型）| responding（普通模型）
thinking  --thought_done--> responding（思考结束开始吐正文）
responding --tool_calls--> tool_calling --tool_auto/allow--> executing --tool_done--> tool_calling（还有下一个）
                                                                  --result_back--> thinking/responding（重新请求模型）
tool_calling --tool_needs_permission--> waiting_permission --allow--> executing
                                                           --reject--> thinking/responding
responding --final_answer--> finished
任意运行态（thinking/responding/tool_calling/waiting_permission/executing/compacting）--cancel--> cancelled / --error--> error
finished/cancelled/error/idle/compacting --reset--> idle
thinking/responding/idle/tool_calling/executing/waiting_permission --compact_start--> compacting --compact_done--> 指定态
```

- `thinking`：已把 context 发给推理模型，等待思考产出（reasoning 流式）。
- `responding`：模型在产出面向用户的正文（流式）。
- `tool_calling`：模型请求了工具、参数流式生成中（UI 显示「正在调用 X…」）。
- `waiting_permission`：工具需要审批，暂停等用户决策。
- `executing`：工具正在本地/远程执行。
- `compacting`：压缩摘要调用进行中（自动与手动都有可见状态）。
- 关键规则：`reject`/`result_back` 之后的「重新请求模型」与 submit 等价——按 `reasoning` 决定回 `thinking` 还是 `responding`；`tool_done` 表示批量工具中还有下一个，从 executing/waiting_permission 回 tool_calling。

**取消双机制。** BusyGate 同时承载两套取消语义，职能不同、不可互相替代：① 协作检查点——loop 在每次迭代开头与每个工具执行前轮询 `isCancelled()`，保证取消后逻辑一致（返回部分结果、补全未配对 tool_calls）；② 在飞中断——`enter()` 返回的 AbortController 的 signal 传给 LLM fetch、每个工具、压缩摘要调用，取消时它们立即以 AbortError 失败，保证取消的及时性。两路由 `cancel()` 一次触发，loop 同时消费二者（checkCancelled 回调 + signal）。

### R-DLG-01 流式响应

- **需求背景与动机**：一次 agent 回复动辄数十秒（推理 + 多次工具轮），若等完整回复再呈现，用户在大部分时间里面对静止界面，无法判断 agent 是在正常工作还是卡死——只能干等或反复怀疑「是不是挂了」。流式呈现把「等待」变成「可观察的过程」：思考在走、正文在出、工具在跑，每一步都可见。
- **功能规格**：
  1. **触发条件**：轮次进行中，模型产出经 SSE 增量到达 agent。
  2. **处理规则**：agent 逐条广播 `text_delta`（正文增量）与 `thought_delta`（思考增量）——**两条独立通道**；`thought_delta` 仅在当前模型 `reasoning: true` 时向 UI 广播（普通模型的杂散 reasoning 不显示）。
  3. **输出与用户可见表现**：思考内容以可折叠的黄色块呈现（折叠态显示前 3 行 + 「…（回车展开完整思考）」），正文是正式回复（markdown 渲染后打印）；WebUI 侧为折叠面板。
  4. **处理规则**：前端 reducer 把增量拼接成未落盘的 partial 块；`text_delta` 到达时若还有思考 partial 会先 flush 落盘再开新回答块，反之亦然——保证思考与正文不会混进同一块。
  5. **输入与前置**：思考流是否存在取决于模型（`reasoning: true` 才有），非思考模型只有正文流。
  6. **状态联动**：状态机的 `thought_done` 迁移发生在「第一个正文 delta 到达」或「整条 assistant 消息收齐但无正文」两个时机，让状态栏从 Thinking 切到 Responding。
- **边界与失败模式**：
  - 流式中途断开/超时不产生任何伪造正文——异常沿 R-DLG-06 语义处理。
  - 取消时 partial 块在 `state → cancelled` 时被 flush 落盘，已产生的部分输出保留可见，且不会被下一轮 text_delta 错误拼接（reducer 在 cancelled/idle 时强制 flush 是修复「取消后回答错位」bug 的关键）。
  - 思考内容不进 history/context，只在 `thinking` 数组里随会话单独持久化，resume 后按轮次对齐重建显示；`reasoning: false` 时即使模型返回 reasoning 也存空字符串（不记录不显示）。
- **验收标准**：
  1. 当模型输出 reasoning 且 `reasoning: true`，则 UI 顺序收到 `thought_delta` 且思考块实时增长；当 `reasoning: false`，则 agent 不广播任何 `thought_delta`。
  2. 当第一个 `text_delta` 到达且当前态为 `thinking`，则状态机迁 `thought_done → responding`，思考 partial flush 落盘。
  3. 当整条 assistant 消息收齐但全程无正文（只有 tool_calls），则收尾处补一次 `thought_done` 迁移。
  4. 当流式中途失败，则对话区不出现任何伪造正文，轮次按 R-DLG-06 错误语义收尾。
  5. 当取消时存在未落盘 partial，则 `state → cancelled` 时 partial 被落盘保留，且下一轮新 text_delta 从新块开始。
- **场景走查**：用户提交「解释这段代码」→ 状态栏 Thinking、灰色思考块逐字出现 → 第一个正文 delta 到达，思考块折叠落盘、状态栏 Responding、正文逐字流式 → 收尾 finished，正文块成为 Static 区的一部分。

### R-DLG-02 多轮上下文（R1/R2 双写立法）

- **需求背景与动机**：用户在长会话里常要回查「刚才那个文件路径是什么」——如果只有一份「发给模型的消息」列表，压缩或截断就等于销毁历史，回查无据可依；如果不做分离，UI 显示与模型上下文会互相牵制（UI 要完整、模型要精简）。没有 R2 闸门的话，压缩进行到一半时又提交新消息，会把压缩产物与新消息交错写入，产生损坏的 context，下一轮请求直接 400。
- **功能规格**：
  1. **数据形态**：history 完整保存每条 user/assistant/tool 消息原文（`Message = { role, content, tool_calls?, tool_call_id? }`），永不淘汰，随会话持久化（见 06-会话管理）；context 是每轮实际发给模型的内容视图，与 history 同构但可被压缩重写。
  2. **触发条件**：user 消息提交时 `pushUserMessage` 一次双写（同一消息对象同时进 history 与 context）。
  3. **处理规则**：assistant/tool 消息由 loop 收集进 `newMessages`（`LoopResult.newMessages`），轮末 `applyTurnResult` 统一 append 到 history；loop 全程只碰 context。
  4. **请求组装**：每轮发给模型的内容 = system prompt + 全部工具 schema + context 消息数组。system prompt 由 `ContextAssembler.systemPrompt()` 组装：`loadSystemPrompt(config.systemPrompt)`（配置存路径不存正文，未配置用内置默认）+ 动态段回调现算（skills 广告段 + shell 环境引导段）。
  5. **现算语义**：systemPrompt 是**每次请求现算**的——skills 增删、shellProgram 变更即刻反映到下一轮请求，无需重启。
  6. **R2 拦截**：运行中收到 submit/compact/会话管理/配置编辑类命令发 notice「运行中，请稍候」拒绝，不排队、不合并——用户重试即可；纯查询类始终放行。
- **边界与失败模式**：
  - 压缩后 context 只剩一条摘要消息，但 history 不动——摘要丢失的信息可人工回查。
  - `/clear`（clear_history）清空 history 与 context 双方（thinking 不动）。
  - 旧会话文件只有 messages 字段时，load 期回退 `context = [...history]`。
  - R2 违规尝试（运行中提交/压缩/换会话）被闸门以 notice 拒绝——不静默丢弃，用户明确知道要重试。
- **验收标准**：
  1. 当用户提交一条消息，则该消息在 history 与 context 中各出现一次且内容一致。
  2. 当自动压缩把 context 替换为单条摘要后，则 history 长度不变，聊天区向上滚动仍能看到全部原始消息。
  3. 当轮次运行中再次 submit，则收到 notice「运行中，请稍候」，context 中不出现新消息。
  4. 当加载只有 `messages` 字段的旧会话文件，则 context 回退为 history 的浅拷贝，对话可继续。
  5. 当修改 skills 或 shellProgram 配置，则下一轮请求的 system prompt 已包含变更，无需重启。
- **场景走查**：长对话触发压缩后，用户在聊天区向上滚动仍能看到全部原始消息（来自 history 重建），而下一轮请求只带摘要 + 新消息——两侧各取所需。

### R-DLG-03 工具调用循环

- **需求背景与动机**：agent「边干边看」的工作方式——读文件 → 改文件 → 跑测试 → 再改——本质上就是「模型发起工具、结果回填、模型再思考」的循环。没有这个循环，模型只能一次给出所有假设性操作，无法根据真实执行结果修正方案：改错的文件名没人纠正，跑挂的测试没人修复。
- **功能规格**：
  1. **触发条件**：模型回复含 tool_calls（可一次多个）。
  2. **处理规则**：每个调用**串行**经过 ToolExecutor 四分支：
     - ① 未知工具名 → tool_end 带错误「未知工具 X」，回填 tool 消息；
     - ② arguments JSON 解析 + zod schema 校验，失败 → 回填「参数校验失败」；
     - ③ 权限分类（见 05-权限与安全）为 reject → 回填「用户拒绝了此工具调用，请勿再次尝试同一工具，改用其它方式或询问用户。」（明确告知模型不要盲目重试同一工具，否则会形成权限请求循环）；
     - ④ ask → 状态迁 waiting_permission，挂起等用户决策；allow/auto → 执行。
  3. **执行路径**：ask 放行与 auto 统一走——广播 `tool_start` → `tool.execute(args, ctx)` → 输出治理截断（8000 字符 cap）→ 广播 `tool_end`（带 error 标记）→ tool 消息回填。
  4. **参数流式反馈**：模型开始生成工具调用参数时（parser 发出 tool_call_start），agent 广播 `tool_pending { name }`——大参数的流式生成期间 UI 有「正在调用 X…」可见反馈。
  5. **状态联动**：批量工具中每个处理完迁 `tool_done` 回 tool_calling，最后一个处理完迁 `result_back`/`reject`（按 reasoning 定下一态）重新请求模型。
  6. **循环边界**：一轮对话可包含任意多次这样的循环，仅受 maxIterations 约束（见 R-DLG-07）。
- **边界与失败模式**：
  - 工具执行出错不终止对话——错误信息作为 tool 消息回填，模型自行决定重试、换路或向用户说明。
  - 工具抛异常（而非返回 error）也被 catch 兜底成 tool_end——保证 tool_start 总有配对的 tool_end，UI 不会留下永久「执行中」的块。
  - 权限等待期间用户取消 → 挂起的 permission Promise 被 rejectAll（CancelledError）→ 走取消路径。
  - zod 校验失败与未知工具也发 tool_end（拒绝/失败对 UI 可见，渲染「tool ✕ denied」），不再静默塞消息。
- **验收标准**：
  1. 当模型一次发起 2 个 tool_calls 且都放行，则两者串行执行：第一个完成后状态回 tool_calling，第二个完成后迁 result_back/reject 重新请求模型。
  2. 当模型调用未注册的工具名，则不发 tool_start、tool_end 带 error「未知工具 X」，tool 消息回填且循环继续。
  3. 当工具 execute 抛异常（而非返回 { error }），则仍发出配对的 tool_end（error 标记），UI 无悬挂「执行中」块。
  4. 当权限分类为 reject 桶或用户拒绝，则 tool 消息内容为「请勿再次尝试同一工具…」，UI 渲染「tool ✕ denied」。
  5. 当参数 JSON 非法或未过 zod schema，则回填「参数校验失败」，工具本体从未执行。
- **场景走查**：用户提交「把 utils.ts 里的 formatDate 改成支持时区，然后跑测试」→ 模型发起 read_file（allow 放行）→ 结果回填 → 发起 edit_file（ask → 审批横幅 → 用户「本次允许」）→ 执行回填 → 发起 shell 跑 vitest → 输出回填 → 模型看到测试通过，输出总结 → finished。全程四轮 LLM 调用、三次工具执行。

### R-DLG-04 上下文压缩（自动 + 手动）

- **需求背景与动机**：模型窗口有限（如 128k），长对话不加处理会在中途 400（超出窗口）；「砍掉最旧消息」会拆散 tool_calls/tool 配对（OpenAI API 强制要求配对，拆散即 400）且让模型失忆——刚建立的任务上下文全丢。压缩必须是「把整个 context 交给模型总结、替换为一条摘要消息」——摘要就是任务交接文档，新的助手实例仅凭它就能接续工作。
- **功能规格**：
  1. **触发条件**：每次 LLM 请求前，用本地估算器估算 system prompt + context + 工具 schema 的总 token，超过 `windowTokens * 80%`（COMPACTION_THRESHOLD = 0.8，阈值留缓冲避免在模型刚好要回答时压缩打断）自动触发；用户也可随时 `/compact`（WebUI 为 compact 按钮）。
  2. **估算口径**：CJK 字符按 1 token/字、其余按 4 字符 ≈ 1 token；assistant 消息的 tool_calls 不在 content 里，需单独 `JSON.stringify` 计入——与实际请求完全同口径。
  3. **管线**（Compactor 统一入口）：估算 before → context 为空直接跳过 → 手动 force=true 无条件执行、自动需过阈值 → 调 `summarizeHistory`：把整个 context 交给当前 provider 的模型，用结构化交接提示词要求逐项保留六类要素：
     1. 任务目标与用户核心诉求；
     2. 已完成步骤与结果；
     3. 涉及的文件路径与关键代码位置；
     4. 重要决策及理由；
     5. 未完成事项与下一步计划；
     6. 用户偏好与约束。

     并要求「摘要必须显著短于原文，寒暄一两句即可，不要为凑类别展开」；maxOutput 2000（摘要是唯一上下文，太小会截断长任务交接）、maxRetries 1、tools 空。
  4. **替换**：产出为 `[对话已压缩——以下是此前上下文的结构化摘要]\n<摘要>` 的单条 user 消息，整体替换 context；下次压缩对「摘要 + 新对话」重新完整总结，无叠加劣化。
  5. **非劣原则**：压缩后 token 若 ≥ 压缩前，视为未压缩原样返回（手动 /compact 小 context 时交接文档可能比原文还长，压缩没有意义；自动路径 80% 触发时 context 已很大，天然不受影响）。
  6. **输出与用户可见表现**：广播 `compaction { before_tokens, after_tokens, source: auto|manual }`——source 区分手动/自动，UI 据此决定弹 overlay 还是插提示块（「Context compacted: X → Y tokens」）；压缩期间状态迁 compacting，自动压缩完成后回 thinking/responding 继续本轮请求，手动完成后回 idle。
  7. **计数**：压缩次数累计进会话存档（自动走 LoopResult.compactions，手动走 incrementCompaction）。
- **边界与失败模式**（诚实失败语义）：
  - 摘要为空 → 抛「压缩摘要为空」而非静默通过（空摘要会让后续对话失去全部上下文）。
  - LLM 调用失败 → 异常上抛，该轮以 error 收尾——不做降级静默处理，由用户决定重试 /compact 或 /new。
  - 压缩期间取消 → AbortError 按取消处理（「已打断压缩」），状态经 cancel 回 idle。
  - context 为空或非劣原则不通过时，手动 /compact 回 notice「当前上下文无需压缩」。
  - history 原文不受任何影响（ADR-0011 立法：无保留尾巴、无淘汰、无硬丢弃）。
- **验收标准**：
  1. 当 context 估算 token 超过 `windowTokens * 80%`，则下一次 LLM 请求前自动压缩，且广播 `compaction` 事件（source=auto）。
  2. 当压缩成功，则 context 变为单条 `[对话已压缩…]` user 消息，history 数组不变，compactions 计数 +1。
  3. 当摘要调用返回空白，则抛「压缩摘要为空」，轮次以 error 收尾，context 保持压缩前状态。
  4. 当对小 context 手动 /compact 且摘要 ≥ 原文，则收到 notice「当前上下文无需压缩」，context 不变。
  5. 当压缩期间用户取消，则收到 notice「已打断压缩」，状态经 cancelled 回 idle。
- **场景走查**：长任务 token 到 81% → 自动压缩，状态栏短暂 Compacting，信息面板显示 98000 → 4200 tokens；继续提交「继续」→ 模型仅凭摘要就知道任务目标与已完成步骤。手动 /compact 在未超阈值时也强制执行（只要非劣原则通过）；context 为空时回 notice「当前上下文无需压缩」。

### R-DLG-05 取消

- **需求背景与动机**：agent 可能发起长时间操作——120s 的 shell 命令、大仓库遍历、跑偏的无限循环（工具失败 → 再试 → 再失败）。没有可靠取消，用户只能杀进程，丢掉全部会话状态与已产生的部分成果；取消必须既「及时」（在飞的 fetch/进程立即停）又「一致」（context 补齐配对、部分结果保留）。
- **功能规格**：
  1. **触发条件**：对话进行中（thinking/responding/tool_calling/waiting_permission/executing/compacting 任一态）用户可随时取消（TUI Ctrl+C / WebUI 的取消入口）→ agent 收到 `cancel` 消息。
  2. **处理规则**：`gate.cancel()` 同时置协作标志并 abort signal——一次触发，两路消费。
  3. **传播路径**：
     - LLM fetch 立即中断（AbortError → 转 CancelledError）；
     - 正在执行的本地工具收到 abort——shell 杀整个进程树（Windows `taskkill /T /F`，POSIX `kill(-pid)` 进程组），遍历类工具在每个目录间隙 `signal.throwIfAborted()`；
     - 挂起的审批 Promise 被 rejectAll（CancelledError）；
     - 压缩摘要调用中断。
  4. **部分结果**：loop 捕获 CancelledError 后**返回部分结果**——已产生的 assistant/tool 消息保留，并通过 `patchUnpairedToolCalls` 补全配对：向后扫描最后一条带 tool_calls 的 assistant 消息，为每个没有配对 tool 结果的调用补一条 `{ role: 'tool', tool_call_id, content: 'cancelled（用户打断了操作）' }` 的 tool 消息。
  5. **输出与用户可见表现**：状态迁 `cancelled` → 轮末 reset 回 idle，notice「已打断当前操作」。
- **边界与失败模式**：
  - 取消不回填任何伪造的「成功」结果——已产生的部分输出保留可见。
  - 批量工具中 tool 1 执行完、tool 2 被取消时，补全逻辑必须向后扫描而非只查尾部（旧版只查尾部会漏掉非尾部的 assistant；OpenAI API 要求每个 tool_call 必须有配对的 tool 消息，缺了下一轮请求会 400）。
  - 退避重试等待中的取消立即中断 sleep（不等计时结束）。
  - 取消引发的 AbortError 与超时引发的 StreamTimeoutError 严格区分——前者是用户意图不重试，后者可重试。
- **验收标准**：
  1. 当轮次任一运行态收到 cancel，则状态迁 cancelled 后轮末回 idle，notice「已打断当前操作」，输入框立即可提交新消息。
  2. 当 shell 工具执行中被取消，则子进程树被杀（Windows taskkill /T /F、POSIX 进程组 kill），已有输出随部分结果保留。
  3. 当取消时存在未配对 tool_calls（含批量工具非尾部情形），则每个未配对调用都补一条 `cancelled（用户打断了操作）` tool 消息，下一轮请求不 400。
  4. 当退避 sleep 等待中收到取消，则 sleep 立即以 AbortError 中断，不等计时结束。
  5. 当挂起的权限审批等待中取消，则该 Promise 被 rejectAll（CancelledError），走取消路径而非 error。
- **场景走查**：模型正在跑 `npm run dev`（常驻进程不会退出）→ 用户 Ctrl+C → shell 子进程树被杀、状态 cancelled、聊天区显示「已打断当前操作」→ 输入框立即可提交新消息。

### R-DLG-06 错误重试（提交回填）

- **需求背景与动机**：LLM 请求失败（网络抖动、余额不足、服务 5xx）或轮次异常时，用户精心写的长 prompt 如果丢失，就得重新打字——对长任务这是不可接受的重试成本。错误收尾必须保证：报错可见、原文可一键找回、已产生的部分内容不丢。
- **功能规格**：
  1. **触发条件**：轮次以 error 收尾时（loop 返回 error——maxIterations 达上限、API 失败重试耗尽、压缩失败等——或意外异常）。
  2. **处理规则**：agent 广播 `error { message }`，状态机迁 error → 轮末 reset 回 idle。
  3. **输出与用户可见表现**：两端 UI 各自把**最近一次提交的原文**自动回填输入框——TUI 从输入历史栈取末条（onErrorRetry），WebUI 的 turn-tracking 记录 lastSubmitText 生成 retryText——用户直接改或重发，不需要重新打字。
  4. **错误展示**：错误本身作为红色 error 块显示在对话区；loop 内部未 catch 的意外错误有外层兜底 catch（理论上不可达，防御性存在）。
  5. **部分内容保留**：error 时流式 partial 被 flush 落盘——不丢已产生的部分文本，也不留「流式幽灵块」；已完成的工具执行按错误链路保存（loop 统一返回部分结果）。
- **边界与失败模式**：
  - 回填的是「原始提交文本」——用户看到的就是自己输入的内容，非改写版。
  - 重试后成功则历史栈正常推进；请求级瞬态错误优先走 R-DLG-08 的自动重试，只有重试耗尽才落到本条语义。
  - error 时流式 partial 被 flush 落盘，与取消路径共用同一 flush 机制（cancelled/idle/error 态均触发）。
- **验收标准**：
  1. 当轮次以 error 收尾，则对话区出现红色 error 块（含 message），状态经 error → reset 回 idle。
  2. 当 TUI 收到 error，则输入框自动填回最近一次提交的原文。
  3. 当 WebUI 收到 error，则输入框自动填回 lastSubmitText 派生的 retryText，回填后清除待重试状态。
  4. 当 error 时存在未落盘流式 partial，则 partial 已 flush 可见，无幽灵块残留。
  5. 当 429/5xx 在 maxRetries 内重试成功，则不出现 error 块也不触发回填（用户全程无感）。
- **场景走查**：用户提交长 prompt → 服务端 500，重试 3 次仍失败 → error 块显示「HTTP 500」→ 输入框自动填回原文 → 用户点发送即重试。

### R-DLG-07 迭代上限（maxIterations）

- **需求背景与动机**：模型可能陷入「工具失败 → 再试 → 再失败」的循环，无限循环会烧 token 且永不结束。交互场景靠用户取消兜底即可，但无人值守批处理（脚本调 API、定时任务）没有人在旁边按 Ctrl+C，需要硬上限防跑飞。
- **功能规格**：
  1. **配置与命令入口**：`maxIterations` 是 config 顶层键，/config 树或 WebUI General 区可编辑。
  2. **取值语义**：`-1` 无限（**默认**，交互场景靠取消兜底）；正整数 N 为上限；`0` 非法（schema `refine(n === -1 || n >= 1)` 拒绝）。
  3. **处理规则**：loop 每次迭代开头检查 `maxIterations >= 0 && iterations++ >= maxIterations` → 状态迁 error、抛「达到 maxIterations 上限」。
  4. **输出与用户可见表现**：该轮以 error 收尾，已完成的工具执行按错误链路保存（部分结果不丢），触发 R-DLG-06 的提交回填。
- **边界与失败模式**：
  - 计数对象是 LLM 请求次数而非工具执行次数（一次请求可发起多个工具）。
  - 设为 1 时一轮只能一次请求（模型发起工具调用也无机会执行——tool_calls 后的循环被上限拦下）。
  - 配置为非法值 0 会在加载/编辑期被 zod 拒绝并回滚。
- **验收标准**：
  1. 当 `maxIterations: 8` 且模型发起第 9 次请求，则抛「达到 maxIterations 上限」，轮次以 error 收尾。
  2. 当 `maxIterations: -1`（默认），则循环永不因次数截断，仅受取消/错误/最终回复终止。
  3. 当配置 `maxIterations: 0`，则加载/编辑期被 zod 拒绝并回滚，运行期不出现 0。
  4. 当第 N 次请求前触达上限，则已完成的工具执行结果已保存（部分结果不丢）。
- **场景走查**：批处理脚本设 `maxIterations: 8` → 模型第 9 次想继续调工具时被截断 → error「达到 maxIterations 上限」→ 脚本读退出码与已落盘部分结果。

### R-DLG-08 请求重试（maxRetries）

- **需求背景与动机**：对 LLM 的单次 HTTP 请求会遭遇瞬态失败（网络抖动、429 限流、5xx）。一次失败就报错会让用户体验割裂——这些错误重试大概率成功；而用户取消（AbortError）与参数错误（4xx）重试毫无意义，必须区分对待，否则取消会被无谓拖延、坏请求会被反复重放。
- **功能规格**：
  1. **配置与命令入口**：`maxRetries`（config 顶层键，默认 3，schema `min(0)`）控制单次请求失败后的重试次数，实际尝试次数 = maxRetries + 1。
  2. **可重试性判定**：429 与 5xx、网络层错误（ECONNRESET 等）、流式超时（连接 60s 无响应头 / 相邻 chunk 间隔 60s，统一抛 StreamTimeoutError）可重试；其余 4xx fail-fast（请求本身有问题，重试无意义）；AbortError/CancelledError（用户取消）绝不重试；未知错误默认不重试（避免对未预期错误反复重放）。
  3. **退避策略**：指数退避 500ms × 2^attempt；429 时优先尊重服务端 `Retry-After` header（支持秒数与 HTTP-date 两种格式）；退避 sleep 可被 abort 中断。
  4. **超时模型**两级：连接超时（fetch 发起 → 响应头返回）60s、空闲超时（相邻 chunk 最大间隔）60s，统一抛 StreamTimeoutError（retry 层可重试）；不设总时长上限——持续出字节的流是健康的，生成长度由 maxOutput 决定。
  5. **离线调用**：压缩摘要与标题生成是离线单次调用，固定 maxRetries 1（更激进的重试策略）。
- **边界与失败模式**：
  - 重试全部耗尽 → 最后一次错误上抛，按 R-DLG-06 收尾。
  - 重试发生在「整次流式请求」粒度——流中途断开则整条重发，已广播的 text_delta 会重复出现（已知取舍：重发概率低且部分厂商无断点续传）。
  - 超时触发的 reader.cancel 会让流「正常」结束——归因还原成 StreamTimeoutError（可重试），否则长生成被掐断会误报成「流未产生最终消息」。
- **验收标准**：
  1. 当请求遇 429 且带 `Retry-After: 30`，则等待约 30s 后重发（优先于指数退避），成功则用户全程无感。
  2. 当请求遇 400（非 429），则立即 fail-fast 不重试，错误按 R-DLG-06 收尾。
  3. 当用户在退避等待期间取消，则 sleep 立即中断并按取消处理，不发起下一次尝试。
  4. 当服务器 60s 未返回响应头或相邻 chunk 间隔超 60s，则抛 StreamTimeoutError 并按可重试错误退避重发。
  5. 当重试全部耗尽，则最后一次错误上抛进入 R-DLG-06 语义（error 块 + 提交回填）。
- **场景走查**：模型请求遇 429 带 `Retry-After: 30` → 等 30s 重发 → 成功，用户全程无感。

### R-DLG-09 会话标题

- **需求背景与动机**：会话列表若只显示消息截断预览，多个会话难以区分（全是「帮我…」的前 40 字符）；每次都手动 /rename 又太繁琐。自动标题让列表可扫读（侧栏一眼定位目标会话），手动命名保留最终控制权。
- **功能规格**：
  1. **触发条件**：首轮对话**成功结束后**后台触发（fire-and-forget，不阻塞下一轮提交）；前置条件四项——当前无标题、无生成在飞（titleGenerating 去重）、gate 空闲、history 已有 user+assistant 消息。
  2. **处理规则**：生成是一次独立 LLM 调用（不进 loop、不发 stream 事件）：提示词要求「只输出标题本身，不超过 32 字，不加引号、句号或『标题：』前缀」；输入取首条用户消息与首条助手回复各前 500 字符；maxRetries 1。
  3. **参数依据**：maxOutput 512——上限不是目标，普通模型二十来字即停，但推理模型的思考 token 计入该预算，给 64 会被思考烧光导致 content 为空而静默失败（这是 512 的来历）。
  4. **产出清洗**：取首行 → 剥离首尾引号（`"'「『」』` 等）→ 截断 32 字。
  5. **输出与用户可见表现**：写入后广播 notice「已自动生成会话标题…」+ 重推 session_list + 落盘会话存档。
- **边界与失败模式**：
  - 手动命名（`/rename <名称>` 或侧栏铅笔按钮）优先于自动——写回前再查一次标题，生成期间用户若已 /rename，自动结果直接丢弃（竞态窗口保护）。
  - 生成失败/空结果返回 null，调用方静默跳过（标题是装饰，不值得打扰用户）。
  - 生成期间用户立即开始下一轮 → gate busy 条件跳过本次生成。
- **验收标准**：
  1. 当首轮对话成功结束且会话无标题，则数秒内生成标题（≤32 字）并重推 session_list。
  2. 当标题生成期间用户执行 /rename，则自动结果被丢弃，最终标题为手动命名值。
  3. 当标题生成在飞时再次完成轮次，则因 titleGenerating 去重不重复生成。
  4. 当生成调用失败或产出清洗后为空，则返回 null 静默跳过，无 notice 无报错。
  5. 当 gate 忙碌（用户已开始下一轮），则跳过本次生成。
- **场景走查**：用户首轮提交「帮我排查 vitest 超时」→ 对话 finished → 数秒后侧栏该会话标题变为「排查 vitest 超时问题」（≤32 字），notice 提示 /rename 可重命名。

### R-DLG-10 状态与用量广播

- **需求背景与动机**：状态机、token 估算、会话用量都是 agent 内部状态，UI 若不持续同步，状态栏与信息面板就只能显示陈旧数据——用户会在「明明在跑」的界面上反复重试，或在窗口将满时毫无预警地撞上压缩。广播机制把内部状态变成 UI 可实时消费的事实。
- **功能规格**：
  1. **广播源一（状态变化）**：`emitState` 在状态机 fire 后若状态有变，广播 `state { from, to }` 并随行一条 `status_state { sessionId, provider, model, cwd, state, estimatedTokens, windowTokens, usage { promptTokens, completionTokens, turns } }`。
  2. **广播源二（主动查询）**：`status_request` / `set_cwd` 成功后复用同一条 `status_state`（统一 emitStatusState 出口）。
  3. **广播源三（轮末）**：`finished` 携带本轮真实 API usage（prompt/completion tokens，轮内多次调用累加）。
  4. **token 估算**：`estimateCurrentTokens` 按当前 context 内容**本地现算**——与实际请求同口径（同一 systemPrompt + 同一工具 schema），不等 API 返回，流式过程中数字即可跳动。
  5. **仪表盘**：`context_request` 回 `context_state { estimatedTokens, windowTokens, percent, breakdown(system/user/assistant/tool/tools 分桶), lastTurn, sessionUsage, compactions }`——分段之和等于总估算。
  6. **轮询节奏**：TUI 在运行中每 2s 轮询 `context_request` 刷新状态栏；WebUI 信息面板展开时每 3s 轮询。
  7. **配置联动**：config_updated 钩子触发 `emitStatusState`，isConfigured 为 true 时立即推送——切模型不等下一轮对话。
- **边界与失败模式**：
  - 配置未就绪（无 provider）时 status_state 发射失败被静默跳过——不阻塞状态迁移本身。
  - `context_state` 查询在未配置时回 notice「尚未配置 provider，请先 /config」。
  - 估算器是粗估（非 tokenizer），面板注明口径差异（会话累计用量包含已被压缩掉的历史用量，天然大于当前估算，见 R-SES-10）。
- **验收标准**：
  1. 当状态机发生一次可见迁移，则 UI 先后收到 `state` 与 `status_state`，状态栏数字与 provider/model 同步刷新。
  2. 当用户发送 status_request，则收到与状态变化广播同构的 status_state。
  3. 当轮次 finished，则事件携带本轮真实 usage 并累计进 sessionUsage、记为 lastTurn。
  4. 当 context_state 返回，则 breakdown 各分桶之和等于 estimatedTokens（同口径自洽）。
  5. 当 /config 切换模型成功，则状态栏立即显示新 provider/model，无需发起对话。
- **场景走查**：用户在 /config 切换模型 → config_updated 钩子触发 `emitStatusState` → 状态栏/顶栏立即显示新 provider/model，不等下一轮对话。
