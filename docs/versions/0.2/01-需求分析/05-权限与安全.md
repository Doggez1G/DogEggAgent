# R-PRM 权限与安全

权限系统回答一个问题：**这次工具调用允不允许执行**。它决定 agent 的自主边界——读代码可以放行，改文件要确认，删库必须拒绝。三层结构：配置三桶（持久）、会话提升（临时）、固定安全默认（兜底，不可关闭）。

## 工作原理概述

**三份数据，一个引擎。** 权限判定消费三类数据：①配置三桶（config.json 的 `permission` 字段，v3 结构化：桶 → 键 → `{ whole, patterns }`，用户持久配置）；②会话提升（PermissionManager 内存中的 `Map<工具名, 模式数组>`，用户在审批弹层点「始终允许」产生，随会话存档持久化）；③工具身份快照（注册表 `identities()` 的现取提供者——MCP 服务键匹配按身份进行）。三者在 `classifyPermission`（bridge 契约包的纯函数）里汇合，优先级固定五行：`reject 命中 → 拒绝；会话提升命中 → 放行；ask 命中 → 审批；allow 命中 → 放行；全部未命中 → 默认 ask`。引擎是 schema 的唯一解释者——agent 运行时与两端 UI 显示共用同一实现，判定与展示永不漂移。

**归一化在判定之前。** 路径类匹配必须先统一坐标系，agent 侧 PermissionManager 在调用引擎前做两件归一：

- 参数侧：把 path 经 `realpathSync` 解析为真实绝对 posix 路径（符号链接在此被识破）；
- 规则侧：把带锚点的 path 模式按锚点解析（`./`/`../` 相对 cwd、`~/` 相对主目录、绝对原样、`*` 开头保留）。

shell 的 command 模式与 MCP 服务键不动（无 cwd 概念）。归一化只做解析、不决定作用域——作用域由模式自己的锚点声明，无锚点的字面量模式在加载期就被拒绝。

**两类键，两种匹配函数。** 桶键分两类：

- 内建工具键（read_file、shell 等）：patterns 是**主参数模式**——path 主参数用 matchGlob（`*` 单段、`**` 跨段、`?` 单字符，段边界是安全性质），command 主参数用 matchWildcard（平文本，`*` 通配到结尾）；
- MCP 服务键 `mcp:<服务名>`：patterns 是服务内部工具名选择器（启用匹配，永不涉参数），按身份命中。

桶内多条规则 OR 匹配（任一命中即命中），匹配语义 fail-closed（无参数可比、参数非字符串、模式全不命中 → 不命中）。

**运行时提升的生命周期。** 审批弹层的四档决策经 `permission.apply` 落库：allow_always → 整工具（patterns 空）；allow_always_scoped → 追加范围模式（path 模式落库时解析为绝对；去重；已有整工具提升时窄范围无意义直接忽略）。提升可 snapshot（落盘/展示）/restore（resume）/revoke（/permissions 撤销）/reset（新建会话清空）。配置编辑重建 PermissionManager 实例时先 snapshot 再 restore——用户点过的「始终允许」不因改配置丢失。

**审批是协作式挂起。** 落 ask 的调用经 `requestPermission` 返回一个 Promise，在收到 UI 的 `permission_decision` 消息时才 resolve——agent 的轮次在此挂起，状态机停 waiting_permission，UI 弹审批层；范围模式由 `deriveAlwaysScope` 在请求时刻随行下发（推导不出则 UI 维持三档）。

## 需求点

### R-PRM-01 三桶与固定安全默认

**需求动机**：agent 能读写文件、执行命令——没有权限网关，一条模型幻觉指令（`rm -rf`）就能造成不可逆破坏；同时「什么都问」会让用户疲于点确认。三桶 + 安全默认让用户按风险分级授权。

**详细行为**：

- `allow`（放行）/ `reject`（拒绝）/ `ask`（每次询问）三个桶，持久保存于 config.json 的 `permission` 字段；判定顺序固定（见 R-PRM-07）。
- 出厂默认（仅对「配置文件未写 permission 字段」的加载生效；用户显式配置的三桶不受影响）：
  - allow：read_file / ls / glob / grep 整工具（whole: true）——只读安全、探索顺畅的前提；
  - ask：write_file / edit_file / shell 整工具——写入与命令需审批。
- **「未列出 → ask」是固定安全默认**：宁可多问，不可漏拦；该兜底不可被任何配置关闭。

**边界与失败模式**：

- 配置文件里删掉整个 permission 字段 → 回落出厂默认而非「全放行」。
- 第三方 MCP 工具默认 ask 无需配置（固定安全默认自然覆盖未列出的键）。
- /config 权限树里有只读说明行「（未列出的工具一律询问——固定安全默认）」，编辑器不提供关闭入口。

**场景走查**：全新安装 → 模型调 read_file 自动放行 → 调 edit_file 弹审批 → 用户在 /config 把 write_file 加入 allow → 后续写入静默放行。

### R-PRM-02 规则形态（v3 结构化）

**需求动机**：旧格式（条目数组/字符串数组）无法表达「整工具生效但保留已配的细规则」——用户在「整选」与「细化」间切换时配置会丢。v3 把两种状态显式化。

**详细行为**：

- 桶内是「键 → 规则」映射，每条规则 `{ whole: boolean, patterns: string[] }`：
  - `whole: true` → 整键生效：该键覆盖的所有调用都按本桶处理；patterns 不参与匹配，仅作取消整选后的恢复内容（编辑器保存用户配过的细规则，切换整选不丢）；
  - `whole: false` → patterns 生效（多条 OR 匹配）；
  - **空 patterns = 键存在但不命中任何规则**（编辑中的空选态，语义上等于暂无规则）。
- 编辑器两端提供整选开关 + 细化编辑：切回整选保留已配规则，取消整选原样恢复。

**边界与失败模式**：

- 注意配置层与会话提升的语义刻意不同：配置的「空选 = 不命中」，会话提升的「空数组 = 整工具提升」（运行时内部结构，非用户配置）。
- patterns 无论 whole 与否都参与加载期锚点校验（它们是规则的待命态，编写期就该正确）。
- 空选态在 UI 上有明确文案（「未选择任何工具——本键当前不命中任何规则」），避免用户误以为在生效。

**场景走查**：用户把 shell 配了 `git *`、`npm *` 两条模式 → 切整选（「整工具生效」）→ 两条模式仍显示为保留态 → 取消整选 → 两条模式原样恢复生效。

### R-PRM-03 键的两类与主参数表

**需求动机**：模式字符串必须落到「工具的哪个参数」上才有意义——shell 的模式匹配的是 command，文件工具匹配的是 path。这个映射若无单一出处，三端（引擎/TUI/WebUI）各自猜测必然漂移。

**详细行为**：

- **内建工具键**（如 `read_file`、`shell`）：patterns 是主参数模式——主参数表 `PRIMARY_SPECIFIER` 立法：shell → `command`，其余（read/write/edit/ls/glob/grep）→ `path`（`primarySpecifier()` 缺省 path，新工具非 path 主参数必须显式登记）。
- **MCP 服务键** `mcp:<服务名>`：必须带前缀，裸服务名键加载期拒绝——config schema 的 superRefine 交叉校验：桶键若与 mcpServers 里的服务名同名且无前缀，报错并指明应写 `mcp:<名>`（静默失配比报错危险）。patterns 是服务内部工具名选择器（`browser_close`、`browser_*` 平文本通配）——启用匹配，永不涉及执行参数。
- 服务键按注册期身份匹配，不解析 LLM 可见名；服务名零字符约束（含 `__`、中文、空格、与内建同名均无歧义——前缀即语义）。

**边界与失败模式**：

- 手写通配工具键（如 `mcp__x__*`）也照常按名字分支匹配（防御支持，编辑器只产精确名）。
- 唯一加载期拒绝的键形态：裸服务名键（与 mcpServers 服务同名）。

**场景走查**：用户在 ask 桶配 `shell: { whole: false, patterns: ['rm *', 'git push *'] }` → 模型调 `shell { command: 'rm -rf dist' }` → command 主参数命中 `rm *` → 弹审批；调 `git status` → 未命中 → 未列出 → 默认 ask（shell 未在 allow）。

### R-PRM-04 路径作用域锚点与 realpath 防逃逸

**需求动机**：路径模式若无显式作用域，`docs/**` 会从盘根匹配（只能命中盘根下名为 docs 的条目）——这几乎必然是用户忘了写锚点，静默失配比报错危险得多。而符号链接则是对路径规则的经典逃逸手段：词法上在范围内、真实读取越界。

**详细行为**：

- **锚点校验（加载期）**：内建 path 工具（BUILTIN_PATH_TOOLS 六个）的 patterns 必须显式声明作用域，四种写法：
  - `./` 或 `../` 开头 → cwd 作用域（`..` 可出 cwd，写明就行）；
  - `~/` 开头 → 主目录作用域；
  - 盘符（`C:/`）或 `/` 开头 → 绝对子树；
  - `*` 开头 → 无锚点，glob 从文件系统根匹配（`**/x` 全盘任意深度、`*/x` 仅盘根一层）。
- 字面量打头的裸模式（`docs/**`、`test`）直接拒绝加载，错误信息列出全部合法写法。
- 该校验只对内建 path 工具生效（MCP 服务键的 patterns 是工具名选择器，无路径语义；shell 的 command 模式无作用域概念）。
- **realpath 归一（判定期）**：参数按真实位置匹配——目标存在 → `realpathSync`（OS 沿链接解析，含 Windows junction）；目标不存在（write_file 新建）→ 真实父目录 + 文件名；父目录也不存在 → 词法解析兜底。cwd 内符号链接指向 cwd 外时词法匹配会被骗，真实位置越界即失配落 ask（ADR-0010）。

**边界与失败模式**：

- `../` 锚点刻意允许出 cwd（用户显式声明就是这个意思）。
- 规则与参数归一到同一 posix 坐标系后 matchGlob 才有意义（Windows 反斜杠已统一）。
- 模式缺失锚点 → 加载报错 + /config 编辑保存时同样校验拦截回滚。

**场景走查**：用户配 `read_file: { whole: false, patterns: ['./src/**'] }` → 模型读 `src/index.ts` → 归一后 `D:\proj\src\index.ts` 命中 → allow；读 `link-out/secrets`（link-out 指向 cwd 外）→ realpath 越界 → 失配 → 未列出 → ask。

### R-PRM-05 会话提升（apply/snapshot/restore/revoke）

**需求动机**：同一片区域反复审批是最大的摩擦来源（连改 5 个文件 = 5 次确认）。「始终允许」需要生命周期管理——会话内有效、可查看、可撤销、可随会话恢复。

**详细行为**：

- 提升是 PermissionManager 内存中的 `Map<工具名, 模式数组>`，四个操作构成生命周期：
  - **apply**（审批决策落库）：allow_always → 整工具（set(tool, [])，覆盖已有窄范围——提宽不提示，/permissions 可见可撤）；allow_always_scoped → 追加范围模式（去重；path 模式经 `resolve(cwd, p)` 解析为绝对形式落库；已是整工具时忽略窄范围）；
  - **snapshot**（导出快照）：/permissions 展示、会话落盘、配置编辑保留共用同一形态（`[{ tool, patterns }]`）；
  - **restore**（按存档还原）：resume 时先 reset 再 restore，同目录工具不再重复审批；
  - **revoke**（撤销）：不带 pattern 撤整工具；带 pattern 撤单条，撤光即整条移除（与配置桶「删光模式留整工具」刻意不同：这里的每条模式是独立的授权事件）。
- 提升命中优先于配置 ask 规则（用户本会话最新显式意图），但 reject 恒压过提升。

**边界与失败模式**：

- 提升是会话隔离的——新建/切换会话 reset 清空，恢复会话按存档还原（见 06-会话管理 R-SES-09）。
- 旧会话文件的 allowedTools 字段（纯工具名数组）不再读取——旧会话提升视为空。
- 展示层必须区分「配置永久 allow」与「会话提升 always」（`effectivePerm`：bucket 为 allow 且 sessionRules 有该工具且配置 allow 桶没有该键 → 显示 always）。

**场景走查**：用户对 edit_file 点「对此范围不再询问（./src/**）」→ 模式落库为绝对路径 → 同会话内 src 下后续编辑静默执行 → /permissions 面板显示该模式 → 点撤销 → 下一次 src 内编辑重新弹审批。

### R-PRM-06 范围模式自动推导

**需求动机**：「对此范围不再询问」的范围不能由模型或用户手填（模型会倾向写宽）——agent 必须给出「最窄的可复用范围」：窄到不放过大片未批准区域，宽到消除同一片区域的重复审批。

**详细行为**：

- `deriveAlwaysScope(tool, input, cwd)` 在 permission_request 时刻推导，随请求下发 `alwaysScope: { pattern }`；推导不出（参数缺失/形态异常）返回 undefined，UI 维持三档（fail-safe）。
- 推导规则按主参数分派：
  - **command（shell）**：首词前缀——命令按「程序名」聚类，首词就是用户心里「这类命令」的边界：`git status` → `git *`；无后续参数（`ls`）→ 精确 `ls`；
  - **path（六个文件工具）**：所在目录 `./<dir>/**`——重复审批的痛点来自同一片区域反复改；文件在 cwd 根部时回退精确 `./<file>`（父目录即 cwd，给 `./**` 等于放行全项目）；参数即 cwd 本身或在 cwd 外 → undefined（保守）；
  - **其余（无主参数）** → undefined。

**边界与失败模式**：

- 推导返回 cwd 相对形式（`./` 前缀），落库时才解析为绝对（匹配坐标系统一）。
- 审批弹层展示推导出的模式原文（「对此范围不再询问（./src/**）」）——用户点之前就知道授权范围。
- shell 的范围提升仍是平文本通配（`git *` 也命中 `git x && rm y`——命令模式是「便利而非安全边界」，见边界与立法）。

**场景走查**：模型调 `shell { command: 'git commit -m "fix"' }` 落 ask → 弹层四档含「对此范围不再询问（git *）」→ 用户点它 → `git *` 落库 → 后续所有 git 开头命令免审批。

### R-PRM-07 优先级的完整立法

**需求动机**：三桶 + 会话提升四层叠加时，判定顺序就是安全语义本身——顺序错了（如 allow 压过 ask）会让「例外强制确认」失效。

**详细行为**（五行源码即立法）：

```
1. reject 命中                    → 拒绝（安全底线，最高）
2. 会话提升命中                    → 放行（用户本会话最新显式意图）
3. ask 命中                        → 审批（显式「强制确认」压过宽放行——例外强制确认）
4. allow 命中                      → 放行
5. 全部未命中                      → 默认 ask（固定安全默认，不可配置关闭）
```

- 推论 1：**「allow 整组 + ask 勾选个别」可行**（整组放行、个别询问——ask 在第 3 层先命中）；反向「ask 整组 + allow 个别」不成立（ask 命中即问）。
- 推论 2：会话提升压过 ask 桶规则——否则对 write_file/shell 这些最常被提升的 ask 工具，提升会失效；提升仍被 reject 压制（配置层硬拒绝是底线）。
- 桶内多条规则 OR 匹配（任一命中即命中）；桶间是优先级关系（先到先判）。

**边界与失败模式**：

- 判定顺序实现在 `classifyPermission` 的五行 if——任何新桶/新层必须显式插入该序列并更新立法。
- 引擎对未知工具（无身份、无键）自然落到第 5 层默认 ask。

**场景走查**：配置 allow.read_file 整组 + ask.read_file `./secrets/**` → 读 `src/a.ts` → ask 桶模式未命中、allow 命中 → 放行；读 `secrets/key.txt` → ask 先命中 → 审批（例外强制确认生效）。

### R-PRM-08 编辑两端（TUI 树 / WebUI 设置）

**需求动机**：权限配置若只能手改 JSON，规则写错的成本（安全漏洞或全被拦）太高——两端 UI 必须提供同等能力的结构化编辑，且校验失败不落盘。

**详细行为**：

- TUI /config 权限树与 WebUI 设置 Permissions 区**同等编辑能力**：
  - 三桶卡片（桶内按键分组，MCP 服务键带来源标注）；
  - 整选开关（回车切换，恒可用）；
  - 模式行就地编辑/删除（d 键 / chips ×）；
  - MCP 服务键**勾选式细化**（对运行时工具清单勾选 + 通配规则行 + 添加通配——服务未运行时显示「已保存规则按保存内容生效」）；
  - 添加工具（内建逐个 + MCP 服务整组的 selectTool 选择器，**选择即钻入**）。
- 校验失败（模式缺锚点、schema 不合）编辑即报错回滚（validateConfig 回 lastGood 快照），不写坏配置。
- 固定安全默认在树里有只读说明行——不可编辑是立法。

**边界与失败模式**：

- 跨桶提示：同一键在其它桶也有规则时显示提示（防「已放行为什么还问」的困惑——ask 第 3 层压过 allow）。
- WebUI 添加下拉排除已有键。
- display-only 调用不传 args——参数化规则按 fail-closed 不命中，标签回落整键规则/默认 ask（展示层宁可保守，不替参数化规则宣称放行）。

**场景走查**：TUI /config → permission → allow → ＋添加工具 → 选择器列出内建工具与「playwright（MCP 服务）· 12 个工具」→ 选中即钻入该键细化层 → 回车切整组生效 → 保存广播 config_updated。

### R-PRM-09 格式演进不兼容（ADR-0013）

**需求动机**：权限格式历史上经历条目数组（M1）→ 字符串数组（v2）→ v3 结构化。兼容旧格式会让引擎背负三套解释逻辑，且旧格式无法表达整选/保留语义——静默的语义降级比报错危险。

**详细行为**：

- 权限配置只支持当前 v3 格式（`permissionSchema` 是唯一合法格式）：旧扁平条目数组、v2 字符串数组、`**` 标记形态 → 加载期 zod 校验失败直接报错并指引文档（bin/dogegg.ts 启动时给出明确错误）。
- 裸服务名键（未加 `mcp:` 前缀且与 mcpServers 服务同名）→ superRefine 交叉校验拒绝，错误信息指明应写 `mcp:<名>`。
- 服务键强制前缀立法见 ADR-0012/0013。
- /config 编辑期同一 schema 校验——错误在编辑时也会浮出并回滚。

**边界与失败模式**：

- 不兼容是双向的——新格式文件不被旧版本理解（预期）。
- 加载失败程序不会带病启动（宁可起不来也不能带着错误的权限边界跑）。

**场景走查**：用户从 0.1 升级，config.json 还是 v2 格式 → 启动报错「permission 配置格式不兼容…见 docs/config.md」→ 按文档迁移为 v3 → 启动成功。

## 边界与立法

- **命令模式是「便利而非安全边界」**：通配会命中命令链（`git *` 也命中 `git x && rm y`）——命令链拆分器（逐段判定）是独立后续批次；在此之前，危险命令的防线是 ask/reject 显式压制 + 默认 ask。
- 固定安全默认不可配置关闭：未列出 → ask 是最后防线。
- 会话提升是运行时内存结构（随会话存档持久化），与配置三桶分离；展示层必须区分「配置永久 allow」与「会话提升 always」（`effectivePerm`/`displayPerm` 的标签来源区分）。
- 内置读豁免（实现细节）：read_file 落 ask 且目标位于 agent 管理的资产目录（用户级 skills 目录）内时自动 allow——系统提示引导模型读 SKILL.md，不应反复弹审批；仅此一例，且只对配置桶落 ask 生效（reject/提升等更早判定不受影响）。
