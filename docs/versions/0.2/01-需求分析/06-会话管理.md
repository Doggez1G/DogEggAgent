# R-SES 会话管理

> 会话是对话历史的持久化单元：可恢复、可删除、可切换工作目录、可命名。用户在项目 A 里修完 bug，明天打开 agent 能接着昨天的上下文继续干——这是会话管理的目标。覆盖：存档内容与落盘时机、恢复链、会话列表与项目分组、删除与接管、/cd 联动、标题、权限提升隔离、用量双口径。

## 域机制概览

**工作集与存档的分离。** Conversation 是 agent 运行期的可变对话状态（唯一数据归属）：history、context、thinking 数组、sessionId、cwd、累计用量、压缩计数、标题。会话存档（SessionSnapshot）是它某一时刻的完整快照——「发生过什么（history/context）+ 授权到哪（sessionPermissions）+ 干到哪（usage/compactions）+ 在哪干（cwd）+ 想过什么（thinking）+ 叫什么（title）」。所有落盘调用点都经 `snapshotFull()` 这一个组装入口，保证四件套（history/context/提升/用量）之外的字段不遗漏。

**存档四件套。** history：完整原文（永不淘汰），恢复后 UI 重现全部对话；context：含压缩后摘要状态的模型视图——恢复后模型看到的 context 与中断前一致；sessionPermissions：会话权限提升（整工具与范围模式，path 模式已解析为绝对），resume 后 restore 免重复审批；usage：累计 prompt/completion tokens 与轮数，跨刷新续计。附加字段：compactions（压缩次数）、cwd（恢复时一并还原项目归属）、thinking（推理内容数组，与 assistant 消息一一对应，恢复思考块显示）、title。

**自动落盘时机。** 落盘不依赖用户手动保存——对话结束（finished/error/cancelled 全路径）、手动压缩成功、/rename、/cd 切换成功、自动标题写回（仅 gate 空闲期；轮中触发的标题只写内存，轮末落盘时随快照一并持久化）、/clear 清空后（必须同步落盘——内存与磁盘是同一工作集的两份，只清内存会让 resume 复活旧历史；落盘失败发 notice 告知 resume 可能恢复旧历史）、新建会话（持久版）都会立即 save。另有**轮中检查点**：轮次进行中每 15s 节流落盘一次（onProgress 检查点——每条消息都写会让高频工具轮把磁盘打成热点，15s 粒度把崩溃损失上限压到 15s 进度；快照落盘前对 history/context 修补未配对 tool_calls，崩溃恢复后下一轮请求不 400）；进程退出（SIGINT/SIGTERM 优雅收尾）时兜底最终落盘。写入是**原子写**（先写 tmp 再 rename，tmp 名含 pid 与随机后缀防并发互踩），避免半写文件损坏会话。轮末落盘失败发 notice（「会话保存失败（磁盘空间不足或权限问题）」），新建/标题等次要路径静默——不打扰但不无声丢主链路数据。

**恢复链。** `resume(id)` → SessionStore.load（含旧格式兼容回退）→ Conversation.load 整体替换工作集（快照带 cwd 时一并恢复）→ permission.reset + restore(存档提升) → 广播 `session_ready { id, messages, thinking }` → 两端 UI 按 history + thinking 重建消息块（含工具块按 tool_call_id 结构化配对）→ 恢复后首轮提交即可继续。

**删除与接管语义。** 删除是幂等文件删除（不存在静默成功）；删除**当前正在使用**的会话时，立即创建一个**不落盘**的新空会话接管界面——旧工作集必须被替换，否则下一轮落盘会把刚删掉的会话原样写回（「复活」）；但新会话不能立即落盘，否则删空的项目永远非空（僵尸空会话挡住 WebUI 删除项目）。接管会话首轮对话后才持久化。

### R-SES-01 持久化内容（存档四件套）

- **需求背景与动机**：恢复的价值 = 「不需要用户重新交代任何背景」。缺 history 则对话空白；缺 context 则模型失忆；缺提升则同一目录反复弹审批；缺用量则统计清零——任何一件缺失，resume 都不完整。
- **功能规格**：
  - 输入与前置：
    1. 每个会话一个 JSON 文件（`~/.dogegg/sessions/<id>.json`），由 snapshotFull() 统一组装、SessionStore.save() 原子写入。
  - 处理规则：
    2. 存档字段：`id`、`updatedAt`（save 时统一刷新，列表按它降序）、`history`（每条 user/assistant/tool 消息原文）、`context`（模型视图，压缩后仅剩摘要消息）、`sessionPermissions`（`[{ tool, patterns }]`，patterns 空 = 整工具提升）、`usage`（`{ promptTokens, completionTokens, turns }`）、`compactions`、`cwd`、`thinking`（`[{ text }]`，空字符串 = 该轮无思考、与 assistant 消息一一对应）、`title?`。
    3. 存档即「发生过什么 + 授权到哪 + 干到哪」的完整快照——history 与 context 双写分离（history 给 UI、context 给模型，压缩只动 context）。
    4. 两个形态刻意分离：SessionSnapshot（完整存档，落盘/恢复用）与 SessionSummary（列表轻量项：id/updatedAt/preview/cwd/title?）——列表扫描不反序列化全部消息细节到 UI。
  - 输出与用户可见表现：
    4. 文件为标准 JSON，可直接人工检视；updatedAt 为 ISO 时间戳。
- **边界与失败模式**：
  - load 兼容旧格式——只有 messages 字段的文件回退 `history = messages`、`context = [...history]`。
  - load 时对 history/context 修补未配对 tool_calls（与检查点落盘前同一修补规则、同一文案）——旧版本写入的配对毒化存档在恢复时被就地修复。
  - 旧 allowedTools 字段（提升的旧形态）不再读取，视为空（重新询问一次即可）。
  - 缺省字段逐个兜底（usage 归零、thinking 空数组）。
- **验收标准**：
  1. 当完成一轮含压缩的对话，则存档同时包含完整 history 与压缩后的 context，两者条数不同属预期。
  2. 当会话存有范围提升，则 sessionPermissions 中对应 patterns 为绝对路径形式。
  3. 当加载只有 messages 字段的旧格式文件，则 history/context 正确回退且不报错。
  4. 当存档缺 usage/thinking 字段，则 resume 后分别按 0 与空数组兜底。
  5. 当 thinking 存在空字符串条目（非推理轮），则恢复后对应消息不显示思考内容。
- **场景走查**：用户昨天在 `D:\work\app` 里修到一半 → 今天的存档里有 40 条 history、2 次压缩后的 context、`./src/**` 的 edit_file 提升 → resume 后三者全部还原。

### R-SES-02 自动落盘

- **需求背景与动机**：对话数据若只在显式保存时写盘，崩溃/断电就丢整轮；若每条消息写一次，IO 压力与半写风险又太高。轮次粒度的自动落盘是平衡点。
- **功能规格**：
  - 触发条件：
    1. 落盘触发点：
       1.1 轮次结束（runTurn 的 finally——成功/失败/取消全路径都落）；
       1.2 手动 /compact 成功后；
       1.3 /rename 命名后；
       1.4 set_cwd 切换成功后（立即落盘 + 重推 session_list——会话文件携带 cwd，WebUI 侧栏按 cwd 分组项目树，不即时保存的话新项目要等下一轮对话才出现）；
       1.5 自动标题写回后（仅 gate 空闲期立即落盘；轮中触发的标题只写内存，轮末落盘时随快照一并持久化）；
       1.6 新建会话（persist 版，让 list_sessions 立即返回新会话）；
       1.7 /clear 清空后（同步落盘防 resume 复活旧历史；落盘失败发 notice「历史已清空，但落盘失败…resume 可能恢复旧历史」）。
  - 处理规则：
    2. 原子写：tmp + rename（tmp 名含 pid 与随机后缀——固定 `<id>.json.tmp` 在双进程/同进程重入并发写同一会话时互踩；后缀在 .json 之后，list 的 .endsWith('.json') 过滤不会把残留 tmp 当会话文件）。
    3. 全部触发点走同一组装：snapshotFull()（permission.snapshotPermissions + usage + compactions 注入）→ sessions.save()——无第二组装路径，字段不遗漏。轮中另有 15s 节流检查点（轮次进行中的崩溃保护，见上）：快照在落盘前对 history/context 修补未配对 tool_calls（「会话在工具执行中被中断」文案），不改动内存真相。
    4. 落盘后侧栏会话列表同步刷新（session_list 广播，预览文本随最后一条消息更新）——/rename、set_cwd、自动标题三个触发点在 save 后各自显式重推。
  - 输出与用户可见表现：
    4. 正常路径落盘无感知（无 notice）；侧栏时间与预览即时更新。
- **边界与失败模式**：
  - 轮末落盘失败 → notice 提醒（不静默）。
  - /clear 落盘失败不打断清空本身（内存已清、UI 已可继续），但 notice 告知后果——resume 可能恢复旧历史。
  - 新建/标题/命名路径失败静默（主链路数据不受影响）。
  - 检查点是尽力而为——保存失败静默（磁盘故障在轮末 saveOrNotice 会再暴露一次）。
  - updatedAt 在 save 时统一刷新——列表按它降序（最新在前）。
- **验收标准**：
  1. 当一轮对话以错误或用户取消结束，则存档同样更新（部分结果入档）。
  2. 当落盘被模拟为失败（如目录只读），则轮末路径发 notice「会话保存失败…」，新建/标题路径无 notice；/clear 路径发「历史已清空，但落盘失败…」notice。
  3. 当新建会话成功，则 sessions 目录立即出现新文件且 list_sessions 返回它。
  4. 当检查写盘过程，则目标路径不会出现半写内容（tmp + rename）。
  5. 当自动标题写回成功，则存档 updatedAt 刷新且 session_list 重推（列表时间序更新）。
  6. 当 /clear 后立即 resume 同一会话，则恢复的是空对话（历史不复活）。
  7. 当轮次进行中崩溃，则重启后 resume 至少找回最近一次检查点（约 15s 内）的进度，且快照无未配对 tool_calls（下一轮请求不 400）。
- **场景走查**：一轮长对话 finished → 存档更新（history +40 条、usage 累计）→ WebUI 侧栏该会话的预览与时间即时刷新，无需刷新页面。
- **场景走查（新增）**：一轮对话进行中进程被强杀 → 重启 agent 后 resume → 找回最近一次检查点落盘的内容（最多丢约 15s 进度——轮中检查点节流的固有边界），未配对的 tool_calls 已在落盘前修补为「会话在工具执行中被中断」占位，续聊直接可用。

### R-SES-03 恢复（resume）

- **需求背景与动机**：「接着昨天干」是 agent 的核心场景——若 resume 后模型不知道之前干了什么、或又要重新审批一遍工具，恢复就是不完整的。
- **功能规格**：
  - 触发条件与输入：
    1. 入口：TUI `/session`（会话选择器：输入过滤 + ↑↓ + 回车）或 WebUI 侧栏点击 → `resume_session { id }`。
    2. 恢复链逐步：SessionStore.load（含旧格式兼容回退）→ Conversation.load 整体替换工作集（快照带 cwd 时一并恢复，lastTurn 置空；**加载时对 history/context 修补未配对 tool_calls**——兜底修复旧版本写入的配对毒化文件，恢复后下一轮请求不 400）→ permission.reset + restore(存档提升) → 广播 `session_ready { id, messages, thinking }`（thinking 空时省略字段）。
    3. resume 的 id 先过白名单（`/^[A-Za-z0-9._-]+$/`，防路径穿越读目录外任意 json）——非法 id 直接 notice「非法会话 id：X」拒绝，不发起加载。
  - 处理规则：
    3. 恢复后聊天区重现全部对话（含思考块与工具块——工具块按 tool_call_id 从 history 结构化重建，与实时 tool_start/tool_end 同构；纯 tool_calls 无正文的 assistant 不产生块）。
    4. 会话权限提升按存档还原（restore 后同目录工具不再重复审批）。
    5. 累计用量续计；cwd 恢复（项目→会话切换恢复目录——用户从另一个项目的会话切回来，工具执行基准目录跟着回去）。
  - 输出与用户可见表现：
    6. 两端按 session_ready 重建界面；恢复后首轮提交即可继续——模型看到的 context 与中断前一致。
- **边界与失败模式**：
  - 文件不存在/已损坏 → notice「会话 X 加载失败（文件不存在或已损坏）」不崩溃。
  - id 含白名单外字符（如 `/`、`\`、空格）→ notice「非法会话 id」拒绝——会话 id 会被直接拼进文件名，白名单是防路径穿越的第一道关口。
  - 运行中（gate busy）恢复被阻塞（工作集不可在中途换）。
  - MCP 连接状态不在存档里——恢复后 MCP 按当前配置重新连接，工具可用性由当前配置决定（存档里注册过的工具若 server 已删，模型收到「未知工具」回执自行调整）。
- **验收标准**：
  1. 当 resume 一个含 40 条 history、thinking 数组非空的存档，则聊天区消息数与 thinking 块与中断前一致。
  2. 当存档带 sessionPermissions，则恢复后同范围调用不再弹审批。
  3. 当存档 cwd 与当前 cwd 不同，则恢复后工具执行基准目录为存档 cwd。
  4. 当 resume 指向不存在的 id，则收到加载失败 notice，当前工作集不变。
  5. 当 gate busy 时发 resume_session，则被阻塞并 notice「运行中，请稍候」。
  6. 当恢复后查询 context_request，则 lastTurn 为空而 sessionUsage 为存档值（续计起点）。
- **场景走查**：用户 resume 昨天的会话 → 聊天区完整重现（40 条消息 + 折叠思考块 + 工具块带输出）→ 直接输入「继续跑剩下的测试」→ 模型凭压缩摘要 + 新消息准确接续。

### R-SES-04 会话列表

- **需求背景与动机**：多会话并行（不同项目、不同任务）时，用户需要一个可扫读的列表：哪个会话、在哪个项目、最后聊到哪、什么时候。
- **功能规格**：
  - 触发条件与输入：
    1. `list_sessions` → SessionStore.list 扫描存档目录（`*.json`）。
  - 处理规则：
    2. 每条产出：`id`、`updatedAt`（ISO 时间，降序排序最新在前）、`preview`（**history 末条非 tool 消息**的前 40 字符——用 history 而非 context：preview 要反映用户真实对话，context 可能只剩摘要）、`cwd`（项目分组依据）、`title?`（缺省时展示层回退 preview）。
    3. TUI 以会话选择器呈现（可输入过滤）；WebUI 侧栏按项目分组聚合（见 R-SES-06）。
    4. list 是纯查询——gate busy 时也可调用，不与动工作集命令同受阻塞约束。
- **边界与失败模式**：
  - 单个文件损坏不阻断整个列表——跳过解析并返回占位项（「（文件损坏）」）。
  - 目录不存在返回空列表；列表读取失败 → notice「会话列表读取失败」。
  - 末条消息 content 非字符串（如 tool_calls 无正文）时不产预览（preview 为空串）。
  - updatedAt 缺失的存档按空串参与降序排序——稳定排到末尾，不影响其余条目次序。
- **验收标准**：
  1. 当目录有 N 个存档文件，则列表返回 N 条且按 updatedAt 降序排列。
  2. 当某会话最后一条为 tool 消息，则 preview 取更早的非 tool 消息（取不到为空）。
  3. 当人为写入一个损坏 JSON，则列表仍完整返回其余条目，损坏条目显示占位文案。
- **场景走查**：用户 /session → 选择器列出 8 个会话（标题/预览/时间）→ 输入 "vitest" 过滤到 2 个 → 回车恢复。

### R-SES-05 删除与当前会话接管

- **需求背景与动机**：删除是清理手段，但删除「当前正在用的会话」有一个陷阱：若只删文件不换内存工作集，下一轮落盘会把会话原样写回（僵尸复活）；若换成一个立即落盘的空会话，刚删空的项目又变非空（挡住项目删除）。接管语义必须同时防住两者。
- **功能规格**：
  - 触发条件与输入：
    1. 可删除任意会话（TUI 选择器 d 键 / WebUI 侧栏，均带确认弹层）→ `delete_session { id }`。
  - 处理规则：
    2. 流程：gate busy 时阻塞 → id 先过白名单（非法 → notice「非法会话 id」，防路径穿越删目录外任意 json）→ `sessions.delete(id)`（文件不存在静默成功——幂等）→ 广播 `session_deleted { id }`（两端据此移除对应条目，无需重拉全列表）。
    3. 若删除的正是当前会话：notice「当前会话已删除，已切换到新会话」；`newSession(undefined, { persist: false })`——新 id、空工作集、提升清空，但**不落盘**；接管会话首轮对话后才持久化（防僵尸会话阻塞项目删除——用户删除项目下最后一个会话时，项目才能真正消失）。
    4. 接管不改变 cwd——新会话继承当前工作目录（newSession 未传 cwd 时 reset 不动 cwdValue）。
  - 输出与用户可见表现：
    4. 界面立即切到全新空白对话，侧栏该条目消失。
- **边界与失败模式**：
  - 删除失败（磁盘权限）→ notice「删除失败」且不做接管（当前会话仍在）。
  - 接管会话若用户直接 /quit 不发一言 → 磁盘上无任何残留文件。
  - 删除非当前会话 → 无接管，列表刷新即可。
- **验收标准**：
  1. 当删除当前会话后不提交任何消息，则 sessions 目录无新文件出现。
  2. 当删除当前会话后提交一条消息，则落盘的是一个全新 id 的会话文件。
  3. 当 delete 指向不存在的 id，则静默成功并广播 session_deleted。
  4. 当 gate busy 时发 delete_session，则被阻塞并 notice。
  5. 当删除的会话非当前会话，则当前工作集不变、仅列表刷新。
- **场景走查**：WebUI 里用户删除当前会话 → 确认弹层 → 界面立即变成全新空白对话（侧栏该条目消失）→ 用户不提交任何消息 → `~/.dogegg/sessions/` 里没有新文件出现。

### R-SES-06 项目维度（分组与遗忘）

- **需求背景与动机**：会话天然按项目聚类（同一个 cwd 下反复工作）——平铺列表在 20+ 会话后不可用。项目维度的聚合与「遗忘」让侧栏成为轻量工作区管理器。
- **功能规格**：
  - 处理规则：
    1. 分组依据是**会话存档的 cwd**，不是当前工作目录——历史会话永远归属它创建时的项目。
    2. WebUI 侧栏按 cwd 分组聚合会话树（组头 = 项目路径，条目 = 标题/更新时间/预览）；「添加项目」经目录浏览器选中 cwd 后 new_session(cwd)（agent 侧校验：路径不存在或不是目录 → notice，不新建）。
    3. new_session 的 persist 语义：缺省（WebUI 添加项目、/new）为 true——立即保存空会话让 list_sessions 即时返回；仅删除接管的替换场景传 persist=false（见 R-SES-05）。新建成功广播 session_ready（messages 为空数组、无 thinking 字段）。
    4. 项目可显式「遗忘」：删除其下全部会话后项目从侧栏消失——WebUI 的删除项目操作是「逐个 delete_session + 本地 knownProjects 清单移除」的组合（前端维护已见项目的本地清单，让 0 会话的占位组也能显示和移除）。
    5. 项目目录本身不被删除，可随时重新添加。
  - 输出与用户可见表现：
    6. 侧栏项目树随 session_list 刷新（落盘触发点都会重推）。
- **边界与失败模式**：
  - cwd 为空的旧存档归入「(unknown)」组。
  - 删除项目前有确认弹层并明示将删除 N 个会话记录。
  - 删光会话后若存在「接管中未落盘」的空会话不会撑回该项目（R-SES-05 的 persist=false 语义）。
- **验收标准**：
  1. 当两个不同 cwd 的会话并存，则侧栏出现两个项目组且各归其位。
  2. 当删除项目下全部会话，则该项目组消失且磁盘上对应存档文件全部删除。
  3. 当 new_session 传入不存在的 cwd，则收到 notice 且不产生新会话。
  4. 当存档无 cwd 字段，则归入 (unknown) 组而非丢失。
  5. 当删除项目下最后一个会话，则项目组消失且 sessions 目录无空会话文件残留（persist=false 语义兜底）。
- **场景走查**：侧栏两个项目组（app、blog）→ 用户删除 blog 项目 → 确认（提示 3 个会话将被删除）→ 三个 delete_session + 本地遗忘 → blog 组消失，磁盘上三个存档文件删除。

### R-SES-07 工作目录切换（/cd）

- **需求背景与动机**：用户可能中途切换目标项目（在 app 里聊到一半要去 blog 改文章）——cwd 不只是显示信息，它是工具执行基准、权限归一锚点、项目级扫描根的公共源头，必须原子切换并联动全部下游。
- **功能规格**：
  - 触发条件与输入：
    1. `/cd <path>`（WebUI 经目录浏览器）→ `set_cwd` 消息 → gate busy 阻塞（避免 in-flight 工具写到错误目录）。
    2. set_cwd 是运行期改 cwd 的唯一 agent 侧入口（new_session(cwd) 在新建时刻设置）——两者共用 conversation.setCwd，工具执行、权限归一、项目扫描读同一 cwdValue。
  - 处理规则：
    3. 校验：resolve + statSync isDirectory；不存在 → notice「路径不存在」；不是目录 → notice。
    4. 校验通过 → `conversation.setCwd(resolved)`，随后触发联动链：
       4.1 项目级 skills 目录重扫（skills.setProjectDir + emitSkillsList——新项目的技能出现、旧项目的消失，系统提示段下一轮请求自动生效）；
       4.2 MCP diff 重建（项目级 .mcp.json 随 cwd 变化）；
       4.3 立即落盘 + 重推 session_list（项目树即时出现新分组）；
       4.4 status_state 推送（cwd 同步到状态栏与 @path 联想候选）。
  - 输出与用户可见表现：
    5. notice「工作目录已切换到 X」。
- **边界与失败模式**：
  - 切换只影响此后——已在 context 里的历史消息与工具结果不重写（模型若需要新项目信息需重新探索）。
  - 权限路径规则按 cwd 归一——`./src/**` 这类锚点模式在新 cwd 下有新含义（刻意的：作用域跟会话 cwd 走）。
  - 落盘失败静默（切换本身已成功并提示）。
  - 切换后的 status_state 推送不依赖 provider 配置——cwd 独立于 config，未配置 provider 也能完成切换显示。
- **验收标准**：
  1. 当 /cd 到有效目录，则状态栏 cwd 更新且收到切换成功 notice。
  2. 当 /cd 到不存在路径或文件路径，则 notice 指明原因且 cwd 不变。
  3. 当新项目有 .mcp.json 与项目级 skills，则切换后对应 server 与技能立即出现。
  4. 当 gate busy 时发 set_cwd，则被阻塞并 notice。
  5. 当切换成功后立即查看 session_list，则该会话的 cwd 已更新（项目树即时出现新分组）。
- **场景走查**：`/cd D:\work\blog` → 状态栏 cwd 变化 → /skills 面板出现 blog 的技能 → 项目级 MCP server（blog 专属）自动启动 → @ 联想列 blog 的文件 → 侧栏新增 blog 分组。

### R-SES-08 标题（手动优先）

- **需求背景与动机**：标题是列表可扫读性的关键——自动生成解决「懒得命名」，手动命名保留最终控制权，两者的优先级必须明确。
- **功能规格**：
  - 触发条件与输入：
    1. 手动命名（`/rename <名称>` 或侧栏铅笔按钮）优先于自动标题——手动 setTitle 后自动生成跳过（conversation.getTitle() 有值即跳过），生成期间的竞态窗口在写回前再查一次（见 R-DLG-09）。
  - 处理规则：
    2. /rename 的实现：trim 后为空 → notice 用法提示；成功 → setTitle + 立即落盘 + notice「会话已命名」+ session_list 广播。
    3. 自动标题仅在会话无标题、首轮已有 user+assistant 消息、gate 空闲时生成一次；生成中再次完成轮次经 in-flight 去重跳过（titleGenerating 标志）。
    4. 自动标题写回前再查一次 conversation.getTitle()——生成期间 /rename 已命名的直接丢弃自动结果；写回成功 notice「已自动生成会话标题「X」（/rename 可重命名）」+ 落盘 + session_list。
  - 输出与用户可见表现：
    5. WebUI 重命名弹框预填「原名」（标题优先，无标题回退预览文本）——在原名基础上修改而非从空白开始；「原名」直接取自列表项的 title/preview 字段。
    6. 标题变更同步侧栏与状态栏（TUI 状态栏 title 字段随 status_state 刷新）。
- **边界与失败模式**：
  - 命名落盘失败静默（内存标题已生效，下次轮末落盘会补上）。
  - 预览与标题的关系：列表展示 `title || preview`——标题永久覆盖预览显示，但预览仍在（重命名弹框的回退来源）。
- **验收标准**：
  1. 当 /rename 成功，则侧栏与状态栏即时显示新标题且存档 title 字段更新。
  2. 当自动标题生成期间用户手动 /rename，则自动结果因写回前复查被丢弃，手动标题保留。
  3. 当 /rename 只传空白，则收到用法提示 notice 且标题不变。
- **场景走查**：首轮对话自动生成「排查 vitest 超时问题」→ 用户 /rename「vitest 超时排查（0.2）」→ 侧栏与状态栏同步更新 → 后续自动标题不再触发。

### R-SES-09 会话隔离（权限提升）

- **需求背景与动机**：「始终允许」若跨会话生效，用户在项目 A 给 shell 的提权会泄漏到项目 B 的会话里——临时授权必须以会话为边界；但恢复同一个会话时授权又要回来（否则 resume 失去意义）。
- **功能规格**：
  - 处理规则：
    1. 会话权限提升只在本会话生效：**新建会话** → `permission.reset()` 清空提升集；**切换会话**（resume 另一个）→ reset + 按目标存档 restore；**恢复会话**（resume 自己的存档）→ reset + restore（存档里的提升原样回来，含路径解析结果）。
    2. 配置三桶是持久的，跨会话不变——隔离的只有「用户在本会话内点过的始终允许」。
    3. 隔离边界是「会话」而非「项目」——同一项目下的两个会话互相隔离提升（reset 以会话生命周期为界）。
  - 输出与用户可见表现：
    3. WebUI 端在 session_ready 时清空本地提升镜像并重新播种 permissions_request——面板显示与 agent 内存一致。
- **边界与失败模式**：
  - 提升随存档持久化（sessionPermissions 字段）——不是「关闭即丢」而是「换会话不跟」。
  - 旧格式 allowedTools 不读取（见 R-SES-01）。
  - /permissions 面板撤销（permission_revoke）只影响当前会话的内存提升，立即重推清单。
- **验收标准**：
  1. 当会话 A 提权后 /new 新建会话，则同参数调用重新弹审批。
  2. 当 resume 回会话 A，则 A 存档中的提升原样生效（含绝对路径模式）。
  3. 当切换到从未提权的会话 B，则 B 中无任何提升（不会读到 A 的）。
  4. 当配置三桶在 A 中有 allow 规则，则 B 中同样生效（配置跨会话）。
  5. 当存档无 sessionPermissions 字段，则恢复后提升为空（旧格式兼容路径）。
- **场景走查**：会话 A 里给 `git *` 提了权 → /new 新会话 → 跑 `git status` 重新弹审批（隔离生效）→ resume 回会话 A → `git status` 又免审批了（存档还原）。

### R-SES-10 用量累计（双口径）

- **需求背景与动机**：「这个会话花了多少 token」与「当前 context 占多少」是两个不同的问题——前者是成本累计（含已被压缩掉的历史），后者是窗口占用。混用一个数字会两者都错。
- **功能规格**：
  - 处理规则：
    1. 会话累计（`usage`）：promptTokens/completionTokens/turns 跨轮累加并持久化，resume 续计——数据来自 API 真实返回（`stream_options.include_usage`），每轮的 prompt+completion 加进累计并记为 lastTurn（最近一轮快照，与本地估算并排对照可校准误差）；turns 与 usage 捆绑累加——本轮 API 未返回用量则轮数同样不计（口径一致）。
    2. 当前 context 估算：本地粗估（CJK 1 token/字、其余 4 字符 ≈ 1 token）现算 system + context + 工具 schema，驱动压缩阈值与进度条。
    3. context_request 的载荷字段级构成：`estimatedTokens`（当前估算）、`windowTokens`、`percent`、`breakdown { system, user, assistant, tool, tools }`（分段估算）、`lastTurn`（最近一轮真实用量，resume 后为空）、`sessionUsage`、`compactions`——一个请求看全双口径。
    4. status_state 每次状态迁移随行 estimatedTokens/usage——状态栏的 token 显示不依赖手动刷新。
    5. 两口径在信息面板并排展示并注明——**累计包含已被压缩掉的历史用量，大于当前估算属预期**。
- **边界与失败模式**：
  - API 未返回 usage（部分端点不支持 stream_options）→ 该轮计 0（累计偏小但不中断）。
  - 压缩后 context 骤减而累计不变（正确语义）。
  - 手动压缩的计数入口 incrementCompaction 与自动压缩（LoopResult.compactions）分开累加，最终都进存档 compactions 字段。
  - lastTurn 只存内存不入存档——resume 后为空，下一轮成功后重新记入（面板相应字段空缺属预期）。
- **验收标准**：
  1. 当完成 N 轮对话，则 usage.turns = N 且 prompt/completion 为各轮真实返回之和。
  2. 当手动 /compact 一次，则 compactions 加 1 且 history 不变、context 缩短。
  3. 当 resume 后查看信息面板，则累计用量与存档一致续计。
  4. 当某轮 API 未返回 usage，则该轮 turns 与 token 计 0、对话继续。
- **场景走查**：信息面板 Context 卡显示「估算 18,400 / 128,000（14%）· 会话累计 96,000 tokens / 23 轮 · 最近一轮 7,200」——三个数字各有所指。

## 边界与立法

- history 永不淘汰是全局立法；会话删除是用户显式行为，不受此约束。
- 会话存档不包含 MCP 连接状态——恢复后 MCP 按当前配置重新连接（工具可用性由当前配置决定）。
- 动工作集类命令（new/resume/delete/clear/rename/set_cwd）在 gate busy 时被阻塞并 notice，不排队——轮次中途换工作集会损坏 context（rename/set_cwd 的 busy 落盘还会把检查点刚写的轮内进度回退成旧态）；list_sessions 等纯查询不受限。
- 优雅退出（SIGINT/SIGTERM）收尾链：运行中先取消轮次（与 cancel 消息同款双机制 + 挂起审批唤醒）→ 等待运行轮收尾（5s 宽限上限，退出路径不被单个收尾环节拖死）→ 停全部 MCP server → 尽力而为最终落盘（有历史才写）——空闲期直接退出与「取消收尾后仍有未落盘变更」两种情形都由此兜底；二次信号强制退出不再等待。
