# R-SES 会话管理

会话是对话历史的持久化单元：可恢复、可删除、可切换工作目录、可命名。用户在项目 A 里修完 bug，明天打开 agent 能接着昨天的上下文继续干——这是会话管理的目标。

## 工作原理概述

**工作集与存档的分离。** Conversation 是 agent 运行期的可变对话状态（唯一数据归属）：history、context、thinking 数组、sessionId、cwd、累计用量、压缩计数、标题。会话存档（SessionSnapshot）是它某一时刻的完整快照——「发生过什么（history/context）+ 授权到哪（sessionPermissions）+ 干到哪（usage/compactions）+ 在哪干（cwd）+ 想过什么（thinking）+ 叫什么（title）」。所有落盘调用点都经 `snapshotFull()` 这一个组装入口，保证四件套（history/context/提升/用量）之外的字段不遗漏。

**存档四件套。**

- **history**：完整原文（永不淘汰），恢复后 UI 重现全部对话；
- **context**：含压缩后摘要状态的模型视图——恢复后模型看到的 context 与中断前一致；
- **sessionPermissions**：会话权限提升（整工具与范围模式，path 模式已解析为绝对），resume 后 restore 免重复审批；
- **usage**：累计 prompt/completion tokens 与轮数，跨刷新续计。

附加字段：compactions（压缩次数）、cwd（恢复时一并还原项目归属）、thinking（推理内容数组，与 assistant 消息一一对应，恢复思考块显示）、title。

**自动落盘时机。** 落盘不依赖用户手动保存——对话结束（finished/error/cancelled 全路径）、手动压缩成功、/rename、/cd 切换成功、自动标题生成、新建会话（持久版）都会立即 save。写入是**原子写**（先写 `.tmp` 再 rename），避免半写文件损坏会话。轮末落盘失败发 notice（「会话保存失败（磁盘空间不足或权限问题）」），新建/标题等次要路径静默——不打扰但不无声丢主链路数据。

**恢复链。** `resume(id)` → SessionStore.load（含旧格式兼容回退）→ Conversation.load 整体替换工作集（快照带 cwd 时一并恢复）→ permission.reset + restore(存档提升) → 广播 `session_ready { id, messages, thinking }` → 两端 UI 按 history + thinking 重建消息块（含工具块按 tool_call_id 结构化配对）→ 恢复后首轮提交即可继续。

**删除与接管语义。** 删除是幂等文件删除（不存在静默成功）；删除**当前正在使用**的会话时，立即创建一个**不落盘**的新空会话接管界面——旧工作集必须被替换，否则下一轮落盘会把刚删掉的会话原样写回（「复活」）；但新会话不能立即落盘，否则删空的项目永远非空（僵尸空会话挡住 WebUI 删除项目）。接管会话首轮对话后才持久化。

## 需求点

### R-SES-01 持久化内容（存档四件套）

**需求动机**：恢复的价值 = 「不需要用户重新交代任何背景」。缺 history 则对话空白；缺 context 则模型失忆；缺提升则同一目录反复弹审批；缺用量则统计清零——任何一件缺失，resume 都不完整。

**详细行为**：

- 每个会话一个 JSON 文件（`~/.dogegg/sessions/<id>.json`），字段：
  - `id`、`updatedAt`（save 时统一刷新，列表按它降序）；
  - `history`：每条 user/assistant/tool 消息原文；
  - `context`：模型视图，压缩后仅剩摘要消息；
  - `sessionPermissions`：`[{ tool, patterns }]`，patterns 空 = 整工具提升；
  - `usage`：`{ promptTokens, completionTokens, turns }`；
  - `compactions`、`cwd`、`thinking`（`[{ text }]`，空字符串 = 该轮无思考）、`title?`。
- 存档即「发生过什么 + 授权到哪 + 干到哪」的完整快照。

**边界与失败模式**：

- load 兼容旧格式——只有 messages 字段的文件回退 `history = messages`、`context = [...history]`。
- 旧 allowedTools 字段（提升的旧形态）不再读取，视为空（重新询问一次即可）。
- 缺省字段逐个兜底（usage 归零、thinking 空数组）。

**场景走查**：用户昨天在 `D:\work\app` 里修到一半 → 今天的存档里有 40 条 history、2 次压缩后的 context、`./src/**` 的 edit_file 提升 → resume 后三者全部还原。

### R-SES-02 自动落盘

**需求动机**：对话数据若只在显式保存时写盘，崩溃/断电就丢整轮；若每条消息写一次，IO 压力与半写风险又太高。轮次粒度的自动落盘是平衡点。

**详细行为**：

- 六个落盘触发点：
  1. 轮次结束（runTurn 的 finally——成功/失败/取消全路径都落）；
  2. 手动 /compact 成功后；
  3. /rename 命名后；
  4. set_cwd 切换成功后（立即落盘 + 重推 session_list——会话文件携带 cwd，WebUI 侧栏按 cwd 分组项目树，不即时保存的话新项目要等下一轮对话才出现）；
  5. 自动标题写入后；
  6. 新建会话（persist 版，让 list_sessions 立即返回新会话）。
- 原子写：tmp + rename。
- 落盘后侧栏会话列表同步刷新（session_list 广播，预览文本随最后一条消息更新）。

**边界与失败模式**：

- 轮末落盘失败 → notice 提醒（不静默）。
- 新建/标题/命名路径失败静默（主链路数据不受影响）。
- updatedAt 在 save 时统一刷新——列表按它降序（最新在前）。

**场景走查**：一轮长对话 finished → 存档更新（history +40 条、usage 累计）→ WebUI 侧栏该会话的预览与时间即时刷新，无需刷新页面。

### R-SES-03 恢复（resume）

**需求动机**：「接着昨天干」是 agent 的核心场景——若 resume 后模型不知道之前干了什么、或又要重新审批一遍工具，恢复就是不完整的。

**详细行为**：

- 入口：TUI `/session`（会话选择器：输入过滤 + ↑↓ + 回车）或 WebUI 侧栏点击 → `resume_session { id }` → 恢复链（见工作原理概述）。
- 恢复后：
  - 聊天区重现全部对话（含思考块与工具块——工具块按 tool_call_id 从 history 结构化重建，与实时 tool_start/tool_end 同构；纯 tool_calls 无正文的 assistant 不产生块）；
  - 会话权限提升按存档还原（restore 后同目录工具不再重复审批）；
  - 累计用量续计；
  - cwd 恢复（项目→会话切换恢复目录——用户从另一个项目的会话切回来，工具执行基准目录跟着回去）。
- 恢复后首轮提交即可继续——模型看到的 context 与中断前一致。

**边界与失败模式**：

- 文件不存在/已损坏 → notice「会话 X 加载失败」不崩溃。
- 运行中（gate busy）恢复被阻塞（工作集不可在中途换）。
- MCP 连接状态不在存档里——恢复后 MCP 按当前配置重新连接，工具可用性由当前配置决定（存档里注册过的工具若 server 已删，模型收到「未知工具」回执自行调整）。

**场景走查**：用户 resume 昨天的会话 → 聊天区完整重现（40 条消息 + 折叠思考块 + 工具块带输出）→ 直接输入「继续跑剩下的测试」→ 模型凭压缩摘要 + 新消息准确接续。

### R-SES-04 会话列表

**需求动机**：多会话并行（不同项目、不同任务）时，用户需要一个可扫读的列表：哪个会话、在哪个项目、最后聊到哪、什么时候。

**详细行为**：

- `list_sessions` → SessionStore.list 扫描存档目录（`*.json`），每条产出：
  - `id`、`updatedAt`（ISO 时间，降序排序最新在前）；
  - `preview`：**history 末条非 tool 消息**的前 40 字符——用 history 而非 context：preview 要反映用户真实对话，context 可能只剩摘要；
  - `cwd`（项目分组依据）、`title?`（缺省时展示层回退 preview）。
- TUI 以会话选择器呈现（可输入过滤）；WebUI 侧栏按项目分组聚合（见 R-SES-06）。

**边界与失败模式**：

- 单个文件损坏不阻断整个列表——跳过解析并返回占位项（「（文件损坏）」）。
- 目录不存在返回空列表；列表读取失败 → notice「会话列表读取失败」。

**场景走查**：用户 /session → 选择器列出 8 个会话（标题/预览/时间）→ 输入 "vitest" 过滤到 2 个 → 回车恢复。

### R-SES-05 删除与当前会话接管

**需求动机**：删除是清理手段，但删除「当前正在用的会话」有一个陷阱：若只删文件不换内存工作集，下一轮落盘会把会话原样写回（僵尸复活）；若换成一个立即落盘的空会话，刚删空的项目又变非空（挡住项目删除）。接管语义必须同时防住两者。

**详细行为**：

- 可删除任意会话（TUI 选择器 d 键 / WebUI 侧栏，均带确认弹层）。
- 流程：gate busy 时阻塞 → `sessions.delete(id)`（文件不存在静默成功——幂等）→ 广播 `session_deleted { id }`。
- 若删除的正是当前会话：
  - notice「当前会话已删除，已切换到新会话」；
  - `newSession(undefined, { persist: false })`——新 id、空工作集、提升清空，但**不落盘**；
  - 接管会话首轮对话后才持久化（防僵尸会话阻塞项目删除——用户删除项目下最后一个会话时，项目才能真正消失）。

**边界与失败模式**：

- 删除失败（磁盘权限）→ notice「删除失败」且不做接管（当前会话仍在）。
- 接管会话若用户直接 /quit 不发一言 → 磁盘上无任何残留文件。
- 删除非当前会话 → 无接管，列表刷新即可。

**场景走查**：WebUI 里用户删除当前会话 → 确认弹层 → 界面立即变成全新空白对话（侧栏该条目消失）→ 用户不提交任何消息 → `~/.dogegg/sessions/` 里没有新文件出现。

### R-SES-06 项目维度（分组与遗忘）

**需求动机**：会话天然按项目聚类（同一个 cwd 下反复工作）——平铺列表在 20+ 会话后不可用。项目维度的聚合与「遗忘」让侧栏成为轻量工作区管理器。

**详细行为**：

- 分组依据是**会话存档的 cwd**，不是当前工作目录——历史会话永远归属它创建时的项目。
- WebUI 侧栏按 cwd 分组聚合会话树（组头 = 项目路径，条目 = 标题/更新时间/预览）；「添加项目」经目录浏览器选中 cwd 后 new_session(cwd)。
- 项目可显式「遗忘」：删除其下全部会话后项目从侧栏消失——WebUI 的删除项目操作是「逐个 delete_session + 本地 knownProjects 清单移除」的组合（前端维护已见项目的本地清单，让 0 会话的占位组也能显示和移除）。
- 项目目录本身不被删除，可随时重新添加。

**边界与失败模式**：

- cwd 为空的旧存档归入「(unknown)」组。
- 删除项目前有确认弹层并明示将删除 N 个会话记录。
- 删光会话后若存在「接管中未落盘」的空会话不会撑回该项目（R-SES-05 的 persist=false 语义）。

**场景走查**：侧栏两个项目组（app、blog）→ 用户删除 blog 项目 → 确认（提示 3 个会话将被删除）→ 三个 delete_session + 本地遗忘 → blog 组消失，磁盘上三个存档文件删除。

### R-SES-07 工作目录切换（/cd）

**需求动机**：用户可能中途切换目标项目（在 app 里聊到一半要去 blog 改文章）——cwd 不只是显示信息，它是工具执行基准、权限归一锚点、项目级扫描根的公共源头，必须原子切换并联动全部下游。

**详细行为**：

- `/cd <path>`（WebUI 经目录浏览器）→ `set_cwd` 消息 → gate busy 阻塞（避免 in-flight 工具写到错误目录）→ 校验（resolve + statSync isDirectory；不存在 → notice「路径不存在」；不是目录 → notice）→ `conversation.setCwd(resolved)`。
- **联动链**：
  1. 项目级 skills 目录重扫（skills.setProjectDir + emitSkillsList——新项目的技能出现、旧项目的消失，系统提示段下一轮请求自动生效）；
  2. MCP diff 重建（项目级 .mcp.json 随 cwd 变化）；
  3. 立即落盘 + 重推 session_list（项目树即时出现新分组）；
  4. status_state 推送（cwd 同步到状态栏与 @path 联想候选）。
- notice「工作目录已切换到 X」。

**边界与失败模式**：

- 切换只影响此后——已在 context 里的历史消息与工具结果不重写（模型若需要新项目信息需重新探索）。
- 权限路径规则按 cwd 归一——`./src/**` 这类锚点模式在新 cwd 下有新含义（刻意的：作用域跟会话 cwd 走）。
- 落盘失败静默（切换本身已成功并提示）。

**场景走查**：`/cd D:\work\blog` → 状态栏 cwd 变化 → /skills 面板出现 blog 的技能 → 项目级 MCP server（blog 专属）自动启动 → @ 联想列 blog 的文件 → 侧栏新增 blog 分组。

### R-SES-08 标题（手动优先）

**需求动机**：标题是列表可扫读性的关键——自动生成解决「懒得命名」，手动命名保留最终控制权，两者的优先级必须明确。

**详细行为**：

- 手动命名（`/rename <名称>` 或侧栏铅笔按钮）优先于自动标题——手动 setTitle 后自动生成跳过（conversation.getTitle() 有值即跳过），生成期间的竞态窗口在写回前再查一次（见 R-DLG-09）。
- /rename 的实现：trim 后为空 → notice 用法提示；成功 → setTitle + 立即落盘 + notice「会话已命名」+ session_list 广播。
- WebUI 重命名弹框预填「原名」（标题优先，无标题回退预览文本）——在原名基础上修改而非从空白开始。
- 标题变更同步侧栏与状态栏（TUI 状态栏 title 字段随 status_state 刷新）。

**边界与失败模式**：

- 命名落盘失败静默（内存标题已生效，下次轮末落盘会补上）。
- 预览与标题的关系：列表展示 `title || preview`——标题永久覆盖预览显示，但预览仍在（重命名弹框的回退来源）。

**场景走查**：首轮对话自动生成「排查 vitest 超时问题」→ 用户 /rename「vitest 超时排查（0.2）」→ 侧栏与状态栏同步更新 → 后续自动标题不再触发。

### R-SES-09 会话隔离（权限提升）

**需求动机**：「始终允许」若跨会话生效，用户在项目 A 给 shell 的提权会泄漏到项目 B 的会话里——临时授权必须以会话为边界；但恢复同一个会话时授权又要回来（否则 resume 失去意义）。

**详细行为**：

- 会话权限提升只在本会话生效：
  - **新建会话** → `permission.reset()` 清空提升集；
  - **切换会话**（resume 另一个）→ reset + 按目标存档 restore；
  - **恢复会话**（resume 自己的存档）→ reset + restore（存档里的提升原样回来，含路径解析结果）。
- 配置三桶是持久的，跨会话不变——隔离的只有「用户在本会话内点过的始终允许」。
- WebUI 端在 session_ready 时清空本地提升镜像并重新播种 permissions_request——面板显示与 agent 内存一致。

**边界与失败模式**：

- 提升随存档持久化（sessionPermissions 字段）——不是「关闭即丢」而是「换会话不跟」。
- 旧格式 allowedTools 不读取（见 R-SES-01）。
- /permissions 面板撤销（permission_revoke）只影响当前会话的内存提升，立即重推清单。

**场景走查**：会话 A 里给 `git *` 提了权 → /new 新会话 → 跑 `git status` 重新弹审批（隔离生效）→ resume 回会话 A → `git status` 又免审批了（存档还原）。

### R-SES-10 用量累计（双口径）

**需求动机**：「这个会话花了多少 token」与「当前 context 占多少」是两个不同的问题——前者是成本累计（含已被压缩掉的历史），后者是窗口占用。混用一个数字会两者都错。

**详细行为**：

- 会话累计（`usage`）：promptTokens/completionTokens/turns 跨轮累加并持久化，resume 续计——数据来自 API 真实返回（`stream_options.include_usage`），每轮的 prompt+completion 加进累计并记为 lastTurn（最近一轮快照，与本地估算并排对照可校准误差）。
- 当前 context 估算：本地粗估（CJK 1 token/字、其余 4 字符 ≈ 1 token）现算 system + context + 工具 schema，驱动压缩阈值与进度条。
- 两口径在信息面板并排展示并注明——**累计包含已被压缩掉的历史用量，大于当前估算属预期**。

**边界与失败模式**：

- API 未返回 usage（部分端点不支持 stream_options）→ 该轮计 0（累计偏小但不中断）。
- 压缩后 context 骤减而累计不变（正确语义）。
- 手动压缩的计数入口 incrementCompaction 与自动压缩（LoopResult.compactions）分开累加，最终都进存档 compactions 字段。

**场景走查**：信息面板 Context 卡显示「估算 18,400 / 128,000（14%）· 会话累计 96,000 tokens / 23 轮 · 最近一轮 7,200」——三个数字各有所指。

## 边界与立法

- history 永不淘汰是全局立法；会话删除是用户显式行为，不受此约束。
- 会话存档不包含 MCP 连接状态——恢复后 MCP 按当前配置重新连接（工具可用性由当前配置决定）。
- 动工作集类命令（new/resume/delete/clear）在 gate busy 时被阻塞并 notice，不排队——轮次中途换工作集会损坏 context。
