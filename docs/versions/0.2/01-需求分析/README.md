## 每篇的结构约定

1. **篇首「工作原理概述」**：用 3~6 段讲清该域的**运作机制**——数据怎么流、状态怎么迁移、判定怎么进行。目标读者是「不了解本项目实现的人」，读完概述应能理解原理而不只是现象。
2. **需求点列表**：每个需求点 = 一个编号小节（`### R-<域>-<NN> 标题`），每点包含四个要素（见下节）。
3. **篇尾「边界与立法」**（部分篇目）：跨需求点的横切约束、非目标、与其它域的接缝。

## 需求点的四要素书写约定

每个需求点按「动机 → 行为 → 边界 → 场景」展开，四要素各有明确职责：

- **需求动机**：这个需求解决什么问题。必须给出「没有它会怎样」的具体坏场景（如：没有 R2 闸门，压缩进行到一半时提交新消息会损坏 context），不写「该功能很重要」式的空话。
- **详细行为**：触发条件、完整数据流/交互流（谁 → 谁 → 谁）、用户可见的表现。涉及配置/命令入口时给出具体配置键或命令（如 `shellProgram`、`/permissions`）。机制描述必须与源码一致——写前读对应源码核实。
- **边界与失败模式**：异常输入、超时、冲突、竞态下的行为；失败时是诚实失败还是静默降级、由谁兜底。
- **场景走查**：用具体例子走一遍（真实文件名/命令/数值），形如「用户提交 X → 系统 Y → 呈现 Z」。

## 阅读提示

- 「安全默认」「固定安全默认」指**不可被配置关闭**的兜底行为（未命中任何规则 → ask）。
- 涉及跨版本语义决策的需求点标注 ADR 编号（如 ADR-0013）；完整决策见 `docs/adr/`。
- 篇与篇之间存在引用（如 01 的压缩依赖 02 的 contextWindow、05 的判定被 03/04 的工具消费）——机制细节写在归属域，其它域只引用编号不重复展开。
- 需求与实现有出入时，以实现为准并视为文档缺陷——请提 issue 或直接修订。
