# R-LLM 模型接入

> 通过 OpenAI 兼容协议接入任意模型服务商（GLM、DeepSeek、OpenAI、本地端点等）。多 provider、多 model 可配，随时切换——模型接入层是可替换的，其余全部功能域不感知具体厂商。

## 域机制概览

**协议分派与客户端形态。** agent 侧唯一入口是 `clientFor(protocol, { baseURL, apiKey })`：一个 protocol 一个实现类（当前只有 `openai` → `OpenAiClient`），agent 调用方不直接引用任何具体 client——将来新增协议（如 Anthropic 原生）时在 clientFor 加分支即可，对话核心一行不改。连接参数（baseURL/apiKey）归 client 实例所有，同一 provider 的多个模型复用同一实例；每轮对话开始时由门面在「提交时刻」解析当前 provider 并构造 client（配置切换天然生效于下一轮）。

**请求构造。** 每次请求的 HTTP 形态完全确定：`POST {baseURL 去尾斜杠}/chat/completions`，header 带 `content-type: application/json` 与 `Authorization: Bearer <apiKey>`；body 恒为流式：`stream: true` + `stream_options: { include_usage: true }`——usage 随流末尾的独立 chunk 返回（choices 为空数组）；messages = `{ role: 'system', content: systemPrompt }` + 对话消息（ChatRequest.messages 只含 user/assistant/tool，system 由 client 自行拼接）；`tools` 为注册表 `schemas()` 现算的全量 function schema；`max_tokens: maxOutput`。

**流式解析与事件归一。** SSE 流被逐行喂给一个有状态的解析器（行驱动，可直接喂 mock 行做无网络单测）：`data:` 行 JSON 解析，非 JSON 行（心跳/注释）静默跳过；`delta.content` → `text_delta`；`delta.reasoning_content`（OpenAI 标准）优先、回退 `delta.reasoning`（部分兼容端点）→ `thought_delta`，同时累积完整 reasoning 供 done 事件携带（持久化用）；`delta.tool_calls` 按 index 聚合——首次见到某 index 发 `tool_call_start`（必须在 name/id 字段合并**之后**发，OpenAI 协议里它们往往随首个分片才到，先广播会让 UI 拿到空名），之后每个 arguments 分片发 `tool_call_delta`；`[DONE]` 时逐 tool call 发 `tool_call_end`（按 index 排序组装完整 id/name/arguments），最后发 `done`（组装成一条 assistant 消息：content 可能为 null，带 tool_calls 时按 index 排序）。

**错误分类与重试。** 错误分四类：`HttpError`（保留状态码；429/5xx retryable，其余 4xx fail-fast）、`NetworkError`（retryable）、`StreamTimeoutError`（连接/空闲两级 60s，retryable）、AbortError（用户取消，绝不重试；未知错误默认不重试）。`withRetry(maxRetries + 1)` 包裹整次流式请求：指数退避 500ms×2^attempt，429 的 `Retry-After` header 优先（秒数与 HTTP-date 两种格式），退避 sleep 可被 abort 中断。

**归一化数据形态。** 接入层的三个契约类型是厂商差异的隔离层——agent 的 loop/UI 只消费这些归一化形状，字段级如下：

| ChatRequest 字段（调用方 → client） | 说明 |
|---|---|
| `model` | 请求的模型名（来自 model 条目 name） |
| `systemPrompt` | system 消息由 client 自行拼接为消息首条 |
| `messages` | 对话历史，只含 user/assistant/tool |
| `tools` | function schema 数组（见 R-LLM-06） |
| `maxOutput` | → 请求的 `max_tokens` |
| `maxRetries` | 请求级保留——压缩摘要等离线调用用更激进的重试策略 |

| ChatResult 字段（client → 调用方） | 说明 |
|---|---|
| `message` | 组装完成的 assistant 消息（content 可能为 null——纯 tool_calls 响应） |
| `reasoning?` | 完整思考文本——持久化、resume 重建用 |
| `usage?` | promptTokens / completionTokens / totalTokens（stream_options.include_usage） |

| LlmStreamEvent（七种流事件） | 携带 |
|---|---|
| `text_delta` | 正文增量 text |
| `thought_delta` | 思考增量 text |
| `tool_call_start` | index / id / name（name/id 字段合并后发出，下游 tool_pending 才有真实名） |
| `tool_call_delta` | index / argsJsonDelta（参数分片） |
| `tool_call_end` | index / id / name / arguments（完整参数，[DONE] 时按 index 排序补发） |
| `done` | message + reasoning? + usage? |
| `error` | Error（provider 内部错误形态） |

### R-LLM-01 多 provider 配置

- **需求背景与动机**：不同任务适合不同模型——代码用 GLM、长文用 DeepSeek、离线实验用本地端点；且单一供应商可能限流或故障。用户需要并存多个服务商并随时切换，而不是改配置重启程序。没有并存与热切换，供应商一次 429 就意味着整个工作流停摆等冷却，或手动改配置重启丢失会话上下文。
- **功能规格**：
  1. **数据形态**：config.json 的 `providers` 数组配置任意多个服务商，每个条目字段级说明：
     | 字段 | 说明 |
     |---|---|
     | `name` | 显示与引用名，defaultProvider 按它精确匹配 |
     | `protocol` | 协议枚举（见 R-LLM-02） |
     | `baseURL` | API 端点（如 GLM 的 `https://open.bigmodel.cn/api/paas/v4`），请求时去尾斜杠后拼 `/chat/completions` |
     | `apiKey` | Bearer 方式随请求发送 |
     | `models[]` | 该服务商下可用模型列表（见 R-LLM-03） |
  2. **配置与命令入口**：多 provider 并存，`/model`（provider → model 两级选择器）或 /config 树（providers 子树，支持 add/remove/set）随时切换——切换即写 config_set → config_updated 广播 → 状态栏即时刷新；providers 为空时子树编辑同样可用（先建第一个 provider）。
  3. **生效时机**：下一轮对话用新模型，正在进行的轮次不受影响——`resolveTurnParams` 在命令时刻把 provider/model 解析成值传入 TurnRunner（派生值不进 ctx，配置编辑天然只影响下一轮）。
  4. **连接参数所有权**：baseURL/apiKey 归 LlmClient 实例所有（构造时注入），同一 provider 的多个模型复用同一实例——client 构造只发生在提交时刻，运行期不重建。
  5. **隔离性**：不同 provider 的模型混用互不影响（每个 provider 独立的 baseURL/apiKey/models）。
- **边界与失败模式**：
  - 非空 name 判重——重名 provider/model 在编辑保存时被 validateConfig 拒绝回滚（「名称重复，已回滚：provider『X』」）。
  - 空 name 的新节点允许多个共存（编辑期放宽，见 R-LLM-08）。
  - defaultProvider 与 providers 数组脱节（引用了不存在的 name）时 resolveCurrent 回落第一个 provider，不报错。
- **验收标准**：
  1. 当配置两个 provider 并保存，则 /model 选择器出现全部条目，任一可选。
  2. 当选中另一个 provider 的模型，则 config 持久化且状态栏立即显示新 provider/model。
  3. 当轮次进行中切换模型，则本轮继续用旧模型，下一轮请求用新模型。
  4. 当保存时两个 provider 同名，则编辑被拒绝回滚并提示「名称重复，已回滚」。
  5. 当 defaultProvider 指向已删除的名字，则解析回落第一个 provider，不报错不阻塞。
  6. 当同一 provider 下切换两个模型，则 baseURL/apiKey 相同（client 连接参数复用），仅请求 body 的 model 参数变化。
  7. 当删除 defaultProvider 指向的 provider，则 onConfigChanged 重推 status_state，状态栏显示回落后的 provider。
- **场景走查**：用户在 /config → providers → 添加 provider，填 name=glm、baseURL、apiKey，models 加两个模型 → 保存 → /model 选择器立即出现新条目 → 选中后状态栏显示 glm/模型名。
- **场景走查（备用切换）**：主力 provider 持续 429 限流 → 用户 /model 切到备用 provider → 下一轮对话直接走备用端点，会话上下文原样延续。

### R-LLM-02 协议（openai 兼容）

- **需求背景与动机**：OpenAI 的 `/chat/completions` + SSE 已是事实标准——GLM、DeepSeek、本地 vLLM/Ollama 等几乎全部兼容。先支持这一种协议即可覆盖绝大多数用户；但不把协议硬编码进调用方——协议抽象（clientFor 分派 + 归一化类型）保证未来扩展（Anthropic 原生等）不需重构：否则每加一家厂商，对话循环、UI、压缩全要跟着改。
- **功能规格**：
  1. **协议内容**：当前仅支持 `protocol: 'openai'`——`/chat/completions` 端点、`tools` 参数以 `{ type: 'function', function: { name, description, parameters } }` 数组声明工具、SSE 流式响应（解析规则见域机制概览）。
  2. **枚举预留位**：`protocol` 字段是枚举预留位（schema `z.enum(['openai'])` 是当前唯一合法值）——新增协议时在此扩展枚举并注册对应 LlmClient 实现（clientFor 加分支）。
  3. **归一化接口**：ChatRequest/ChatResult/LlmStreamEvent 的归一化接口不变——新增协议只影响接入层，agent 的 loop/UI 一行不改。
  4. **解析器可测性**：SSE 解析是行驱动纯函数（`feed(line) → events[]`），无网络即可喂 mock 行做单测——厂商私有行为（字段名差异、分片方式）可穷举验证。
  5. **usage 字段归一**：流末尾独立 usage chunk 的 snake_case 字段在 parser 转换为 camelCase（`prompt_tokens` → promptTokens、`completion_tokens` → completionTokens、`total_tokens` → totalTokens），缺失按 0 记。
  6. **错误归因三路**：fetch 失败按「用户 abort → AbortError；连接超时 → StreamTimeoutError(connect)；其余 → NetworkError」归因——取消与超时严格区分，互不混淆；body 阶段的用户 abort 仍即时中断（abort 监听保留至流结束）。
  7. **残余行处理**：连接关闭时最后一批字节可能没有尾随换行——缓冲的残余行 trim 后再喂 parser；`[DONE]` 缺失（连接提前关闭）则抛「流未产生最终消息」。
- **边界与失败模式**：
  - 不同厂商对参数的私有扩展由接入层适配不外溢——如思考通道字段名（`reasoning_content` vs `reasoning`）在 parser 内统一归一为 thought_delta。
  - 某些端点不支持 `stream_options` 时 usage 缺失，轮次用量记 0（功能不中断）。
  - `Retry-After` 值非法（既非秒数也非 HTTP-date）→ 解析为 undefined，退避走指数策略。
  - 需求分析只约定「OpenAI 兼容」这一协议契约。
- **验收标准**：
  1. 当 provider 配置 `protocol: 'openai'`，则请求发往 `{baseURL}/chat/completions` 且 body 恒带 `stream: true`。
  2. 当端点返回思考字段 `reasoning_content` 或 `reasoning`，则两者都归一为 thought_delta。
  3. 当端点不支持 `stream_options`，则 usage 缺失时轮次用量按 0 记，对话与工具循环不受影响。
  4. 当流中夹带非 JSON 行（心跳/注释），则被静默跳过，不产生任何事件。
  5. 当连接超过 60s 无响应头，则抛 StreamTimeoutError(connect) 且按可重试错误退避重发。
  6. 当服务器在 `[DONE]` 前关闭连接，则抛「流未产生最终消息」（未知错误不重试，直接上抛）。
  7. 当尝试配置 `protocol: 'anthropic'`，则 schema 校验拒绝（当前唯一合法值为 'openai'）。
- **场景走查**：用户把 baseURL 指向本地 Ollama 的 `http://localhost:11434/v1` → 同一套流式解析/工具调用照常工作（Ollama 兼容 OpenAI 协议）。
- **场景走查（自建端点）**：用户把 baseURL 指向自建 vLLM 端点 → 工具声明与流式解析直接可用（vLLM 兼容 OpenAI 工具调用协议），无需改任何代码。

### R-LLM-03 模型条目

- **需求背景与动机**：压缩阈值、输出截断、思考流渲染都依赖模型元数据——没有 `contextWindow` 就无法判断何时该压缩（要么提前反复压缩，要么中途 400）；没有 `reasoning` 标记就无法区分思考流与正文流（思考内容会当正文打印，或状态机永远停在 responding 等不到 thought_done）。
- **功能规格**：
  1. **数据形态**：每个 model 声明四字段（字段级说明）：
     | 字段 | 说明 | 默认值 |
     |---|---|---|
     | `name` | 请求 body 的 model 参数（无默认值；编辑期可为空，见 R-LLM-08） | — |
     | `contextWindow` | 上下文窗口（token 数），驱动压缩阈值（80% × window）、状态栏进度条与 /context percent | 128000 |
     | `maxOutput` | 单次输出上限 → 请求的 `max_tokens` | 16384 |
     | `reasoning` | 是否思考模型 | false |
  2. **reasoning: true 的行为差异**：
     - 状态机 submit 迁 thinking（先思考后正文），false 迁 responding；
     - 思考内容走独立通道渲染（thought_delta / 思考块）；
     - thinking 数组记录实际 reasoning；false 时即使模型返回 reasoning 也存空字符串（不记录不显示）。
  3. **窗口的其它消费方**：/context 的 percent = `round(tokens / contextWindow * 100)`；windowTokens 随 TurnParams 进入压缩判定与 status_state。
  4. **maxOutput 的边界**：只约束对话请求的 `max_tokens`；离线单次调用有独立预算（压缩摘要 2000、标题 512，见 R-DLG-04/R-DLG-09）。
  5. **配置与命令入口**：模型条目在 /config providers 子树与 WebUI Models 区逐字段编辑；数值约束为正整数（zod `int().positive()`），默认值由 schema 并入。
- **边界与失败模式**：
  - contextWindow 配得比实际小 → 压缩提前触发（保守但安全）；配大了 → 可能请求超窗 400，error 块提示后由用户调低。
  - reasoning 误标 false → 思考内容混进正文流（模型行为差异，需用户修正配置）。
  - reasoning 误标 true → 状态先迁 thinking，若模型从不吐 reasoning（直接 tool_calls/正文），则 thought_done 在收尾补迁移，无死锁。
  - model 的 name 编辑期可空（放宽），但空名会致 isConfigured false——发请求前必被拦截，不会发出空 model 参数。
  - 默认值由 zod schema 并入（新建条目不填也能通过校验）。
- **验收标准**：
  1. 当新建 model 只填 name，则 contextWindow=128000、maxOutput=16384、reasoning=false 由 schema 并入。
  2. 当 `reasoning: true` 的模型开始对话，则状态先迁 thinking、thought_delta 走独立通道渲染。
  3. 当 `reasoning: false` 的模型返回 reasoning 字段，则内容被忽略，thinking 数组对应条目为空字符串。
  4. 当 contextWindow 配为 200000，则自动压缩在估算超过 160000 token 时触发，/context percent 按同一窗口计算。
  5. 当 maxOutput 配为 32768，则请求 body 的 `max_tokens` 为 32768（离线调用不受影响）。
  6. 当 contextWindow 或 maxOutput 配为 0 或负数，则 zod 校验拒绝（正整数约束）。
  7. 当 model 条目被删除后查询 /context，则 percent 按回落后的模型窗口计算。
- **场景走查**：接入 GLM-4.6（reasoning）→ models 加 `{ name: 'glm-4.6', contextWindow: 200000, maxOutput: 32768, reasoning: true }` → 对话时状态栏先 Thinking 后 Responding，思考块折叠可展开。

### R-LLM-04 默认模型

- **需求背景与动机**：用户不该每次启动都选模型——`defaultProvider` + `defaultModel` 定义「开箱即用」的对话模型；同时空配置（首次安装）不能让程序崩溃，要能启动并引导配置。缺省规则必须在两个层面成立：落盘配置的补全（加载期）与运行时解析的回落（resolveCurrent），两层语义不一致就会「判定说能对话、解析时却崩」。
- **功能规格**：
  1. **数据形态**：config 顶层 `defaultProvider`/`defaultModel` 指定对话使用的模型。
  2. **加载期补全**（ConfigStore.load）：providers 非空且未显式设置时——defaultProvider 补第一个 provider 的 name；defaultModel 补该 provider 第一个 model 的 name；providers 为空则保持无默认值（补全发生在内存 config 上）。
  3. **运行期回落**（resolveCurrent）：defaultProvider 未命中（未设/名字不存在）→ 回落第一个 provider；defaultModel 未命中 → 回落该 provider 的第一个 model。resolveCurrent 同时被状态推送与参数解析共用（`current()` 唯一入口，不重复解析）。
  4. **轮次参数产物**：提交时刻解析出 TurnParams 六字段（字段级来源）：
     | 字段 | 来源 |
     |---|---|
     | `client` | clientFor(provider.protocol, { baseURL, apiKey })——提交时刻构造 |
     | `model` | model.name |
     | `maxOutput` | model.maxOutput |
     | `maxRetries` | config.maxRetries（config 顶层键，非 model 条目——重试策略全局统一） |
     | `reasoning` | model.reasoning |
     | `windowTokens` | model.contextWindow |
  5. **配置与命令入口**：`/model` 选择器的两连击（选 provider → 选 model）就是两次 config_set 写这两个键。
  6. **空配置行为**：providers 为空时无默认值——程序照常启动，isConfigured 判定 false，状态栏显示「未配置 provider（请先 /config）」，提交对话回 notice 引导。
  7. **类型契约**：resolveCurrent 的调用方（agent 门面）约定先经 isConfigured 判定——空 providers 时直接 `!` 断言会抛（类型层面的契约）。
  8. **配置文件定位**：项目内 `.dogegg.json` 优先，否则 `~/.dogegg/config.json`，都没有则按空配置启动（providers 为空 → 引导用户 /config）。
- **边界与失败模式**：
  - defaultModel 指向的 model 在 provider 被删除后 → 回落第一个 model，不报错。
  - 加载期补全与运行期回落都是数组序——isConfigured 判定通过的配置必然能被 resolveCurrent 解析出非空 provider/model（两层规则一致性的根基）。
  - /model 两连击期间（provider 已选、model 未选）配置处于中间态——defaultModel 未命中回落第一个 model，不会出现不可用状态。
  - TUI 启动瞬间 config 未回来时顶栏显示「加载配置中…」，品牌头延迟到 config + cwd 就绪才打印（Static 只渲染一次，定格错误信息无法纠正）。
- **验收标准**：
  1. 当配置 defaultProvider=glm 后启动，则无需任何选择即可直接对话 glm 下的默认模型。
  2. 当删除 defaultModel 指向的 model，则解析回落该 provider 第一个 model，对话不中断。
  3. 当 providers 为空时启动，则程序正常启动、isConfigured 为 false、提交对话回引导 notice。
  4. 当 defaultProvider 未设但 providers 非空，则加载期补全为第一个 provider 的 name。
  5. 当 /model 两连击完成，则 defaultProvider 与 defaultModel 两键已持久化。
  6. 当 TUI 启动且 config 未就绪，则顶栏显示「加载配置中…」，就绪后才打印品牌头。
  7. 当 config 文件缺失，则按空配置启动（providers=[]）而非崩溃。
- **场景走查**：配置两个 provider（glm、deepseek）与各自的 models → defaultProvider=glm → 启动直接可用；用户想临时用 deepseek → /model 两击切换，配置持久化。

### R-LLM-05 流式双通道

- **需求背景与动机**：推理模型的「思考过程」与「面向用户的回答」价值不同——前者可折叠略读，后者是正式交付物。混在一条流里既难读又无法折叠；且思考内容需要随会话持久化，resume 后才能重建展示——否则重启一次，推理模型的思考痕迹全部丢失。
- **功能规格**：
  1. **通道归一**：响应走 SSE，正文增量（`delta.content` → text_delta）与思考增量（`reasoning_content`/`reasoning` 字段归一为 thought_delta）分通道产出。LlmStreamEvent 归一化枚举共七种：text_delta / thought_delta / tool_call_start / tool_call_delta / tool_call_end / done / error。
  2. **广播门槛**：agent 把 thought_delta 仅在 `turn.reasoning` 为 true 时向 UI 广播（普通模型的杂散 reasoning 不显示）。
  3. **输出与用户可见表现**：UI 双通道渲染——TUI 思考块黄色可折叠（partial 未落盘阶段实时增长），WebUI 折叠面板。
  4. **持久化**：parser 累积完整 reasoning，done 事件携带（ChatResult.reasoning）供持久化——resume 后按 assistant 消息一一对应重建思考块。
  5. **分界时机**：思考块与正文块的分界由第一条 text_delta 触发 flush（reducer 侧）；agent 侧 thought_done 迁移与之一一对应（第一个正文 delta 到达，或整条 assistant 收齐但无正文时补迁移）。
  6. **重建语义**：`reasoning: false` 的空字符串条目在 resume 重建（rebuildBlocksFromHistory）时被跳过——不显示空思考气泡。
  7. **失败衔接**：流式中断/失败按 R-DLG-06 处理。
  8. **流式时序**（推理模型 + 一次工具调用的典型事件序）：`submit → thinking` → thought_delta…（思考块增长）→ 首个 text_delta（thought_done → responding，思考 flush）→ tool_call_start（广播 tool_pending）→ tool_call_delta…（参数累积）→ tool_call_end（[DONE]）→ done（message + reasoning + usage）→ 工具执行 → 下一迭代。
- **边界与失败模式**：
  - 部分兼容端点思考字段名不同（reasoning_content vs reasoning）——parser 双字段回退。
  - 非 reasoning 模型偶发返回 reasoning 字段 → 内容被忽略不渲染（广播门槛在 agent 层判 `turn.reasoning`，parser 层不区分——分层职责）。
  - thinking 数组与 assistant 消息一一对应（每轮 LLM 调用 push 一个条目）——resume 重建按此对齐，空字符串条目跳过。
  - 模型全程无正文只有工具调用时，收尾处补 thought_done 迁移保证状态机一致。
- **验收标准**：
  1. 当推理模型输出 reasoning 分片，则 parser 依次发出 thought_delta 且累积完整 reasoning 文本。
  2. 当 `turn.reasoning` 为 false，则 thought_delta 不被广播到 UI。
  3. 当 done 事件到达，则携带的 reasoning 与本次 thought_delta 顺序拼接结果一致（供持久化）。
  4. 当 resume 会话，则思考块按 assistant 消息顺序一一重建，空 reasoning 条目无气泡。
  5. 当第一条 text_delta 到达时仍有思考 partial，则思考块先 flush 落盘再开正文块。
  6. 当模型全程无正文（纯 tool_calls），则思考块仍完整落盘（flush 于收尾）。
- **场景走查**：glm-4.6 对「分析这段报错」先吐 800 字思考（折叠块增长）→ 转正文流式 → 完成后思考块折叠成 3 行摘要，点击展开看全文。
- **场景走查（resume 重建）**：推理模型完成多轮对话后退出 → 用户 resume 该会话 → 每条 assistant 回复的思考块按原顺序重建、可展开，正文无错位。

### R-LLM-06 工具声明（tools 参数）

- **需求背景与动机**：模型能调用哪些工具由每次请求的 `tools` 参数决定。MCP 工具在运行期动态注册/摘除——若 schema 在启动时缓存成快照，新接入的工具模型永远看不到，摘除的工具模型还会「幻调」（调用已不存在的工具必然失败），对话质量随时间劣化。
- **功能规格**：
  1. **处理规则**：每次请求携带注册表**当前全部工具**的 function schema：`registry.schemas()` 每次调用现算（遍历当前 Map），不缓存快照。
  2. **动态性**：MCP 工具注册/摘除后，下一次请求即时反映——模型永远看到当前可用的工具集。
  3. **数据形态**：schema 形状 `{ type: 'function', function: { name, description, parameters } }`，parameters 为各工具声明的 JSON Schema（MCP 工具为服务原生透传）。
  4. **产出顺序**：schemas() 按 Map 迭代序产出——内建 7 工具先注册在前，MCP 工具运行期追加在后，顺序稳定可预期。
  5. **分片容错**：tool_call 分片的 index 缺失时按 0 处理（部分端点不回 index）；id/name 字段随任一分片到达即合并，首片合并后才广播 tool_call_start。
  6. **口径一致**：压缩判断同样用 `schemas()` 现算工具段 token——loop 同一次迭代内先估算后请求各调一次，工具集合必然一致；工具集变化连压缩估算口径都保持一致。
  7. **UI 同步**：UI 侧 `tools_list` 广播携带身份（builtin/mcp{server,name}），/tools 面板与 WebUI Available Tools 卡按来源分组展示；tool_pending 的名称可见性也依赖 tool_call_start 在字段合并后发出（见域机制概览）——大参数流式生成期间 UI 显示真实工具名。
- **边界与失败模式**：
  - MCP server 半挂载（部分工具注册失败）→ syncRegistry 先摘后挂，失败服务整体摘除——schema 里不会出现残缺工具。
  - 工具名不合规范 → 注册关口已哈希（见 R-TLB-08），schemas() 发出的名字必然合规。
- **验收标准**：
  1. 当 MCP 工具注册完成，则同一会话下一轮请求的 tools 数组已包含其 schema。
  2. 当 MCP 工具被摘除，则下一轮请求的 tools 数组不再包含，模型无法再幻调。
  3. 当 schemas() 被连续调用而注册表无变化，则两次产出等价；注册表变化后立即反映新集合。
  4. 当压缩估算执行，则工具段 token 与请求使用的 schemas() 同源同口径。
  5. 当 MCP server 工具清单变化触发 rebuild，则 schema 反映最终清单（先摘后挂，失败服务整体摘除）。
  6. 当 tools_list 广播，则每条载荷携带 identity，UI 按内建/MCP 来源分组。
- **场景走查**：用户在 /mcp 启用 playwright server → mcp_list/tools_list 广播 → 同一会话下一轮请求即带 `mcp__playwright__browser_navigate` 等工具 → 模型立即调用。

### R-LLM-07 完整性判定（isConfigured）

- **需求背景与动机**：「配置文件存在」不等于「能对话」——可能只有半个 provider（缺 apiKey）、或 defaultModel 拼错。没有一个统一判定，「能不能提交对话」就会在各处各自猜测，TUI 提示与 agent 拦截互相矛盾。需要一个纯函数判定把「能不能提交对话」与「配置长什么样」解耦。
- **功能规格**：
  1. **判定链**：`isConfigured(config)` 的判定链（住 bridge 契约包，agent 与 UI 共用同一实现）：
     1. 找 defaultProvider 命中的 provider，未命中取第一个；
     2. 无 provider → false；
     3. 该 provider 的 name/baseURL/apiKey 任一 trim 后为空、或 models 为空 → false；
     4. 取 defaultModel 命中的 model（未命中取第一个），model 不存在或 name 为空 → false；
     5. 全部通过 → true。
  2. **回落一致性**：判定与 resolveCurrent 用同一回落顺序（defaultProvider/defaultModel 未命中取数组第一个）——isConfigured true 蕴含运行时必然解析出可用 provider/model。
  3. **拦截范围**：所有「动对话」的消息入口（submit/compact_request/invoke_skill/context_request/status_request）先查此判定——false 时发 notice 并拒绝执行，文案分两档：submit/compact_request/invoke_skill 用长文案「尚未配置 provider，请先 /config 添加并保存后重试」，context_request/status_request 用短文案「尚未配置 provider，请先 /config」。
  4. **可用性**：程序照常启动（TUI 状态栏显示引导文案，WebUI 设置弹框可打开）。
  5. **联动刷新**：配置变更后 onConfigChanged 钩子重新判定，true 时立即推送 status_state 刷新界面。
- **边界与失败模式**：
  - 判定是纯派生——TUI 顶栏的「未配置 provider」提示与 agent 的提交拦截永不漂移。
  - providers 数组第一个条目是编辑中的空节点时，isConfigured 会因它 trim 为空而 false——即使后面有完整 provider（回落顺序是数组序，用户应删除空节点或把它填完）。
- **验收标准**：
  1. 当 providers 为空时提交对话，则收到 notice「尚未配置 provider，请先 /config…」且轮次不启动。
  2. 当 provider 缺 apiKey，则 isConfigured 为 false，所有动对话入口被拦截。
  3. 当 defaultModel 拼错但 provider.models 有条目，则回落第一个 model 判定为 true。
  4. 当 submit 与 status_request 在同一配置下执行，则二者判定结论一致（同一纯函数，无漂移）。
  5. 当配置从不完整改为完整保存，则 onConfigChanged 重新判定为 true 并立即推送 status_state。
  6. 当未配置时查询 context_state，则回引导 notice 而非抛错。
  7. 当 defaultProvider 未设且数组第一个节点为编辑中空节点，则判定 false（数组序回落命中空节点）。
- **场景走查**：首次安装 → 空 providers → 提交「你好」→ notice「尚未配置 provider…」→ /config 建好并保存 → 同一会话直接提交成功。

### R-LLM-08 编辑期放宽

- **需求背景与动机**：如果 schema 强制 provider 全字段非空，用户就无法「先建节点、后补字段」——每次回车都校验失败，交互极差（表单填到一半永远保存不了）。编辑期放宽 + 完整性判定（R-LLM-07）把关是刻意解耦：schema 管「结构合法」，isConfigured 管「能对话」。
- **功能规格**：
  1. **放宽范围**：配置编辑器的 provider/model 字段在 zod schema 层刻意放宽：name/baseURL/apiKey 允许暂时为空字符串、models 允许空数组——支持 /config 树与 WebUI 表单里「自由创建节点、逐字段填写」的流程。
  2. **保存管线**：保存仍经 configSchema.parse（并入默认值：contextWindow 128000、maxOutput 16384、reasoning false、models []）+ 重名检查。
  3. **重名口径**：仅非空名判重（findDuplicateName）——空名新节点允许多个共存，与放宽语义配套；判重范围 provider 名跨数组唯一、model 名在所属 provider 内唯一（跨 provider 允许同名——不同厂商常有相同模型名）。
  4. **放宽的边界**：放宽的是「值约束」不是「结构约束」——providers 必须是数组、protocol 必须是枚举值、contextWindow/maxOutput 必须正整数，结构错误仍拒绝。
  5. **失败语义**：validateConfig 返回 `{ ok: false, config: lastGood, error }`——校验失败回滚到 lastGood 快照并 emit error，错误消息为「配置校验失败，已回滚：<issue>」或「名称重复，已回滚：provider「X」/model「X」」——不写坏配置。
  6. **职责边界**：能对话与否由 isConfigured 在运行时把关——两者互不替代。
- **边界与失败模式**：
  - 放宽只作用于 providers 子树——permission 锚点校验、maxIterations 的 -1/正整数约束等其它 schema 校验照常生效（校验失败编辑即报错回滚）。
  - lastGood 快照保证「回滚」总是回到最近一次合法配置——连续失败编辑不叠加损坏。
  - 空节点长期存在会让 isConfigured false（见 R-LLM-07 边界）。
- **验收标准**：
  1. 当创建 name 为空的 provider 节点并保存，则校验通过（放宽），节点落库。
  2. 当逐步补齐 name/baseURL/apiKey/models 后保存，则最终配置合法且 isConfigured 依判定链给出结论。
  3. 当保存触发重名（两个非空同名 provider），则回滚到 lastGood 并 emit「名称重复，已回滚」。
  4. 当同一 provider 内两个 model 同名，则同样判重拒绝回滚（model 名 provider 内唯一）。
  5. 当编辑把 maxIterations 改为 0，则不受放宽影响，校验失败立即报错回滚。
  6. 当空节点存在期间提交对话，则由 isConfigured 拒绝，不因「编辑期放宽」而放行。
- **场景走查**：用户回车「添加 provider」产生空节点 → 逐字段填 name → 先保存（合法）→ 再补 baseURL/apiKey/models → 最终保存成功；期间任何时刻提交对话都由 isConfigured 决定是否放行。
