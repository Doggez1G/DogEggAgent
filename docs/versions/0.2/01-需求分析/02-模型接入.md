# R-LLM 模型接入

通过 OpenAI 兼容协议接入任意模型服务商（GLM、DeepSeek、OpenAI、本地端点等）。多 provider、多 model 可配，随时切换——模型接入层是可替换的，其余全部功能域不感知具体厂商。

## 工作原理概述

**协议分派与客户端形态。** agent 侧唯一入口是 `clientFor(protocol, { baseURL, apiKey })`：一个 protocol 一个实现类（当前只有 `openai` → `OpenAiClient`），agent 调用方不直接引用任何具体 client——将来新增协议（如 Anthropic 原生）时在 clientFor 加分支即可，对话核心一行不改。连接参数（baseURL/apiKey）归 client 实例所有，同一 provider 的多个模型复用同一实例；每轮对话开始时由门面在「提交时刻」解析当前 provider 并构造 client（配置切换天然生效于下一轮）。

**请求构造。** 每次请求的 HTTP 形态完全确定：

- `POST {baseURL 去尾斜杠}/chat/completions`，header 带 `Authorization: Bearer <apiKey>`；
- body 恒为流式：`stream: true` + `stream_options: { include_usage: true }`——usage 随流末尾的独立 chunk 返回（choices 为空数组）；
- messages = `{ role: 'system', content: systemPrompt }` + 对话消息（ChatRequest.messages 只含 user/assistant/tool，system 由 client 自行拼接）；
- `tools` 为注册表 `schemas()` 现算的全量 function schema；`max_tokens: maxOutput`。

**流式解析与事件归一。** SSE 流被逐行喂给一个有状态的解析器（行驱动，可直接喂 mock 行做无网络单测）：

- `data:` 行 JSON 解析，非 JSON 行（心跳/注释）静默跳过；
- `delta.content` → `text_delta`；
- `delta.reasoning_content`（OpenAI 标准）优先、回退 `delta.reasoning`（部分兼容端点）→ `thought_delta`，同时累积完整 reasoning 供 done 事件携带（持久化用）；
- `delta.tool_calls` 按 index 聚合——首次见到某 index 发 `tool_call_start`（必须在 name/id 字段合并**之后**发，OpenAI 协议里它们往往随首个分片才到，先广播会让 UI 拿到空名），之后每个 arguments 分片发 `tool_call_delta`；
- `[DONE]` 时逐 tool call 发 `tool_call_end`（按 index 排序组装完整 id/name/arguments），最后发 `done`（组装成一条 assistant 消息：content 可能为 null，带 tool_calls 时按 index 排序）。

**错误分类与重试。** 错误分四类：`HttpError`（保留状态码；429/5xx retryable，其余 4xx fail-fast）、`NetworkError`（retryable）、`StreamTimeoutError`（连接/空闲两级 60s，retryable）、AbortError（用户取消，绝不重试）。`withRetry(maxRetries + 1)` 包裹整次流式请求：指数退避 500ms×2^attempt，429 的 `Retry-After` header 优先，退避 sleep 可被 abort 中断。

## 需求点

### R-LLM-01 多 provider 配置

**需求动机**：不同任务适合不同模型（代码用 GLM、长文用 DeepSeek、离线实验用本地端点），且单一供应商可能限流或故障——用户需要并存多个服务商并随时切换，而不是改配置重启程序。

**详细行为**：

- config.json 的 `providers` 数组配置任意多个服务商，每个条目含：
  - `name`：显示与引用名（defaultProvider 按它匹配）；
  - `protocol`：协议枚举（见 R-LLM-02）；
  - `baseURL`：API 端点（如 GLM 的 `https://open.bigmodel.cn/api/paas/v4`，请求时去尾斜杠后拼 `/chat/completions`）；
  - `apiKey`：Bearer 方式随请求发送；
  - `models[]`：该服务商下可用模型列表（见 R-LLM-03）。
- 多 provider 并存，`/model`（provider → model 两级选择器）或 /config 树（providers 子树）随时切换——切换即写 config_set → config_updated 广播 → 状态栏即时刷新。
- 下一轮对话用新模型，正在进行的轮次不受影响（client 在提交时刻解析）。
- 不同 provider 的模型混用互不影响。

**边界与失败模式**：

- 非空 name 判重——重名 provider/model 在编辑保存时被 validateConfig 拒绝回滚（「名称重复，已回滚：provider『X』」）。
- 空 name 的新节点允许多个共存（编辑期放宽，见 R-LLM-08）。
- defaultProvider 与 providers 数组脱节（引用了不存在的 name）时 resolveCurrent 回落第一个 provider，不报错。

**场景走查**：用户在 /config → providers → 添加 provider，填 name=glm、baseURL、apiKey，models 加两个模型 → 保存 → /model 选择器立即出现新条目 → 选中后状态栏显示 glm/模型名。

### R-LLM-02 协议（openai 兼容）

**需求动机**：OpenAI 的 `/chat/completions` + SSE 已是事实标准——GLM、DeepSeek、本地 vLLM/Ollama 等几乎全部兼容。先支持这一种协议即可覆盖绝大多数用户；协议抽象（clientFor 分派）保证未来扩展不需重构。

**详细行为**：

- 当前仅支持 `protocol: 'openai'`：`/chat/completions` 端点、`tools` 参数以 `{ type: 'function', function: { name, description, parameters } }` 数组声明工具、SSE 流式响应（解析规则见工作原理概述）。
- `protocol` 字段是枚举预留位（schema `z.enum(['openai'])` 是当前唯一合法值）——新增协议时在此扩展枚举并注册对应 LlmClient 实现。
- ChatRequest/ChatResult/LlmStreamEvent 的归一化接口不变——新增协议只影响接入层，agent 的 loop/UI 一行不改。

**边界与失败模式**：

- 不同厂商对参数的私有扩展由接入层适配不外溢——如思考通道字段名（`reasoning_content` vs `reasoning`）在 parser 内统一归一为 thought_delta。
- 某些端点不支持 `stream_options` 时 usage 缺失，轮次用量记 0（功能不中断）。
- 需求分析只约定「OpenAI 兼容」这一协议契约。

**场景走查**：用户把 baseURL 指向本地 Ollama 的 `http://localhost:11434/v1` → 同一套流式解析/工具调用照常工作（Ollama 兼容 OpenAI 协议）。

### R-LLM-03 模型条目

**需求动机**：压缩阈值、输出截断、思考流渲染都依赖模型元数据——没有 `contextWindow` 就无法判断何时该压缩；没有 `reasoning` 标记就无法区分思考流与正文流。

**详细行为**：

- 每个 model 声明四字段：
  - `name`：请求 body 的 model 参数；
  - `contextWindow`：上下文窗口（token 数），驱动压缩阈值（80% × window）与状态栏进度条，默认 128000；
  - `maxOutput`：单次输出上限 → 请求的 `max_tokens`，默认 16384；
  - `reasoning`：是否思考模型，默认 false。
- `reasoning: true` 的模型：
  - 状态机 submit 迁 thinking（先思考后正文），false 迁 responding；
  - 思考内容走独立通道渲染（thought_delta / 思考块）；
  - thinking 数组记录实际 reasoning；false 时即使模型返回 reasoning 也存空字符串（不记录不显示）。
- 模型条目在 /config providers 子树与 WebUI Models 区逐字段编辑。

**边界与失败模式**：

- contextWindow 配得比实际小 → 压缩提前触发（保守但安全）；配大了 → 可能请求超窗 400，error 块提示后由用户调低。
- reasoning 误标 false → 思考内容混进正文流（模型行为差异，需用户修正配置）。
- 默认值由 zod schema 并入（新建条目不填也能通过校验）。

**场景走查**：接入 GLM-4.6（reasoning）→ models 加 `{ name: 'glm-4.6', contextWindow: 200000, maxOutput: 32768, reasoning: true }` → 对话时状态栏先 Thinking 后 Responding，思考块折叠可展开。

### R-LLM-04 默认模型

**需求动机**：用户不该每次启动都选模型——`defaultProvider` + `defaultModel` 定义「开箱即用」的对话模型；同时空配置（首次安装）不能让程序崩溃，要能启动并引导配置。

**详细行为**：

- config 顶层 `defaultProvider`/`defaultModel` 指定对话使用的模型。
- 加载期缺省规则（resolveCurrent）：defaultProvider 未命中（未设/名字不存在）→ 回落第一个 provider；defaultModel 未命中 → 回落该 provider 的第一个 model。
- `/model` 选择器的两连击（选 provider → 选 model）就是两次 config_set 写这两个键。
- 空配置（providers 为空）时无默认值——程序照常启动，isConfigured 判定 false，状态栏显示「未配置 provider（请先 /config）」，提交对话回 notice 引导。

**边界与失败模式**：

- defaultModel 指向的 model 在 provider 被删除后 → 回落第一个 model，不报错。
- resolveCurrent 的调用方（agent 门面）约定先经 isConfigured 判定——空 providers 时直接 `!` 断言会抛（类型层面的契约）。
- TUI 启动瞬间 config 未回来时顶栏显示「加载配置中…」，品牌头延迟到 config + cwd 就绪才打印（Static 只渲染一次，定格错误信息无法纠正）。

**场景走查**：配置两个 provider（glm、deepseek）与各自的 models → defaultProvider=glm → 启动直接可用；用户想临时用 deepseek → /model 两击切换，配置持久化。

### R-LLM-05 流式双通道

**需求动机**：推理模型的「思考过程」与「面向用户的回答」价值不同——前者可折叠略读，后者是正式交付物。混在一条流里既难读又无法折叠。

**详细行为**：

- 响应走 SSE，正文增量（text_delta）与思考增量（reasoning_content/reasoning 字段归一为 thought_delta）分通道产出。
- agent 把 thought_delta 仅在 `turn.reasoning` 为 true 时向 UI 广播（普通模型的杂散 reasoning 不显示）。
- UI 双通道渲染：TUI 思考块黄色可折叠（partial 未落盘阶段实时增长），WebUI 折叠面板。
- done 事件携带完整 reasoning 供持久化——resume 后按 assistant 消息一一对应重建思考块。
- 流式中断/失败按 R-DLG-06 处理。

**边界与失败模式**：

- 部分兼容端点思考字段名不同（reasoning_content vs reasoning）——parser 双字段回退。
- 非 reasoning 模型偶发返回 reasoning 字段 → 内容被忽略不渲染。
- 思考块与正文块的分界由第一条 text_delta 触发 flush；模型全程无正文只有工具调用时，收尾处补 thought_done 迁移保证状态机一致。

**场景走查**：glm-4.6 对「分析这段报错」先吐 800 字思考（折叠块增长）→ 转正文流式 → 完成后思考块折叠成 3 行摘要，点击展开看全文。

### R-LLM-06 工具声明（tools 参数）

**需求动机**：模型能调用哪些工具由每次请求的 `tools` 参数决定。MCP 工具在运行期动态注册/摘除——若 schema 在启动时缓存成快照，新接入的工具模型永远看不到，摘除的工具模型还会「幻调」。

**详细行为**：

- 每次请求携带注册表**当前全部工具**的 function schema：`registry.schemas()` 每次调用现算（遍历当前 Map），不缓存快照。
- MCP 工具注册/摘除后，下一次请求即时反映——模型永远看到当前可用的工具集。
- schema 形状：`{ type: 'function', function: { name, description, parameters } }`，parameters 为各工具声明的 JSON Schema（MCP 工具为服务原生透传）。
- 压缩判断同样用 `schemas()` 现算工具段 token——工具集变化连压缩估算口径都保持一致。
- UI 侧 `tools_list` 广播携带身份（builtin/mcp{server,name}），/tools 面板与 WebUI Available Tools 卡按来源分组展示。

**边界与失败模式**：

- MCP server 半挂载（部分工具注册失败）→ syncRegistry 先摘后挂，失败服务整体摘除——schema 里不会出现残缺工具。
- 工具名不合规范 → 注册关口已哈希（见 R-TLB-08），schemas() 发出的名字必然合规。

**场景走查**：用户在 /mcp 启用 playwright server → mcp_list/tools_list 广播 → 同一会话下一轮请求即带 `mcp__playwright__browser_navigate` 等工具 → 模型立即调用。

### R-LLM-07 完整性判定（isConfigured）

**需求动机**：「配置文件存在」不等于「能对话」——可能只有半个 provider（缺 apiKey）、或 defaultModel 拼错。需要一个纯函数判定把「能不能提交对话」与「配置长什么样」解耦。

**详细行为**：

- `isConfigured(config)` 的判定链（住 bridge 契约包，agent 与 UI 共用同一实现）：
  1. 找 defaultProvider 命中的 provider，未命中取第一个；
  2. 无 provider → false；
  3. 该 provider 的 name/baseURL/apiKey 任一 trim 后为空、或 models 为空 → false；
  4. 取 defaultModel 命中的 model（未命中取第一个），model 不存在或 name 为空 → false；
  5. 全部通过 → true。
- 所有「动对话」的消息入口（submit/compact_request/invoke_skill/context_request/status_request）先查此判定——false 时发 notice「尚未配置 provider，请先 /config 添加并保存后重试」并拒绝执行。
- 程序照常启动（TUI 状态栏显示引导文案，WebUI 设置弹框可打开）。
- 配置变更后 onConfigChanged 钩子重新判定，true 时立即推送 status_state 刷新界面。

**边界与失败模式**：

- 判定是纯派生——TUI 顶栏的「未配置 provider」提示与 agent 的提交拦截永不漂移。
- providers 数组第一个条目是编辑中的空节点时，isConfigured 会因它 trim 为空而 false——即使后面有完整 provider（回落顺序是数组序，用户应删除空节点或把它填完）。

**场景走查**：首次安装 → 空 providers → 提交「你好」→ notice「尚未配置 provider…」→ /config 建好并保存 → 同一会话直接提交成功。

### R-LLM-08 编辑期放宽

**需求动机**：如果 schema 强制 provider 全字段非空，用户就无法「先建节点、后补字段」——每次回车都校验失败，交互极差。编辑期放宽 + 完整性判定（R-LLM-07）把关是刻意解耦。

**详细行为**：

- 配置编辑器的 provider/model 字段在 zod schema 层刻意放宽：name/baseURL/apiKey 允许暂时为空字符串、models 允许空数组——支持 /config 树与 WebUI 表单里「自由创建节点、逐字段填写」的流程。
- 保存仍经 configSchema.parse（并入默认值：contextWindow 128000、maxOutput 16384、reasoning false、models []）+ 重名检查。
- 校验失败回滚到 lastGood 快照并 emit error——不写坏配置。
- 能对话与否由 isConfigured 在运行时把关——两者互不替代。

**边界与失败模式**：

- 放宽只作用于 providers 子树——permission 锚点校验、maxIterations 的 -1/正整数约束等其它 schema 校验照常生效（校验失败编辑即报错回滚）。
- 空节点长期存在会让 isConfigured false（见 R-LLM-07 边界）。

**场景走查**：用户回车「添加 provider」产生空节点 → 逐字段填 name → 先保存（合法）→ 再补 baseURL/apiKey/models → 最终保存成功；期间任何时刻提交对话都由 isConfigured 决定是否放行。
