# R-SKL 技能系统

Skills 是用户可编写的「指令包」：一个目录 + 一份 SKILL.md，描述「什么时候用、怎么干」。模型在合适场景按需读取全文执行——把领域知识、工作流程、模板沉淀为可复用、可共享的资产。兼容主流 Agent Skills 格式（外部/npx 安装的 skill 包可直接放入目录使用）。

## 工作原理概述

**两级扫描与缓存失效。** SkillsManager 扫描且仅扫描两个目录：用户级 `~/.dogegg/skills/`（个人所有项目可用）、项目级 `<repo>/.dogegg/skills/`（随仓库共享，目录随会话 cwd 走）。`list()` 产出 SkillInfo 数组（项目在前、各自字母序），每个条目带 name/description/scope/path/enabled/missing 六元组。扫描结果有缓存——系统提示段与 token 估算在每次状态变化时都会触发 list()，现扫文件系统会成为热路径；缓存在任何写操作、setProjectDir、显式 invalidate() 时失效，skills_request（面板/联想刷新）走门面的 invalidate + list，保证外部手改文件也可见。

**渐进披露的成本模型。** 技能的核心矛盾：技能库可能有几十个，但每个技能的完整指令很长——全量注入系统提示会吃掉大量上下文，不注入模型又不知道它们存在。解法是两段式披露：

- 第一段：系统提示只注入「广告段」（`## 可用 Skills` + 每条一行 `- 名字：描述（路径）`，无技能时整段不注入）；
- 第二段：模型凭描述判断相关性，命中后**自己用 read_file 读取** SKILL.md 全文获得详细指令——不命中就不读。

几十个技能的稳态成本只是几十行广告。这也是为什么 `description` 是模型判断何时使用的唯一依据（必须写得能区分场景）、以及为什么用户级 skills 目录被列入内置读豁免（系统提示引导模型去读，不应反复弹审批）。

**启停的旁挂设计。** 启停状态存独立名单文件（`{ "disabled": ["名字", ...] }`，与 skills 目录同层：用户级 `~/.dogegg/.skills.json`、项目级 `<repo>/.dogegg/.skills.json`，与 `.mcp.json` 同构），**只记停用名单**（缺省即启用）。不写进 SKILL.md 的原因：外部安装的文件不可安全重写（启停一次就把第三方文件改了，升级会冲突）——主流 SKILL.md 格式零污染。项目级名单随 `.dogegg/` 进 git 与仓库共享。

**三态条目模型。** 扫描把每个条目归为三态：

- **启用**：目录在且不在停用名单；
- **停用**：目录在且在名单——文件保留，退出广告/联想/调用三个生效面；
- **文件缺失**：名单在案但目录已被外部删除（手动/git/换分支产生）——灰显 + 标注，永不进提示与调用，仅供清理。

三态让「外部世界改文件」这类不受控事件有确定的、可见的语义。

**调用渲染。** 斜杠命令 `/<skill名>` → `invoke_skill` 消息 → SkillsManager.forInvocation：在可用条目（enabled 且非缺失）内查找（同名项目级优先）→ 读 SKILL.md → 正文含 `$ARGUMENTS` 占位符则替换为命令参数，无占位且有参则追加「用户参数：…」段 → 渲染结果作为一条用户消息进入对话轮次（模型按指令执行）——技能调用就是一个预填充的 prompt。

## 需求点

### R-SKL-01 目录规范与命名

**需求动机**：技能既是文件系统资产（用户手动放置/编辑）又是命令名（`/xxx` 调用）——目录规范必须同时满足「防路径穿越」与「命令名合法性」，且与主流 Agent Skills 生态兼容。

**详细行为**：

- 只扫两级：用户级 `~/.dogegg/skills/`、项目级 `<repo>/.dogegg/skills/`（不递归扫嵌套、不扫其它位置）。
- skill 名 = 目录名（唯一事实源——SKILL.md frontmatter 里的 name 仅文档性），格式 `SKILL_NAME_RE = /^[a-z0-9][a-z0-9-]*$/`（小写字母/数字开头，含连字符）——也是未来的斜杠命令名。
- 扫描时不符合命名规则的目录直接跳过。

**边界与失败模式**：

- 名称校验双保险：NAME_RE + 路径越界检查（join 后必须仍在根目录内——`assertInside`，`../` 类名字即使绕过正则也进不去）。
- 目录不可读（权限）按无条目处理，不拖垮扫描。

**场景走查**：用户 `mkdir ~/.dogegg/skills/release-notes` 放一个第三方技能包 → 无需重启，下一次 skills_request 后 /skills 面板与斜杠联想即出现 `/release-notes`。

### R-SKL-02 文件格式（frontmatter 子集解析）

**需求动机**：技能要兼容主流 Agent Skills 格式才能复用生态资产——但又不能引入 YAML 解析依赖与全套规范的复杂度。最小子集解析是平衡点。

**详细行为**：

- 每个 skill 一个目录，入口文件 `SKILL.md`。
- frontmatter 声明元数据：`description`（模型判断何时使用的**唯一依据**，必须写得能区分场景）；`name` 可省（缺省取目录名）。
- 解析器（parseSkillMd）不引 YAML 依赖：识别首行 `---` 与闭合 `---` 之间的块，块内只取 `description:` 单行键值，其余键忽略；无 frontmatter 或无闭合 → description 为空、正文为全文。
- 正文即指令：模型命中场景后读取全文照做。
- 目录内可放附属资源（模板/脚本），由正文指引模型按需读取（read_file 天然支持）。

**边界与失败模式**：

- 解析失败（frontmatter 结构坏）不隐身——条目照常出现在清单里，description 显示「（SKILL.md 解析失败——请检查 frontmatter/正文）」供诊断（见 R-SKL-09）。
- description 为空的条目广告行显示「（无描述）」——仍可用但模型难以判断场景。

**场景走查**：外部技能包的 SKILL.md 带 `name`、`description`、`license` 三个 frontmatter 键 → 解析取 description，name/license 忽略 → 面板显示描述、调用按目录名。

### R-SKL-03 渐进披露（上下文成本控制）

**需求动机**：上下文窗口是 agent 最稀缺的资源——几十个全量技能注入可能吃掉 20k+ token，而模型单轮实际命中的往往不超过一个。不控制成本，技能系统本身会成为对话质量的负资产。

**详细行为**：

- 系统提示只注入一行广告：`- 名字：描述（路径）`（`promptSection()` 现算，随每次 systemPrompt() 拼装）——模型凭描述判断相关性。
- 命中后模型**自己用 read_file 读取** SKILL.md 全文获得详细指令——不命中就不读，几十个 skill 的上下文成本也只是几十行。
- 广告段引导语明确告知模型「当用户请求与某个 skill 的描述相关时，先用 read_file 读取其 SKILL.md 获取完整指令再执行」。
- 无任何可用 skill 时整段不注入（省上下文）。
- 停用/缺失条目不进广告段（可用条目 = enabled 且非缺失）。

**边界与失败模式**：

- 广告段是现算的——技能增删/启停即刻反映到下一轮请求。
- token 估算与实际请求同口径（同一 prompt 组装函数），技能段的变化计入压缩阈值判断。
- 模型不守规矩直接猜指令而不读文件是模型行为问题（广告段已给路径引导）。

**场景走查**：用户装了 40 个技能 → 系统提示里只有 40 行广告（约 1.5k token）→ 用户说「帮我写 release notes」→ 模型读到 `- release-notes：按仓库 commit 生成发布说明（~/.dogegg/skills/release-notes/SKILL.md）` → read_file 读取全文 → 按指令执行。

### R-SKL-04 调用（$ARGUMENTS 渲染）

**需求动机**：技能若只能作为「被动广告」等模型自己发现，就无法承载「用户明确点名」的场景（「按 deploy 技能来一遍」）。斜杠命令让技能成为一等公民的显式入口，参数让同一技能可复用于不同输入。

**详细行为**：

- 斜杠命令 `/<skill名>` 触发（命令参数作为 `$ARGUMENTS`，如 `/deploy staging --dry-run` → args=`staging --dry-run`）。
- 渲染规则：
  - 正文含 `$ARGUMENTS` 占位符 → 全部替换为参数（replaceAll）；
  - 无占位且有参 → 参数追加为「用户参数：…」段（指令仍然生效，参数作为附加输入）；
  - 无占位无参 → 正文原样。
- 调用前校验：条目必须在可用清单内（停用/缺失 → 抛错转 notice「未找到 skill：X（可能已停用或目录缺失）」）；正文为空 → 抛错。
- 渲染结果经 `turnRunner.submit(skillText)` 进入对话轮次——模型收到的是一条普通用户消息（内容是指令 + 参数），按指令执行（可能调工具、可能直接回答）。

**边界与失败模式**：

- 内置命令优先——`/skills`、`/mcp` 等内置名是保留字，不可被同名 skill 覆盖（parseCommand 先查内置表）。
- 未配置 provider 时 invoke_skill 被拦截（与 submit 同样的 isConfigured 检查）。
- 调用是同步渲染的——SKILL.md 被外部删除的瞬间调用 → 抛错转 notice。

**场景走查**：用户输入 `/deploy staging` → 渲染后的指令文本作为 user 消息进对话 → 模型按指令执行部署步骤（调 shell 等）→ 全程与普通对话无异，只是首条消息来自模板。

### R-SKL-05 同名覆盖（项目级优先）

**需求动机**：团队在项目里定制了一个技能（如特定部署流程），个人目录里还有个同名的通用版——调用必须无歧义地命中项目定制，否则团队共享形同虚设。

**详细行为**：

- 项目级与用户级可存在同名 skill：调用与联想**取项目级**（forInvocation 在可用条目内先找 scope === 'project' 的命中，没有才取用户级）。
- 面板两组都可见（list() 不去重，条目各自带 scope——用户能看到两份并知道优先级）。
- 系统提示广告段两份都列出（路径不同，模型可自行选择读哪个——但斜杠调用是确定的）。

**边界与失败模式**：

- 项目级停用时同名用户级照常生效（停用 = 退出竞争，不是「连坐」）。
- 项目级缺失（目录被外部删）时用户级接管——覆盖关系按「可用条目内」判定，缺失态不参与。

**场景走查**：`~/.dogegg/skills/deploy` 与 `.dogegg/skills/deploy` 并存 → 面板显示两条（标注 project/user）→ `/deploy` 调用命中项目级 → 用户停用项目级 → `/deploy` 转而命中用户级通用版。

### R-SKL-06 CRUD

**需求动机**：技能的生命周期管理（建/改/删/查）若只能手动操作文件系统，门槛高且易错（frontmatter 格式、目录规范）；两端 UI 的同等 CRUD 让技能管理成为产品能力而非约定。

**详细行为**：

- TUI /skills 面板（↑↓ 选择、Enter 查看全文、a 新建、e 编辑、t 启停、d 删除确认）与 WebUI 设置 Skills 区同等支持，走同一套 `skills_manage` 消息（create/update/delete/get/toggle）。
- **新建**：表单（落点 project/user、名称、描述）→ 生成骨架 SKILL.md（frontmatter name/description + `使用 $ARGUMENTS 作为用户传入的参数。` + 正文占位提示），引导用户充实；名称非法/已存在 → 抛错转 notice。
- **编辑**：TUI 用 $EDITOR 系统编辑器（spawnSync 阻塞至退出，暂停 raw mode，退出后清屏重挂 + 重拉清单；缺省 notepad/vi）；WebUI 用全文编辑框（get 取全文 → update 整文件替换）。
- **删除**：整目录删除（rmSync recursive+force，含附属资源文件），幂等（不存在静默成功），带确认；名单同步清理不留孤儿。
- **查**：get → skill_content 消息 → 详情展示。
- CRUD 全部限定在两级根目录内（名称校验 + 路径越界双保险）。

**边界与失败模式**：

- 缺失态条目不可编辑（无文件可编——「清理走 t 或 d」）。
- 运行中（gate busy）管理操作阻塞（文件写操作与 in-flight 轮次可能竞争）。
- create 后 notice 提醒「正文记得用编辑器充实」。

**场景走查**：TUI /skills → a → 表单填落点=project、名称=code-review、描述=「按团队规范审查代码」→ s 创建 → e 打开 $EDITOR 写正文 → 保存 → `/code-review` 立即可用。

### R-SKL-07 启停（旁挂名单）

**需求动机**：临时不想让某技能被模型使用（调试、季节性任务），但不想删掉配置与文件；同时启停状态要能随项目共享（团队统一停用一个有问题的技能）。

**详细行为**：

- 每个 skill 可停用/启用（TUI `t` 键 / WebUI 按钮）。
- 停用 = 同时退出三个生效面：系统提示广告、斜杠联想、调用（文件保留，随时恢复）。
- 状态存**旁挂名单文件**（与 `.mcp.json` 同构）：用户级 `~/.dogegg/.skills.json`、项目级 `<repo>/.dogegg/.skills.json`，形状 `{ "disabled": ["名字", ...] }`——缺省即启用。
- 项目级停用随 `.dogegg/` 进 git 与仓库共享。
- 写操作同步失效缓存。

**边界与失败模式**：

- 主流 SKILL.md 格式**零污染**——启停状态绝不写进 skill 文件（外部安装的文件不可安全重写）。
- 重复停用幂等（已在名单不重复写）；启用不在名单的名字同样幂等。
- 对缺失态条目「启用」= 清理孤儿记录（notice 文案区分「已清理（移除孤儿记录）」与「已启用」，避免误导）。

**场景走查**：团队发现 deploy 技能在 monorepo 下行为错误 → 在 `.dogegg/.skills.json` 停用它并提交 → 全组拉取后该技能从广告/联想/调用消失，文件仍在仓库里。

### R-SKL-08 缺失态（孤儿可见）

**需求动机**：停用名单在案但目录被外部删除（手动删除/git 操作/换分支）时，名单条目若隐身，用户会困惑「我明明停用过它，怎么找不到了」；若自动清理，又会在分支切换回来自动恢复状态——都不对。可见的孤儿态是第三条路。

**详细行为**：

- 停用名单在案、但 skill 目录已被外部删除 → 条目以「文件缺失」可见（灰显 + 标注「（目录已不存在）」），**永不进提示与调用**（不进可用条目集合——广告、联想、调用都以 enabled && !missing 过滤）。
- 清理 = 启用该条目（移除孤儿记录——t 键/按钮语义即「从名单移除」）；删除缺失条目同样等价清理（remove 幂等）。
- 单个 skill 目录被删 → 该条目孤儿可见；整个 skills 目录被删 → 名单内全部条目可见（目录存在性检查在扫描内、孤儿枚举在扫描外，互不影响）。

**边界与失败模式**：

- 目录整体不可读（权限）也走「无条目 + 孤儿照常枚举」路径。
- 孤儿条目不参与同名覆盖（缺失态退出竞争）。
- 名单里的名字不符合命名规则（外部手写坏）→ 枚举时跳过（不产生垃圾条目）。

**场景走查**：用户在 feature 分支停用了 hotfix 技能 → 切到 main（该目录不存在）→ /skills 显示 hotfix 灰显「（目录已不存在）」→ 切回 feature 分支 → 技能自动恢复可用（名单还在）。

### R-SKL-09 格式自愈与解析失败可见

**需求动机**：状态文件与 SKILL.md 都可能被外部工具或手改弄坏——「坏一个文件拖垮整个技能系统」不可接受；「坏条目静默消失」又会让用户找不到问题。

**详细行为**：

- 状态文件损坏/形状不符（JSON 解析失败、disabled 不是数组、元素非字符串）→ 视为空名单（全部启用），skills 功能不拖垮；用户删状态文件即完全重置。
- readDisabled 的三级容错：文件缺失 → 空名单；JSON 解析失败 → 空名单；形状不符 → 过滤出字符串元素。
- 解析失败的 SKILL.md（frontmatter 结构坏）以「解析失败」条目可见——description 位显示原因（「（SKILL.md 解析失败——请检查 frontmatter/正文）」），不隐身，便于定位修复。
- 失败条目仍参与停用名单语义（可被停用，名单不因解析失败失效）。

**边界与失败模式**：

- 状态文件容错的结果是「保守恢复」——宁可信一切技能可用（有权限网关兜底），不可让技能功能瘫痪。
- SKILL.md 解析失败只影响该条目的 description 展示，正文仍在（调用时读到的正文可能仍是好的）。

**场景走查**：用户手改 `.skills.json` 时不小心写成 `{ disabled: "deploy" }` → 下次扫描视为空名单（全部启用）→ 技能照常可用 → 用户修正文件后停用状态恢复。

### R-SKL-10 重建语义（同名新建 = 全新开始）

**需求动机**：用户停用了一个技能、后来删掉目录、又想重建同名技能——如果旧的停用记录仍然生效，新建的技能会「莫名人不可见」，排查成本极高。创建是显式的新开始。

**详细行为**：

- 同名重建（停用后删除再创建）默认启用——create 成功后自动从停用名单移除同名记录（`writeDisabled(scope, readDisabled(scope).filter(n => n !== name))`）。
- 这一语义同时覆盖：从未停用直接重建（名单本无记录，幂等）与外部曾产生孤儿记录（create 让孤儿记录消亡——目录回来了且不在名单）。

**边界与失败模式**：

- create 在目录已存在时抛错（不覆盖既有技能——重建的前提是先删）。
- 名单移除发生在 create 成功路径（名称非法/已存在的失败不碰名单）。

**场景走查**：用户停用 `deploy` → 手动删目录（名单留孤儿）→ 面板重建同名 → 创建成功且默认启用，孤儿记录被移除。

## 边界与立法

- 调用与广告的命中都在「可用条目」（enabled 且非缺失）内按项目覆盖用户优先——项目级停用时同名用户级照常生效。
- 名称校验双保险：NAME_RE + 路径越界检查（join 后必须仍在根目录内）。
