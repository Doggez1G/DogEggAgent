# R-SKL 技能系统

> Skills 是用户可编写的「指令包」：一个目录 + 一份 SKILL.md，描述「什么时候用、怎么干」。本域给用户三层能力：把领域知识/工作流程/模板沉淀为可复用、可共享的文件资产（兼容主流 Agent Skills 格式，外部安装的 skill 包可直接放入目录使用）；通过斜杠命令显式调用或由模型按描述自动命中执行；在 TUI/WebUI 两端对面板清单做增删改查与启停管理。

## 域机制概览

**两级扫描与缓存失效。** SkillsManager 扫描且仅扫描两个目录：用户级 `~/.dogegg/skills/`（个人所有项目可用）、项目级 `<repo>/.dogegg/skills/`（随仓库共享，目录随会话 cwd 走，`set_cwd` 后重扫广播）。`list()` 产出 SkillInfo 数组（项目在前、各自字母序），每个条目带 name/description/scope/path/enabled/missing 六元组。扫描结果有缓存——系统提示段与 token 估算在每次状态变化时都会触发 list()，现扫文件系统会成为热路径；缓存在任何写操作、setProjectDir、显式 invalidate() 时失效，skills_request（面板/联想刷新）走门面的 invalidate + list，保证外部手改文件也可见。

**渐进披露的成本模型。** 技能的核心矛盾：技能库可能有几十个，但每个技能的完整指令很长——全量注入系统提示会吃掉大量上下文，不注入模型又不知道它们存在。解法是两段式披露：第一段系统提示只注入「广告段」（`## 可用 Skills` + 每条一行 `- 名字：描述（路径）`，无技能时整段不注入）；第二段模型凭描述判断相关性，命中后**自己用 read_file 读取** SKILL.md 全文获得详细指令——不命中就不读。几十个技能的稳态成本只是几十行广告。这也是为什么 `description` 是模型判断何时使用的唯一依据（必须写得能区分场景）、以及为什么用户级 skills 目录被列入内置读豁免（系统提示引导模型去读，不应反复弹审批——仅 read_file、仅配置桶落 ask 时自动 allow，reject/会话提升等更早判定不受影响）。

**启停的旁挂设计与三态条目模型。** 启停状态存独立名单文件（`{ "disabled": ["名字", ...] }`，与 skills 目录同层：用户级 `~/.dogegg/.skills.json`、项目级 `<repo>/.dogegg/.skills.json`，与 `.mcp.json` 同构），**只记停用名单**（缺省即启用）——外部安装的文件不可安全重写，主流 SKILL.md 格式零污染。扫描把每个条目归为三态：启用（目录在且不在名单）、停用（目录在且在名单，退出广告/联想/调用三个生效面）、文件缺失（名单在案但目录已被外部删除，灰显供清理，永不进提示与调用）。三态让「外部世界改文件」这类不受控事件有确定的、可见的语义。

**调用渲染。** 斜杠命令 `/<skill名>` → invoke_skill 消息 → SkillsManager.forInvocation 在可用条目（enabled 且非缺失）内查找（同名项目级优先）→ 读 SKILL.md → 正文含 `$ARGUMENTS` 占位符则替换为命令参数，无占位且有参则追加「用户参数：…」段 → 渲染结果作为一条用户消息进入对话轮次——技能调用就是一个预填充的 prompt。

## 需求点

### R-SKL-01 目录规范与命名

**需求背景与动机**：用户（或第三方包的安装脚本）把技能目录放进文件系统，同时系统要拿目录名当斜杠命令名。目录名若不受限，`../evil` 这类名字会造成路径穿越（CRUD 与调用时的文件操作越出 skills 根目录）；带空格/大写/中文的名字则让 `/xxx` 命令无法输入。目录规范必须同时满足「防路径穿越」与「命令名合法性」，且与主流 Agent Skills 生态兼容。没有它会怎样：一个恶意命名的第三方技能包就能让「删除技能」操作删到 skills 目录之外。

**功能规格**：

1. 触发与扫描时机：挂载播种、skills_request、每次管理写操作之后（门面统一重扫广播）；只扫两级——用户级 `~/.dogegg/skills/`、项目级 `<repo>/.dogegg/skills/`，不递归扫嵌套、不扫其它位置。
2. skill 名 = 目录名（唯一事实源——SKILL.md frontmatter 里的 name 仅文档性），格式 `SKILL_NAME_RE = /^[a-z0-9][a-z0-9-]*$/`（小写字母/数字开头，可含连字符）——也是斜杠命令名。
3. 扫描处理规则：readdirSync 取目录条目（withFileTypes，仅目录），不符合命名规则的直接跳过；条目下无 SKILL.md 的跳过。
4. 输出：SkillInfo 六元组（name/description/scope/path/enabled/missing），项目级在前、用户级在后，各自字母序。
5. 命令入口：TUI /skills 面板与 WebUI 设置 Skills 区展示清单；名称非法在 create 时被拒（见 R-SKL-06）。

**边界与失败模式**：

- 名称校验双保险：NAME_RE + 路径越界检查（assertInside——join 后必须仍在根目录内，`../` 类名字即使绕过正则也进不去；所有 CRUD 与启停前都过这一关）。
- 目录不可读（权限）→ readdirSync 抛错被捕获，按无条目处理，不拖垮扫描（孤儿枚举照常）。
- 项目级目录未就绪（无工作目录）→ 管理操作抛「项目级 skills 目录不可用」转 notice。

**验收标准**：

1. 当 `~/.dogegg/skills/release-notes/` 放入含 SKILL.md 的目录，则下一次 skills_request 后清单出现该条目（scope=user）。
2. 当目录名为 `Release Notes` 或 `../evil`，则不出现在清单中（正则过滤）。
3. 当 skills 目录不可读，则清单为空且不抛错（扫描不崩）。
4. 当 SKILL.md 缺失但目录存在，则该条目不出现在清单中。

**场景走查**：用户 `mkdir ~/.dogegg/skills/release-notes` 放一个第三方技能包 → 无需重启，下一次 skills_request 后 /skills 面板与斜杠联想即出现 `/release-notes`。

### R-SKL-02 文件格式（frontmatter 子集解析）

**需求背景与动机**：用户会从社区复用别人写的技能包（Agent Skills 规范格式），也会自己手写。若要求完整 YAML frontmatter，就得引入 YAML 解析依赖且错误模式复杂；若完全不定义元数据，模型与面板又无从判断「什么时候用这个技能」。最小子集解析是「兼容生态」与「实现简单」的平衡点。

**功能规格**：

1. 文件布局：每个 skill 一个目录，入口文件固定为 `SKILL.md`。
2. frontmatter 声明元数据：`description`（模型判断何时使用的**唯一依据**，必须写得能区分场景）；`name` 可省（缺省取目录名）。
3. 解析规则（parseSkillMd，纯函数）：识别首行 `---` 与闭合 `---` 之间的块，块内只取 `description:` 单行键值（正则逐行匹配、取第一条命中），其余键忽略；CRLF 归一为 LF 后再解析。
4. 无 frontmatter 或无闭合 `---` → description 为空、正文为全文（trim 后）。
5. 正文即指令：模型命中场景后读取全文照做；目录内可放附属资源（模板/脚本），由正文指引模型按需 read_file。
6. 骨架生成（skeletonSkillMd）：create 的产物为 frontmatter（name/description）+ 「使用 $ARGUMENTS 作为用户传入的参数。」+ 正文占位提示「（在此写下交给模型的完整指令……）」——格式正确、立即可用，正文留给用户充实。

**边界与失败模式**：

- 解析失败（frontmatter 结构坏导致 readFileSync/parse 抛错）不隐身——条目照常出现在清单里，description 显示「（SKILL.md 解析失败——请检查 frontmatter/正文）」供诊断（见 R-SKL-09）。
- description 为空的条目广告行显示「（无描述）」——仍可用但模型难以判断场景。
- frontmatter 有 `---` 开头但无闭合 → 按「无 frontmatter」处理，全文当正文。

**验收标准**：

1. 当 SKILL.md 带 `name`、`description`、`license` 三个 frontmatter 键，则解析只取 description，面板显示描述、调用按目录名。
2. 当 frontmatter 缺失，则 description 为空、广告行显示「（无描述）」、调用仍按正文执行。
3. 当正文含 `$ARGUMENTS`，则调用时占位符被替换（见 R-SKL-04）。

**场景走查**：外部技能包的 SKILL.md 带 `name: release-notes`、`description: ...`、`license: MIT` → 面板显示描述、`/release-notes` 按目录名命中调用。

### R-SKL-03 渐进披露（上下文成本控制）

**需求背景与动机**：用户装了几十个技能后，上下文窗口是 agent 最稀缺的资源——几十个全量技能注入可能吃掉 20k+ token，而模型单轮实际命中的往往不超过一个。不控制成本，技能系统本身会成为对话质量的负资产（挤占正事上下文、加速触发压缩）。

**功能规格**：

1. 注入形态：系统提示末尾追加 `## 可用 Skills` 段——引导语（「当用户请求与某个 skill 的描述相关时，先用 read_file 读取其 SKILL.md 获取完整指令再执行」）+ 每个可用条目一行 `- 名字：描述（路径）`。
2. 现算时机：promptSection() 由 ContextAssembler 的动态段回调在每次 systemPrompt() 拼装时现算——技能增删/启停即刻反映到下一轮请求，无需重启。
3. 可用条目定义：enabled 且非 missing；停用/缺失条目不进广告段。
4. 空集行为：无任何可用 skill 时整段不注入（省上下文）。
5. 第二段：模型凭描述判断相关性，命中后自己用 read_file 读取 SKILL.md 全文——不命中就不读。
6. 口径一致：token 估算与实际请求同口径（同一 prompt 组装函数），技能段的变化计入压缩阈值判断。

**边界与失败模式**：

- 模型不守规矩直接猜指令而不读文件是模型行为问题（广告段已给路径引导）。
- 用户级 skills 目录在 read_file 落 ask 时自动 allow（内置读豁免）——否则渐进披露的「模型自己读全文」每次都弹审批（见 05-权限与安全）。
- 项目级 skills 目录不在豁免名单内——项目级技能的读取按常规权限判定。

**验收标准**：

1. 当装了 40 个可用技能，则系统提示里技能部分只有 40 行广告（约 1.5k token 量级），无正文注入。
2. 当全部技能停用或目录为空，则系统提示不含「可用 Skills」段。
3. 当停用某技能，则下一轮请求的广告段不再含该条目。
4. 当模型按引导 read_file 用户级技能的 SKILL.md，则不触发审批弹层（豁免生效）。

**场景走查**：用户装了 40 个技能 → 系统提示只有 40 行广告 → 用户说「帮我写 release notes」→ 模型读到 `- release-notes：按仓库 commit 生成发布说明（~/.dogegg/skills/release-notes/SKILL.md）` → read_file 读取全文 → 按指令执行。

### R-SKL-04 调用（$ARGUMENTS 渲染）

**需求背景与动机**：用户明确点名一个技能时（「按 deploy 技能来一遍」），不能指望模型碰巧从广告段联想到——需要斜杠命令这个一等公民的显式入口；同一技能还要能复用于不同输入（staging / production）。没有参数渲染的话，同一任务的不同目标就得复制出多个技能副本。

**功能规格**：

1. 触发：输入 `/<skill名>`（两端的 parseCommand 在内置命令未命中后，首词命中 skill 名即产出 invoke_skill 消息），命令参数作为 `$ARGUMENTS`（如 `/deploy staging --dry-run` → args=`staging --dry-run`）。
2. 前置校验（agent 侧）：未配置 provider 时 invoke_skill 被拦截，回 notice「尚未配置 provider…」（与 submit 同样的 isConfigured 检查）。
3. 命中规则：forInvocation 在可用条目（enabled 且非 missing）内查找，同名项目级优先（见 R-SKL-05）；全部未命中 → 抛错转 notice「未找到 skill：X（可能已停用或目录缺失）」。
4. 渲染规则：正文含 `$ARGUMENTS` 占位符 → 全部替换为参数（replaceAll，args 先 trim）；无占位且有参 → 参数追加为「用户参数：…」段；无占位无参 → 正文原样。
5. 正文为空 → 抛错转 notice（空指令调了等于没调）。
6. 输出：渲染结果经 turnRunner.submit 进入对话轮次——模型收到一条普通用户消息（内容是指令 + 参数），按指令执行（可能调工具、可能直接回答）。

**边界与失败模式**：

- 内置命令优先——`/skills`、`/mcp` 等内置名是保留字，不可被同名 skill 覆盖（parseCommand 先查内置表）。
- 调用是同步渲染的——SKILL.md 被外部删除的瞬间调用 → 抛错转 notice。
- 渲染失败（未找到/正文空）不进轮次——不会有「空消息」污染 history。

**验收标准**：

1. 当正文含 `$ARGUMENTS` 且调用带参，则渲染文本中占位符全部替换为参数原文。
2. 当正文无占位符且调用带参，则渲染文本末尾追加「用户参数：…」段。
3. 当正文无占位符且调用无参，则渲染文本与正文完全一致。
4. 当目标技能已停用，则调用被拒并提示「未找到 skill」（不进入对话轮次）。
5. 当同名 skill 存在于项目级与用户级且都可用，则调用命中项目级。

**场景走查**：用户输入 `/deploy staging` → 渲染后的指令文本作为 user 消息进对话 → 模型按指令执行部署步骤（调 shell 等）→ 全程与普通对话无异，只是首条消息来自模板。

### R-SKL-05 同名覆盖（项目级优先）

**需求背景与动机**：团队在项目里定制了一个技能（如特定部署流程），个人目录里还有个同名的通用版——调用必须无歧义地命中项目定制，否则团队共享形同虚设；但用户又需要能看到两份的存在以便排查「为什么行为和我本地的不一样」。

**功能规格**：

1. 命中规则：项目级与用户级可存在同名 skill；forInvocation 在可用条目内先找 scope === 'project' 的命中，没有才取用户级。
2. 清单呈现：list() 不去重，条目各自带 scope——面板两组都可见，用户能看到两份并知道优先级。
3. 系统提示广告段两份都列出（路径不同，模型可自行选择读哪个——但斜杠调用是确定的）。
4. 覆盖关系按「可用条目内」判定：停用与缺失态都不参与竞争。

**边界与失败模式**：

- 项目级停用时同名用户级照常生效（停用 = 退出竞争，不是「连坐」）。
- 项目级缺失（目录被外部删）时用户级接管。
- 两份都停用 → 调用报「未找到 skill」。

**验收标准**：

1. 当 `~/.dogegg/skills/deploy` 与 `.dogegg/skills/deploy` 并存且都启用，则 `/deploy` 渲染的是项目级正文。
2. 当项目级 deploy 被停用，则 `/deploy` 命中用户级通用版。
3. 当项目级 deploy 目录被外部删除，则 `/deploy` 命中用户级。
4. 当清单展示，则同名两条都出现且各自标注 project/user。

**场景走查**：两处 deploy 并存 → 面板显示两条（标注 scope）→ `/deploy` 调用命中项目级 → 用户停用项目级 → `/deploy` 转而命中用户级通用版。

### R-SKL-06 CRUD

**需求背景与动机**：技能的生命周期管理（建/改/删/查）若只能手动操作文件系统，门槛高且易错（frontmatter 格式、目录规范、Windows/Linux 路径差异）；两端 UI 的同等 CRUD 让技能管理成为产品能力而非口头约定。没有它会怎样：用户每次建技能都要查格式文档，写错 frontmatter 后技能「静默无效」。

**功能规格**：

1. 统一入口：TUI /skills 面板（↑↓ 选择、Enter 查看全文、a 新建、e 编辑、t 启停、d 删除确认）与 WebUI 设置 Skills 区同等支持，走同一套 `skills_manage` 消息（action: create/update/delete/get/toggle，附 scope/name，create 带 description、update 带 content、toggle 带 enabled）。
2. 新建（create）：表单（落点 project/user、名称、描述）→ 后端生成骨架 SKILL.md（见 R-SKL-02 规格 6）；名称非法/已存在 → 抛错转 notice（channel: skills，面板内联可见）。
3. 编辑（update）：TUI 用 $EDITOR 系统编辑器（spawnSync 阻塞至退出，期间暂停 raw mode，退出后清屏重挂 Static + 重拉清单；缺省 Windows notepad、其它 vi）；WebUI 用全文编辑框（get 取全文 → update 整文件替换）。
4. 删除（delete）：整目录删除（rmSync recursive+force，含附属资源文件），幂等（不存在静默成功），带确认弹层；名单同步清理不留孤儿。
5. 查看（get）：后端回 skill_content 消息（scope/name/content 全文）→ TUI 进 info 面板（可翻页，esc 回面板）；WebUI 进编辑弹框。
6. 路径安全：CRUD 全部限定在两级根目录内（NAME_RE + assertInside 双保险）。
7. 反馈：create 成功回 notice「skill 已创建：X（scope）——正文记得用编辑器充实」；delete 成功回 notice；除 get 外每个成功操作都重播 skills_list 刷新面板。

**边界与失败模式**：

- 缺失态条目不可编辑（e 键守卫 !missing——无文件可编，「清理走 t 或 d」）。
- 运行中（gate busy）管理操作被后端阻塞并 notice「运行中，请稍候」（文件写操作与 in-flight 轮次可能竞争）。
- 编辑态名称/落点锁定（名称即身份）。

**验收标准**：

1. 当 TUI 表单提交名称为 `Code Review`，则提示名称非法且不创建（前端预校验 + 后端双拦截）。
2. 当 create 成功，则清单立即出现新条目（skills_list 重播）且默认启用。
3. 当对缺失态条目按 e，则编辑动作不触发（守卫拦截）。
4. 当删除带附属资源文件的技能，则整个目录消失（recursive 删除）。
5. 当 WebUI 编辑全文保存，则 SKILL.md 内容被整体替换为新文本。

**场景走查**：TUI /skills → a → 表单填落点=project、名称=code-review、描述=「按团队规范审查代码」→ s 创建 → e 打开 $EDITOR 写正文 → 保存 → `/code-review` 立即可用。

### R-SKL-07 启停（旁挂名单）

**需求背景与动机**：用户临时不想让某技能被模型使用（调试期、季节性任务），但不想删掉配置与文件；团队还要能把「停用有问题的技能」随仓库共享。若把启停状态写进 SKILL.md，对外部安装的文件是破坏性重写（升级即冲突）；若存内存则换会话即失忆——旁挂名单文件是唯一两全的位置。

**功能规格**：

1. 操作入口：TUI `t` 键 / WebUI 启停按钮，toggle 语义（enabled 取反）。
2. 生效面：停用 = 同时退出三个生效面——系统提示广告、斜杠联想、调用（文件保留，随时恢复）。
3. 存储：状态存旁挂名单文件——用户级 `~/.dogegg/.skills.json`、项目级 `<repo>/.dogegg/.skills.json`，形状 `{ "disabled": ["名字", ...] }`，缺省即启用；写盘时 mkdirSync 递归建目录。
4. 共享：项目级停用随 `.dogegg/` 进 git 与仓库共享。
5. 缓存：写操作同步失效清单缓存（下一轮系统提示即生效）。
6. 文案：成功后 notice 区分「已启用 / 已停用 / 已清理（移除孤儿记录）」。

**边界与失败模式**：

- 主流 SKILL.md 格式**零污染**——启停状态绝不写进 skill 文件。
- 重复停用幂等（已在名单不重复写）；启用不在名单的名字同样幂等。
- 对缺失态条目「启用」= 清理孤儿记录（notice 文案区分，避免误导为恢复了可用技能）。
- 状态文件损坏按 R-SKL-09 保守恢复。

**验收标准**：

1. 当停用技能 X，则下一轮广告段、斜杠联想、`/X` 调用三处都不再出现 X。
2. 当停用后再启用，则 X 恢复三个生效面（文件从未删除）。
3. 当对已停用的 X 再次停用，则名单文件内容不变（幂等）。
4. 当项目级停用后 git commit，则同事拉取后其面板中该技能同样呈停用态。

**场景走查**：团队发现 deploy 技能在 monorepo 下行为错误 → 在 `.dogegg/.skills.json` 停用它并提交 → 全组拉取后该技能从广告/联想/调用消失，文件仍在仓库里。

### R-SKL-08 缺失态（孤儿可见）

**需求背景与动机**：停用名单在案但目录被外部删除（手动删除/git 操作/换分支）时，名单条目若隐身，用户会困惑「我明明停用过它，怎么找不到了」；若自动清理，又会在分支切换回来自动恢复状态——都不对。可见的孤儿态是第三条路：状态可见、可手动清理、分支切回自动复活。

**功能规格**：

1. 判定：停用名单在案、但 skill 目录已被外部删除 → 条目以「文件缺失」可见（description 位显示「（目录已不存在）」，missing=true）。
2. 隔离：孤儿条目**永不进提示与调用**——广告、联想、调用都以 enabled && !missing 过滤（孤儿恒 enabled=false）。
3. 清理 = 启用该条目（t 键/按钮语义即「从名单移除」）；删除缺失条目同样等价清理（remove 幂等）。
4. 粒度：单个 skill 目录被删 → 该条目孤儿可见；整个 skills 目录被删 → 名单内全部条目可见（目录存在性检查在扫描内、孤儿枚举在扫描外，互不影响）。
5. 枚举过滤：名单里的名字不符合命名规则（外部手写坏）→ 枚举时跳过，不产生垃圾条目。

**边界与失败模式**：

- 目录整体不可读（权限）也走「无条目 + 孤儿照常枚举」路径。
- 孤儿条目不参与同名覆盖（缺失态退出竞争）。
- 孤儿路径字段是拼接出的预期路径（文件并不存在）——仅供展示，不用于读操作。

**验收标准**：

1. 当停用 hotfix 后手动删除其目录，则清单出现 hotfix 条目、标注「（目录已不存在）」且不可调用。
2. 当对孤儿条目执行「启用」，则孤儿记录从名单移除、条目从清单消失（notice 文案为「已清理」）。
3. 当切回包含该目录的分支，则技能自动恢复可用（名单记录仍在且目录回来了）。
4. 当名单里手写了一个不合规名字，则扫描不出垃圾条目。

**场景走查**：用户在 feature 分支停用了 hotfix 技能 → 切到 main（该目录不存在）→ /skills 显示 hotfix 灰显「（目录已不存在）」→ 切回 feature 分支 → 技能自动恢复可用（名单还在）。

### R-SKL-09 格式自愈与解析失败可见

**需求背景与动机**：状态文件与 SKILL.md 都是用户可手改的文件（.skills.json 是 JSON、SKILL.md 是半结构化文本），外部工具或手滑都可能弄坏。「坏一个文件拖垮整个技能系统」不可接受；「坏条目静默消失」又会让用户找不到问题——自愈必须保守、失败必须可见。

**功能规格**：

1. 状态文件容错（readDisabled 三级）：文件缺失 → 空名单；JSON 解析失败 → 空名单；形状不符（disabled 不是数组、元素非字符串）→ 过滤出字符串元素。用户删状态文件即完全重置。
2. 解析失败可见：SKILL.md 解析抛错的条目以「解析失败」条目可见——description 位显示「（SKILL.md 解析失败——请检查 frontmatter/正文）」，不隐身，便于定位修复。
3. 失败条目仍参与停用名单语义（可被停用，名单不因解析失败失效）。
4. 容错方向是「保守恢复」——宁可信一切技能可用（有权限网关兜底），不可让技能功能瘫痪。

**边界与失败模式**：

- SKILL.md 解析失败只影响该条目的 description 展示，正文仍在（调用时读到的正文可能仍是好的）。
- 状态文件形状部分损坏（数组里混入非字符串）只丢弃坏元素，好记录保留。

**验收标准**：

1. 当 `.skills.json` 被写成 `{ disabled: "deploy" }`，则下次扫描视为空名单（全部启用），无异常抛出。
2. 当 `.skills.json` 的 disabled 数组混入数字元素，则仅字符串记录生效。
3. 当某 SKILL.md frontmatter 结构损坏，则该条目在清单中显示解析失败提示，其余技能不受影响。
4. 当删除 `.skills.json`，则全部技能恢复启用（等价重置）。

**场景走查**：用户手改 `.skills.json` 时写成 `{ disabled: "deploy" }` → 下次扫描视为空名单（全部启用）→ 技能照常可用 → 用户修正文件后停用状态恢复。

### R-SKL-10 重建语义（同名新建 = 全新开始）

**需求背景与动机**：用户停用了一个技能、后来删掉目录、又想重建同名技能——如果旧的停用记录仍然生效，新建的技能会「莫名人不可见」，排查成本极高（用户很难想到去查名单文件）。创建是显式的新开始，语义必须干净。

**功能规格**：

1. 规则：create 成功后自动从停用名单移除同名记录（writeDisabled(scope, readDisabled(scope).filter(...))）——新技能默认启用。
2. 覆盖情形：从未停用直接重建（名单本无记录，filter 幂等）；外部曾产生孤儿记录（create 让孤儿记录消亡——目录回来了且不在名单）。
3. 顺序：名单移除发生在 create 成功路径（目录创建 + 骨架写入之后），与缓存失效同批。

**边界与失败模式**：

- create 在目录已存在时抛错（不覆盖既有技能——重建的前提是先删）。
- 名称非法/已存在的失败路径不碰名单。

**验收标准**：

1. 当停用 deploy → 删目录 → 重建同名，则新技能默认启用（名单中无 deploy 记录）。
2. 当名单留有孤儿记录时重建同名，则孤儿记录消失、条目呈正常启用态。
3. 当目标目录已存在时 create，则抛错转 notice「skill 已存在」且名单不变。

**场景走查**：用户停用 `deploy` → 手动删目录（名单留孤儿）→ 面板重建同名 → 创建成功且默认启用，孤儿记录被移除。

## 边界与立法

- 调用与广告的命中都在「可用条目」（enabled 且非缺失）内按项目覆盖用户优先——项目级停用时同名用户级照常生效。
- 名称校验双保险：NAME_RE + 路径越界检查（join 后必须仍在根目录内）。
- 启停与 MCP server 启停同构（toggle 消息、面板键位、UI 交互），但 skills 无运行进程——纯声明式的可用性开关。
- 内置读豁免：用户级 skills 目录在 read_file 落 ask 时自动 allow（见 05-权限与安全）——渐进披露的「模型自己读全文」依赖这一豁免才不会每次弹审批。
