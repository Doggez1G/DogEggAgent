# 10 - 配置体系与编辑器

> 职责：一个 JSON 配置文件的生命周期——schema 立法（bridge）、加载与落盘（store.ts）、内存编辑与校验回滚（editor/）、消息驱动的控制器（controller.ts）。编辑流程（/config）与运行时联动（权限/assembler/MCP 重建）都从这里出发。

## 1. 职责与边界

| 文件 | 职责 |
|---|---|
| `bridge/src/contract/config.ts` | configSchema 全字段 + 权限 v3 schema + 两条 superRefine + isConfigured |
| `agent/src/config/store.ts` | ConfigStore：定位策略、zod 加载、默认值填充、落盘 |
| `agent/src/config/editor/paths.ts` | 点号路径 → 强类型操作解析（parseConfigSet/parseConfigAdd） |
| `agent/src/config/editor/mutate.ts` | applySet/applyAdd/applyRemove 原地变更 |
| `agent/src/config/editor/validate.ts` | zod safeParse + 重名检查 + 回滚快照 |
| `agent/src/config/editor/editor.ts` | ConfigEditor 门面：lastGood 快照持有者 |
| `agent/src/config/controller.ts` | ConfigController：config_* 消息实现归属 + edit 统一链路 |
| `agent/src/agent.ts` | onConfigChanged 运行时联动（:333-343） |
| `bin/dogegg.ts` | loadConfigOrExit 加载失败路径（:20-39） |

依赖矩阵中 config 域只依赖 ROOT（architecture.test.ts:131）——schema 的权威在 bridge，agent 域只有读写与编辑。

## 2. 核心数据结构：configSchema 全字段（bridge/src/contract/config.ts:114-142）

| 字段 | 类型/默认 | 说明 |
|---|---|---|
| `systemPrompt` | string?, 可选 | 自定义系统提示词路径/文本（缺省内置，agent.ts:455 判断） |
| `defaultProvider` / `defaultModel` | string?, 可选 | 缺省时 store.load 补第一个（store.ts:44-49） |
| `maxIterations` | int, 默认 -1 | 对话最大轮次：**-1 = 无限**（靠取消/错误终止）；正整数 = 上限（无人值守批处理）；**0 非法**（config.ts:119 的 refine） |
| `maxRetries` | int≥0, 默认 3 | LLM 请求重试次数（《03》§3.4） |
| `shellProgram` | string?, 可选 | shell 解释器（缺省平台默认；非法值被 resolveShell 回退，《05》§3.4） |
| `permission` | permissionSchema, 默认出厂 | 三桶 v3 结构化（见下） |
| `mcpServers` | mcpServerSchema[], 默认 [] | 全局 MCP 服务列表（transport stdio/http 判别联合，:25-42） |
| `providers` | providerSchema[], 默认 [] | provider = { name, protocol:'openai', baseURL, apiKey, models[] }；model = { name, contextWindow=128000, maxOutput=16384, reasoning=false }（:7-20） |

**出厂默认权限**（config.ts:125-138）：读类工具（read_file/ls/glob/grep）整工具 allow；写类与 shell（write_file/edit_file/shell）整工具 ask——**仅对"配置文件未写 permission 字段"的加载生效**（schema default 语义）；用户显式配置的三桶整体覆盖不合并（:123-124 立法）。

**校验宽松/严格的分界**（config.ts:3-5 注释）：模型/提供商字段刻意放宽（name/baseURL/apiKey/models 允许暂空）——支持 /config 里"自由创建节点、逐字段填写"的编辑流程；能否真正对话由 `isConfigured()`（:169-175：存在完整 provider 且默认模型可解析）判定，而非 schema 强制非空。**权限模式严格**：两条 superRefine（作用域锚点 + 服务键前缀，见《06》§3.7）fail-closed。

## 3. 关键流程走查

### 3.1 加载路径（store.ts:34-51）

1. **定位策略**（findConfig，:8-14）：项目内 `.dogegg.json` 优先，否则 `~/.dogegg/config.json`，都没有返回 null——路径策略是模块私有，外部只经 ConfigStore 存取（:7 注释）；
2. 找不到文件 → `data = {}` → zod parse 后得到**空配置**（providers 为空）——程序能启动、引导用户去 /config（:33 注释）；不主动创建文件；
3. `configSchema.parse(data)`（:42）——zod 填默认值；**校验失败即抛**（ZodError 上抛给调用方）；
4. 仅存在 provider 时补默认 provider/model（:44-49）；空配置保持无默认值；
5. `sourcePath()`（:28-30）暴露加载源——启动报错指明"该改哪个文件"（bin/dogegg.ts:25 使用）。

### 3.2 加载失败路径（bin/dogegg.ts:20-39 的 loadConfigOrExit）

1. catch ZodError → issues 逐条拼 `path.join('.')：message`（bin/dogegg.ts:26-27）——错误信息带配置内路径，可直接定位；
2. 输出四要素（:29-36）：待修文件（sourcePath 或"未找到"）、逐字段原因、恢复方式（"把上述字段改写为当前格式 { whole, patterns }；或整段删除 permission 字段回退出厂默认"）、格式文档位置（本地实际存在的路径优先，在线文档可能尚未发布）；
3. `process.exit(1)`。**不覆写文件**——损坏配置的原样保留是排障前提。

### 3.2.1 加载失败的输出示例

`loadConfigOrExit` 对一个含旧格式 permission 的配置的输出形态（bin/dogegg.ts:29-36）：

```
配置加载失败（文件：/home/u/.dogegg/config.json）：permission：Invalid input
恢复方式：把上述字段改写为当前格式 { "whole": boolean, "patterns": string[] }；或整段删除 "permission" 字段回退出厂默认，再经 /config 重新配置。
配置格式说明：/usr/lib/node_modules/dogegg/docs/versions/0.2/03-用户手册/01-配置指南.md
```

四要素齐备：**待修文件**（sourcePath() 或"未找到"——用户可能不知道是哪个文件在生效）、**逐字段原因**（ZodError 的 path.join('.') 前缀）、**两条恢复方式**（改格式或删字段回出厂默认）、**文档路径**（import.meta.dirname 相对 → cwd 相对 → 在线文档兜底，`existsSync` 找到第一个真实存在的，:31-36——"本地实际存在的路径优先——在线文档可能尚未发布"）。

### 3.3 编辑器强类型操作解析（editor/paths.ts）

UI 编辑不直接改 JSON，而是发 `config_set/config_add/config_remove` 上行消息，路径文法（paths.ts:24-28 立法）：

```
'defaultProvider' | 'defaultModel' | 'maxIterations' | 'maxRetries' | 'systemPrompt' | 'shellProgram'
'permission.allow' | 'permission.reject' | 'permission.ask'
'providers.<index>.<field>'            field ∈ { name, baseURL, apiKey, protocol }
'providers.<i>.models.<j>.<field>'     field ∈ { name, contextWindow, maxOutput, reasoning }
```

`parseConfigSet`（paths.ts:51-81）按段数四分支解析为 `ConfigSetOp` **判别联合**（:30-34）——取代旧代码手写 split 梯子（:29 注释）。每个分支做三件事：段数/字段名白名单校验（非法返回 null）、index 数字校验、值容错归一（asString/asNumber/asBoolean，:4-6——运行时类型检查替代 as 断言，避免错误类型的值静默通过）。

**permission 是整桶替换原语**（:59-62）：`permission.<bucket>` 的值 = 键 → `{whole, patterns}` 对象**整体替换**（asBucketRules 逐键过滤非字符串模式、形状非法键丢弃——fail-closed 防御手写消息，:10-22）。UI 重算整桶对象提交，天然原子——无需 item 级增删改消息。

`parseConfigAdd`（:88-97）：`providers` 追加 provider、`providers.<i>.models` 追加 model。`applyRemove`（mutate.ts:42-48）只允许 providers/models 两路径。`applySet/applyAdd`（mutate.ts:5-39）：越界 index **静默跳过**（不抛错，:4 注释）——竞态删除后迟到的编辑不炸。

### 3.3.1 一次 set 的完整解析走查

以 `config_set { path: 'providers.0.models.1.reasoning', value: true }` 为例：

1. `path.split('.')` → `['providers','0','models','1','reasoning']`（5 段）；
2. 命中第四分支（paths.ts:73-79）：`seg[0]==='providers' && seg[2]==='models'`；`pi=0, mi=1` 都是合法非负整数；`field='reasoning'` 在 MODEL_FIELDS 白名单内；
3. field 是 reasoning → 值按 asBoolean 归一 → 产出 `{ kind:'model', providerIndex:0, modelIndex:1, field:'reasoning', value:true }`；
4. `applySet`（mutate.ts:23-28）：定位 `providers[0].models[1]`——越界则静默跳过；写入后进入 afterEdit；
5. `validateConfig`：configSchema.safeParse——若上一步误传字符串 `"true"`，asBoolean 归一为 true 已挡一层；若 contextWindow 被设为 -3，zod 的 `.positive()` 在此拒绝 → 回滚 lastGood + notice"配置校验失败，已回滚：Number must be greater than 0"。

再看 `config_set { path: 'permission.ask', value: {...} }`：两段命中 permission 分支（paths.ts:60-64）→ `asBucketRules` 逐键归一（`{whole: 'yes'}` 这种手写坏值 → whole=false 的安全侧；patterns 含非字符串元素被过滤）→ **整桶替换** `config.permission.ask` → afterEdit 的 safeParse 会再跑两条 superRefine（作用域锚点 + 服务键前缀）——UI 层造出的非法模式在此被拒并回滚。

### 3.4 校验 + 回滚（editor/validate.ts + editor.ts）

`ConfigEditor` 持有 `config` + `lastGood`（最后合法快照，构造时 structuredClone，editor.ts:10-14）。每次 set/add/remove 后走 `afterEdit`（:47-56）：

1. `validateConfig`（validate.ts:24-34）：`configSchema.safeParse` 失败 → `{ ok:false, config: lastGood, error: '配置校验失败，已回滚：' + 首条 issue }`；`findDuplicateName`（:4-20，仅非空名判重——**编辑期的新空节点允许多个共存**，:3 注释）发现重名 → 同样回滚；
2. 成功 → config 更新为 parse 后结果（并入默认值）、lastGood 更新为克隆快照（editor.ts:52-55）；
3. 失败 → `this.config = structuredClone(result.config)` 回滚到 lastGood（:50）。

**不变量：内存配置永远处于合法状态**——非法值在编辑当下即被拒绝并回滚，落盘的永远是 parse 过的形状。

### 3.5 控制器统一链路（controller.ts:40-51）

`edit(fn)` 是所有编辑的统一入口，五步：gate.busy 则 notice 阻塞（:41，编辑运行中阻塞）→ 执行编辑（editor 返回 ok/error）→ 失败 emit notice（含回滚原因）→ 成功则 `onConfigChanged(config)`（运行时联动）→ `configs.save(config)` 落盘 → emit `config_updated`（:47-50）。`replaceMcpServers`（:35-37）是 /mcp 面板全局写入的整组替换原语——不走点号路径文法（数组结构由 zod 整体校验），但共用同一条链路（gate/校验/落盘/广播/联动，:33-34 注释）。

### 3.6 运行时联动（agent.ts:333-343 的 onConfigChanged）

配置编辑成功后整体替换 ctx 中可变的三个成员：

1. `ctx.config = config`；
2. **PermissionManager 重建 + 授权保留**：`snapshotPermissions()` → new → `restore(saved)`（:335-337）——配置三桶生效、会话提升不丢；
3. **ContextAssembler 重建**（:338）——新 systemPrompt 路径生效（组装函数闭包现取 skills/shell 引导）；
4. `rebuildMcp()`（:340）——mcpServers 可能变化，diff 重建幂等空转不广播（《07》§3.2）；
5. `isConfigured` 则 emitStatusState（:342）——provider/model 变更即时推送状态栏，不等下一轮状态机变化（:341 注释）。

## 4. 关键立法与不变量

- **INV-1 不兼容演进原则（ADR-0013）**：配置格式不做旧版兼容——schema 只接受当前版本；格式不符加载报错（人话 + 文档指引 + 退出）。**格式即版本**：无版本号字段、无迁移机器；格式演进 = 一次性人工迁移（错误信息给出迁移指引）。
- **INV-2 内存配置永远合法**：一切编辑过 zod safeParse，失败即回滚 lastGood。
- **INV-3 permission 整桶原子**：桶级替换原语，无部分更新状态。
- **INV-4 出厂默认只补缺**：permission default 仅在字段整体缺失时生效；显式配置整体覆盖。
- **INV-5 宽严分界**：编辑流字段放宽（isConfigured 判完整性）；安全相关严格（权限两条 superRefine、maxIterations 拒 0）。
- **INV-6 编辑运行中阻塞**：gate.busy 时 set/add/remove 一律 notice（controller.ts:41）。
- **INV-7 落盘路径策略**：save 目标 = 已存在的配置文件优先（项目 .dogegg.json 优先于用户级），都没有则落到 `~/.dogegg/config.json`（store.ts:16-19）——"在项目里配置的项目用，全局配置全局用"的空间语义自然成立。
- **INV-8 测试隔离警示**：ConfigStore 构造器的 defaultPath 是落盘测试接缝，"凡会触发配置保存的测试必须注入临时路径，否则会用测试数据覆写用户真实配置"（store.ts:23-25 的 ⚠️ 注释立法）。
- **INV-9 config_updated 是运行时联动的唯一信号**：编辑器成功必 emit（controller.ts:50）——onConfigChanged 的 permission/assembler/MCP 重建与两端 UI 刷新都挂在这一条消息上，无旁路写入口。

## 5. 失败模式与恢复

| 失败 | 行为 | 恢复 |
|---|---|---|
| 配置文件 JSON 损坏 | load 抛错 → loadConfigOrExit 人话报错 + exit(1)，不覆写 | 按提示修文件或删字段回默认 |
| zod 校验失败（含旧格式） | 同上；issue 带配置内路径 | "整段删除回退出厂默认，再经 /config 重配" |
| 编辑值非法（如 permission 模式无锚点） | afterEdit 回滚 lastGood + notice 显示首条 issue（validate.ts:27） | UI 修正后重提交；配置保持上一个合法态 |
| provider/model 重名 | 重名检查回滚（validate.ts:29-32）；空名节点不判重 | 改名保存 |
| 无效点号路径 | parse 返回 null → notice"无效的配置路径"（editor.ts:22） | UI 侧修正 |
| 越界 index 编辑 | applySet 静默跳过（mutate.ts:19, 25） | 无需恢复（竞态容忍） |
| 落盘失败 | save 抛错 → edit 链路外未捕获？——save 在 onConfigChanged 之后（controller.ts:49），异常被 agent.send 的 catch 吞（agent.ts:117） | 内存与广播已完成；下次编辑重写 |
| 测试覆写真实配置 | ConfigStore 构造注入 defaultPath 接缝（store.ts:23-25 警示注释） | 测试规范约束 |

## 6. 与其它子系统的接缝

- **→ 02 轮次**：TurnParams 每轮从 config 现解析（maxIterations/maxRetries/shellProgram/reasoning/windowTokens）。
- **→ 03 LLM**：provider 连接参数与 model 参数的唯一来源。
- **→ 06 权限**：permission 三桶 + 两条 superRefine（详见《06》§3.7）；onConfigChanged 的 snapshot/restore 保留提升。
- **→ 07 MCP**：mcpServers 字段 + replaceMcpServers 原语 + rebuild 联动。
- **→ 11/12 前端**：config_state/config_updated 消息 + config_set/add/remove 消息是两端 /config 面板与设置区的全部通道（TUI features/config 的 buildEntries 双端共用，见《11》§3.4）。
