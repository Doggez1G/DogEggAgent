# 02 - 对话轮次引擎

> 职责：把"用户说一句话"变成"一轮完整的 agentic 对话"——驱动 LLM 调用、工具执行、权限审批、上下文压缩、取消与收尾落盘。核心编排住 `agent/src/turn/`，门面装配在 `agent/src/agent.ts`。

## 1. 职责与边界

`turn/` 域的文件分工（依赖矩阵允许 turn 依赖 session/llm/tools/context/permission/shared/ROOT，见 bridge/test/architecture.test.ts:128-139）：

| 文件 | 职责 |
|---|---|
| `agent/src/turn/turn-runner.ts` | 三命令实现归属：submit / cancel / compact；R2 阻塞语义与落盘 |
| `agent/src/turn/loop.ts` | AgentLoop：问模型 → 执行工具 → 回填 → 再问的主循环 |
| `agent/src/turn/state.ts` | TransitionInput + 迁移表 + StateMachine（10 态） |
| `agent/src/turn/tool-executor.ts` | 单个 tool_call 的完整流程（解析 → 权限 → 执行/拒绝 → 回填） |
| `agent/src/turn/compactor.ts` | 压缩编排器（loop 自动 + 手动 /compact 共用入口） |
| `agent/src/turn/summarize.ts` | 摘要提示词与离线总结调用 |
| `agent/src/turn/pending.ts` | 挂起中的权限请求（Promise 注册表） |
| `agent/src/turn/title.ts` | 自动标题生成 |
| `agent/src/turn/types.ts` | LoopServices / TurnInput / LoopResult 契约 |

**R1/R2/R3 三条内建立法**（散布在代码注释中，是本域设计的骨架）：

- **R1 双写分离**：`history`（完整原文，UI 显示与持久化用）与 `context`（发给模型的消息，可压缩）分开持有（agent/src/session/conversation.ts:24）；loop 只操作 context，本轮新增消息收集进 `newMessages` 由 core 同步 append 到 history（agent/src/turn/loop.ts:13-15）。压缩只换 context，history 永不回缩。
- **R2 并发闸门**：同一时刻只允许一个"动 context"的操作（轮次或手动压缩）在飞（agent/src/shared/gate.ts:2）；运行中动工作集的命令发 notice 阻塞，纯查询放行（agent/src/agent.ts:345 注释）。
- **R3 可见失败**：拒绝（reject 桶 / 用户 reject）、未知工具、参数校验失败也发 tool_end（带 error 标记），不静默塞消息（agent/src/turn/tool-executor.ts:20-21）。

## 2. 核心数据结构

### 2.1 状态机：10 态 + 15 种迁移输入（agent/src/turn/state.ts）

State 十态定义在 bridge（bridge/src/contract/shared.ts:8-18）：`idle / thinking / responding / tool_calling / waiting_permission / executing / finished / cancelled / error / compacting`。

迁移输入 `TransitionInput` 共 15 种 kind（state.ts:7-22）：`submit / thought_done / final_answer / tool_calls / tool_auto / tool_needs_permission / allow / tool_done / reject / result_back / compact_start / compact_done / cancel / error / reset`。

**全转移表**（state.ts:53-75 的 `transition` 纯函数 + VALID_FROM 白名单 :27-43）：

| input | 合法来源态（VALID_FROM） | 目标态 |
|---|---|---|
| `submit{reasoning}` | idle, finished, cancelled, error | reasoning → thinking / 否则 responding |
| `thought_done` | thinking | responding |
| `final_answer` | responding | finished |
| `tool_calls` | responding, thinking | tool_calling |
| `tool_auto` | tool_calling | executing |
| `tool_needs_permission` | tool_calling | waiting_permission |
| `allow` | waiting_permission | executing |
| `tool_done` | executing, waiting_permission | tool_calling（还有下一个工具） |
| `reject{reasoning}` | executing, waiting_permission, tool_calling | reasoning → thinking / 否则 responding |
| `result_back{reasoning}` | executing | reasoning → thinking / 否则 responding |
| `compact_start` | thinking, responding, idle, tool_calling, executing, waiting_permission | compacting |
| `compact_done{next}` | compacting | 指定态（loop 自动回 thinking/responding；手动回 idle） |
| `cancel` | thinking, responding, tool_calling, waiting_permission, executing, compacting | cancelled |
| `error` | 同上六态 | error |
| `reset` | finished, cancelled, error, idle, compacting | idle |

关键机制：`transition` 先查 VALID_FROM，**(input, from) 非法组合返回当前态不迁移**（state.ts:55-56）——对逻辑错误的防护性立法。`reject/result_back` 携带 reasoning 参数，因为"重新请求模型"与 submit 一样受推理模型影响（state.ts:47-48 注释）。全项目**唯一**状态机实例住 `ctx.machine`；loop 在轮内 fire（loop.ts:42-47 的 `trans` 闭包），门面 emitState 在轮外 fire（agent/src/agent.ts:122-133），无双机镜像（state.ts:78-79 注释）。

### 2.2 轮次参数与结果（turn/types.ts、turn-runner.ts）

- `TurnParams`（turn-runner.ts:15-22）：`client / model / maxOutput / maxRetries / reasoning / windowTokens`——门面在**命令时刻**从 config 解析成值传入，控制器不持探针回指门面内脏（所有权立法，turn-runner.ts:14 注释）。
- `TurnInput`（types.ts:28-43）：TurnParams + `systemPrompt / context / permission / maxIterations / cwd / shellProgram / signal`。
- `LoopResult`（types.ts:48-61）：`context`（可能已压缩）、`newMessages`、`thinking[]`、`usage`（轮内多次调用累加的真实用量）、`compactions`（本轮自动压缩次数）、`cancelled?`、`error?`。

## 3. 关键流程走查

### 3.1 submit 一轮的完整编排（TurnRunner.runTurn，turn-runner.ts:94-134）

1. `ctx.gate.enter()`（:95）——置 running=true、清取消标志、new AbortController 返回（gate.ts:20-25）；
2. `conversation.pushUserMessage(text)`（:96）——R1 双写：同一消息对象进 history 与 context（conversation.ts:65-69）；`emit message user`（:97）；
3. 组装 TurnInput 调 `loop.run(...)`（:99-113）——context 是 `conversation.getContext()` 的引用，loop 原地修改；
4. loop 返回后 `conversation.applyTurnResult(result)`（:117）——context 整体替换（可能已压缩）、newMessages append 进 history、thinking 累积、usage 累计并记 lastTurn、compactions 累加（conversation.ts:73-84）；
5. `result.cancelled` → emit notice"已打断"（:118-119）；`result.error` → emitState error + emit error 消息（:120-122）；
6. finally（:128-133）：`gate.leave()` + `emitState({kind:'reset'})` 复位 idle + `saveOrNotice()` 落盘（保存失败发 notice"会话保存失败"，不静默，:185-197）；
7. 成功结束后台生成标题：`void this.maybeAutoTitle(params)`（:42，fire-and-forget 不阻塞下一轮提交）。

### 3.2 AgentLoop 主循环（loop.ts:22-211）

1. 拷贝 context、初始化 `newMessages` / `turnUsage` / `turnCompactions`，**每轮新建 ToolExecutor**（permission 是轮次参数——config 编辑重建的实例下一轮生效，loop.ts:31-37）；
2. `trans({kind:'submit', reasoning})` 进 thinking/responding（:82）；
3. **无限 for(;;)**，每次迭代头部：`checkCancelled()` 为真 → trans cancel + 抛 CancelledError（:85-88）；`maxIterations >= 0 && iterations++ >= maxIterations` → error（-1 = 无限，bridge/src/contract/config.ts:119 立法，loop.ts:90-93）；
4. **压缩检查**：`estimateContextTokens(systemPrompt, context, registry.schemas())`（:99），超过 `windowTokens * COMPACTION_THRESHOLD(0.8)` → trans compact_start → `compactor.compact(...)` → 成功则 `context.length = 0; context.push(...result.context)` 原地替换 + emit compaction source='auto'（:100-115）→ trans compact_done 回 thinking/responding；
5. `turn.client.chat({...}, turn.signal, onEvent)`（:121-143）——onEvent 分发 LlmStreamEvent：`text_delta`（若在 thinking 则先 thought_done 转 responding）发 text_delta；`thought_delta`（reasoning 开启时）发 thought_delta；`tool_call_start` 发 tool_pending（大参数流式生成期间的可见反馈，:138-141）；
6. chat 抛 AbortError → 视为取消（trans cancel + CancelledError），其余异常 → trans error 上抛（:144-152）；`result.usage` 累加进 turnUsage（:154-157）；
7. push thinking 条目（与 assistant 消息一一对应；reasoning 关闭时存空字符串，重建显示时跳过，:159-163）；assistant 消息 push 进 context + newMessages + emit message（:168-170）；
8. `tool_calls` 为空 → trans final_answer → emit finished（带 turnUsage）→ **return**（:172-177）；
9. 否则 trans tool_calls 后**串行**执行每个 call（:183-200）：每个工具前再查取消；`executor.execute(call, {cwd, signal, shellProgram}, {isLast, reasoning}, trans)` 返回 ToolStep——toolMessage push 进 context + newMessages、trans(step.transitionInput)。

### 3.3 单工具执行（ToolExecutor.execute，tool-executor.ts:33-94）

1. **未知工具**：registry.get 查不到 → emit tool_end（error="未知工具 X"）→ 回填 tool 消息 → 迁移 `rejectOrDone()`（isLast ? reject : tool_done，:39 与 :43-48）；
2. **参数校验**：`tool.schema.parse(JSON.parse(call.function.arguments || '{}'))` 失败 → tool_end + 回填"参数校验失败"（:51-58）；
3. **权限判定**：`permission.classify(tool.name, args, ctx.cwd)`（:62）——cwd 用于路径归一化（详见《06》）；
4. **reject 桶**：emit tool_end denied → 回填 deniedMessage（明确告诉模型"请勿再次尝试同一工具"，防止权限请求死循环，:64-72）；
5. **ask 桶**：trans tool_needs_permission → `await requestPermission(tool, args)` 挂起等待（Promise 由 PendingPermissions 登记）→ `permission.apply(tool, decision, scopePattern, cwd)` 提升落库 → reject 同 reject 桶；allow_once/allow_always 则 trans allow → runAndEmit（:74-88）；
6. **allow 桶**：trans tool_auto → runAndEmit（:90-93）；
7. `runAndEmit`（:99-117）：emit tool_start → `tool.execute(args, ctx)`（try/catch 兜底，保证 tool_start 总有配对 tool_end）→ `truncate(result.content)`（8000 字符上限，agent/src/context/truncate.ts:3-8）→ emit tool_end → 返回 tool 消息。

### 3.4 压缩管线全流程（机制原理逐段）

**① 估算函数怎么算**：`estimateTokens`（agent/src/context/token/estimate.ts:3-7）——CJK 字符（正则 `[一-鿿]`）每字 1 token、其余 4 字符 ≈ 1 token 的粗估；不引 tokenizer，精度需求不高（estimate.ts:2 注释）。`estimateContextTokens` 把 systemPrompt + 全部 context 消息 + 工具 schema JSON 串起来求和。

**② 触发判定**：`shouldCompact(used, windowTokens)` = `used > windowTokens * 0.8`（agent/src/context/compaction/trigger.ts:4-6）。阈值 0.8 是常量 `COMPACTION_THRESHOLD`，住在 bridge contract/shared.ts:6——后端触发与前端进度条过载变色共用同一常量，防两端漂移（shared.ts:4-5 立法注释）。定 80% 而非 100% 是留缓冲，避免模型正要回答时才触发压缩打断（trigger.ts:3 注释）。

**③ 摘要提示词五要素**（agent/src/turn/summarize.ts:8-19 的 HANDOVER_PROMPT）：摘要被设计为"任务交接文档"而非缩写——它是新上下文的**唯一**内容（compactor.ts:24-25 注释）。提示词强制逐项保留：1) 当前任务目标与用户核心诉求；2) 已完成步骤与结果；3) 文件路径与关键代码位置；4) 重要决策及理由；5) 未完成事项与下一步计划；6) 用户偏好与约束。另附两条输出纪律：中文结构化条目；长度与信息密度匹配（寒暄一两句即可，不许为凑类别展开）。`maxOutput: 2000`（summarize.ts:37）——1000 会截断长任务的交接信息。

**④ 调用形态**：`summarizeHistory`（summarize.ts:25-43）是"离线"单次 chat——不进 agent loop、不发 stream 事件、tools 传空、maxRetries 1；signal 接收外部 signal 让取消能中断摘要调用（summarize.ts:24 注释：非无人持有的 new AbortController）。summarize 回调闭合在 agent.ts:310-315——调用时读当前 config 解析 provider/model，配置热切换后自动生效。

**⑤ 产出如何替换 context**（compactor.ts:41-66）：`context = [{ role: 'user', content: SUMMARY_HEADER + '\n' + summary }]`（:57；SUMMARY_HEADER = '[对话已压缩——以下是此前上下文的结构化摘要]'，:16）。**无保留尾巴**（keep=N 已废——切缝会拆散 tool_calls/tool 配对）、无淘汰、无硬丢弃（:23-25 注释）；下次压缩对 [摘要 + 新对话] 重新完整总结，无叠加劣化。

**⑥ history 为何不动**：history 是 UI 显示与持久化的完整原文，压缩是"给模型看的信息管理"而非"删记录"——resume 后用户仍能看到全部对话，模型只看到摘要 + 后续对话。这是 R1 立法的直接推论（compactor.ts:19-20）。

**⑦ 非劣原则**：压缩产出 token ≥ 原文时按未压缩返回（compactor.ts:62-64）——简短对话的交接文档可能比原文还长（结构化提示词鼓励逐项展开），此时压缩没有意义；主要保护手动 /compact 小 context 场景（自动路径 80% 触发时 context 已很大，摘要必然更短）。

**⑧ 失败语义（诚实失败）**：summarize 抛错或返回空摘要 → 异常上抛（空摘要 throw '压缩摘要为空'，compactor.ts:53-56），调用方按错误收尾，**不做降级**——由用户决定 /compact 重试或 /new（compactor.ts:27-28 立法注释）。手动压缩中的取消走 AbortError → cancelled 态而非 error（turn-runner.ts:167-175）。

### 3.5 手动压缩（/compact，turn-runner.ts:140-182）

1. gate.enter 占闸（防压缩期间 submit 并发写 context）→ trans compact_start（:141-142）；
2. `compactor.compact({... force: true, signal})`（:144-151）——force 跳过阈值检查无条件执行（compactor.ts:30, 48）；
3. compacted → `replaceContext` + `incrementCompaction()`（手动压缩的计数入口，自动的走 LoopResult.compactions，:152-162）→ 落盘 → emit compaction source='manual'；未压缩 → notice"当前上下文无需压缩"（:164-166）；
4. finally：还在 compacting 用 compact_done 回 idle，已 cancelled/error 用 reset 回 idle（compact_done 的 VALID_FROM 不含 cancelled/error，:176-181）。

### 3.6 取消传播（双机制，gate.ts:4-9 立法）

1. 用户发 `cancel` → agent.ts:391-392：`ctx.gate.cancel()` + `pending.rejectAll(new CancelledError())`（挂起中的权限请求全部以 CancelledError 拒绝，tool-executor 的 await 立即抛出）；
2. **协作检查点**：loop 在每次迭代头部（loop.ts:85）与每个工具执行前（loop.ts:186）轮询 `checkCancelled()`——保证"取消后逻辑一致"（返回部分结果、补全未配对 tool_calls）；
3. **在飞中断**：`gate.enter()` 返回的 AbortController.signal 随 TurnInput 传给 `client.chat`（loop.ts:130）、工具 ctx（loop.ts:193）与 compactor——挂起的 fetch / 工具 / 压缩立即以 AbortError 失败（gate.ts:6-8）；AbortError 在 loop.ts:146-149 统一转 CancelledError。对 shell 工具，signal 进一步传播到子进程树终止（kill-tree，详见《05》）；
4. catch 块（loop.ts:202-210）：`patchUnpairedToolCalls(context)`（:54-78）向后扫描最后一条带 tool_calls 的 assistant 消息，为每个未配对 tool_call_id 补 `tool: 'cancelled（用户打断了操作）'` 消息——OpenAI API 要求每个 tool_call 必须有配对 tool 消息否则 400（:51-53 注释：多工具批量时 tool1 完成、tool2 被取消，尾部是 tool1_result，只查尾部会漏）；
5. 返回部分结果 `cancelled: true`——已完成的 assistant/tool 消息不丢（:206-207）。

### 3.7 自动标题（turn-runner.ts:48-82 + title.ts）

1. 前置条件四查（:49-56）：titleGenerating in-flight 去重、已有标题跳过、gate 空闲、首轮需同时存在 user + assistant 消息；
2. `generateTitle`（title.ts:12-42）：TITLE_PROMPT 立法"只输出标题本身，≤32 字、不加引号前后缀"（title.ts:5）；输入取首条 user/assistant 消息各前 500 字符；maxOutput 512（给 64 会被推理模型的思考烧光导致 content 为空 → 静默失败，title.ts:9-10 注释）；失败/空结果返回 null（标题是装饰，静默跳过）；
3. 清洗：取首行、剥引号、截 32 字（title.ts:36-37）；
4. 写回前**再查一次标题**——生成期间 /rename 手动命名可能已落（竞态窗口），手动命名优先、自动结果直接丢弃（turn-runner.ts:47, 65）；写回后落盘 + notice + session_list 广播（:66-77）。

## 4. 关键立法与不变量

- **INV-1**：history 单调增长，永不因压缩回缩（R1）；context 可被压缩替换。
- **INV-2**：context 中每条 assistant.tool_call 的 id 必有配对 tool 消息（patchUnpairedToolCalls 保证）——OpenAI 线格式（shared.ts:46-50）可回放的前提。
- **INV-3**：同一时刻至多一个 gate.enter() 区间（R2）；轮次与手动压缩共用闸门。
- **INV-4**：tool_start 与 tool_end 一一配对（runAndEmit 的 try/catch 兜底）。
- **INV-5**：状态机迁移必须过 VALID_FROM 白名单，非法组合原地不动（防非法状态序列）。
- **INV-6**：压缩产出必须非空且严格小于原文（非劣原则），否则视为未压缩。
- **INV-7**：thinking 条目与 assistant 消息一一对应（空串占位），保证 resume 重建显示时索引对齐。

## 5. 失败模式与恢复

| 失败 | 语义 | 恢复 |
|---|---|---|
| LLM API 失败（chat 抛错） | trans error → LoopResult.error → emit error 消息 | 已完成的 assistant/tool 消息保留（loop.ts:202-210）；用户重新 submit |
| 达到 maxIterations | 同 error 路径（loop.ts:90-93） | 调大 config.maxIterations 或设 -1 |
| 用户取消 | AbortError→CancelledError，补全未配对 tool_calls，cancelled: true | context 完整可继续；下一轮 submit 正常 |
| 权限请求中取消 | PendingPermissions.rejectAll 让 await 抛出（agent.ts:392） | 挂起项清理干净，无 Promise 泄漏 |
| 压缩摘要为空 / LLM 失败 | 异常上抛 = 轮次 error，不降级（诚实失败） | /compact 重试或 /new |
| 工具抛异常 | runAndEmit try/catch → tool_end 带 error → 错误文本回填给模型 | 模型看到错误改换路径 |
| 落盘失败 | saveOrNotice 发 notice（turn-runner.ts:194-196） | 用户感知而非静默丢会话 |
| loop 内意外异常 | runTurn 兜底 catch（:124-127，理论上 loop 已 catch 全部） | error 态 + reset 复位 |
| 标题生成失败/竞态 | 返回 null 或写回前发现已有标题 → 丢弃 | 会话继续用 preview 或手动 /rename |

## 6. 与其它子系统的接缝

- **→ 03 LLM**：loop 消费 `LlmClient.chat` 的流式回调（LlmStreamEvent 三类），见《03》。
- **→ 04/05 工具**：`registry.schemas()` 每次请求模型时现取（loop.ts:126）——MCP 工具动态增减即时生效；工具实现见《05》。
- **→ 06 权限**：ask 桶 → requestPermission 挂起 → PendingPermissions → UI 决议 → apply 提升落库，完整链路见《06》。
- **→ 09 会话**：applyTurnResult / snapshotFull / load 是 Conversation 与 SessionStore 的交接面，见《09》。
- **← 10 配置**：TurnParams 每轮从 config 现解析（agent.ts:318-329），config_updated 重建 assembler/permission 后下一轮生效。
