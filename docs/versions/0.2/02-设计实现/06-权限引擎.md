# 06 - 权限引擎

> 职责：对每一次工具调用 `(tool, args)` 求值出 `allow / reject / ask` 三值判定。引擎分两层：**配置三桶的纯派生判断**（`bridge/src/contract/permission.ts`——无状态无 IO，agent 运行时与两端 UI 共用同一实现）+ **运行时会话提升**（`agent/src/permission/manager.ts`——会话内 allow_always 的登记/撤销/恢复）。
>
> **交互图**：[权限判定全流程](./assets/permission-decision.html)（classify → ask → 四档决议 → 提升/撤销的完整回路）。

## 1. 职责与边界

| 文件 | 职责 |
|---|---|
| `bridge/src/contract/permission.ts` | classifyPermission 纯派生 + toolEntryMatches 双分支 + mcpServerHit + sessionHit |
| `bridge/src/contract/config.ts` | permissionSchema（v3 结构化三桶）、PRIMARY_SPECIFIER 主参数表、加载期两条 superRefine |
| `agent/src/permission/manager.ts` | PermissionManager：classify 前归一化、apply/restore/revoke 会话提升、内置读豁免 |
| `agent/src/permission/derive.ts` | deriveAlwaysScope：批准时推导"最窄可复用范围" |
| `agent/src/turn/tool-executor.ts` | 判定结果的三分支执行（reject / ask 挂起 / allow 直通） |
| `agent/src/turn/pending.ts` | 挂起权限请求的 Promise 注册表 |

数据形态（v3 结构化，ADR-0012/0013）：`config.json` 的书写格式 = 内存形态 = 匹配引擎输入，三层同构（config.ts:47-51 注释）：

```ts
// 三桶 = 键 → { whole, patterns }（config.ts:59-62 bucketRuleSchema）
allow/reject/ask: Record<键, { whole: boolean, patterns: string[] }>
// whole: true  → 整键命中（patterns 仅作取消整选时的恢复内容，不参与匹配）
// whole: false → patterns 生效（OR）；空数组 = 键存在但不命中（编辑中空选态）
```

## 2. 核心数据结构与配置形态

- **桶键**：内建工具名（`read_file`…）或 MCP 服务键 `mcp:<服务裸名>`——前缀使服务键与内建键的键空间彻底正交（内建名不含冒号），"这个键是不是服务键"由语法自明（permission.ts:34-35 立法注释）。
- **主参数表**（config.ts:67-76）：`PRIMARY_SPECIFIER = { shell: 'command' }`，其余默认 `'path'`——`whole=false` 时模式字符串对应工具的哪个参数由它统一裁决，三端共享同一解释；`BUILTIN_PATH_TOOLS = ['read_file','write_file','edit_file','ls','glob','grep']`（config.ts:72）界定"patterns 是路径模式"的键集合（作用域校验只对这些键生效）。
- **会话提升形态**（shared.ts:26-29）：`ToolPermission { tool, patterns }` 按 工具 分组——patterns 空 = 整工具提升；非空 = 范围模式列表（运行时内存结构，不受配置"空选 = 不命中"立法影响，permission.ts:28-29 注释）。

## 3. 关键流程走查

### 3.1 classifyPermission 逐桶求值（bridge/src/contract/permission.ts:42-58）

```ts
const hit = (bucket) =>
  Object.entries(cfg[bucket]).some(([ruleTool, rule]) => toolEntryMatches(ruleTool, rule, tool, args)) ||
  mcpServerHit(cfg[bucket], tool, identities)

if (hit('reject')) return 'reject'        // 硬拒绝最优先（安全立法）
if (sessionHit(sessionRules, tool, args)) return 'allow'  // 会话提升第二
if (hit('ask')) return 'ask'              // 显式强制确认压过宽放行
if (hit('allow')) return 'allow'
return 'ask'                              // 兜底默认 ask（fail-closed）
```

**优先级立法**（permission.ts:21-27）：`reject > sessionAllowed > ask 规则 > allow 规则 > 默认 ask`。推论：sessionRules 第二是因为它是用户在本会话最新的显式意图（"此工具别再问了"），否则对 ask 桶工具（write_file/shell 最常被提升的）提升会失效；而配置层 reject 仍能压住它（安全底线）。ask 压过 allow 是"例外强制确认"——显式窄规则压过宽放行。

### 3.2 toolEntryMatches 双分支之名字分支（permission.ts:103-113）

1. **键名匹配**（:104）：`ruleTool !== tool && !matchWildcard(ruleTool, tool)` → 不命中——桶键对工具名精确或平文本通配（防御手写通配键，编辑器只产精确名；遗留 `mcp__x__*` 手写键走此分支）；
2. **whole 规则**（:105）：`rule.whole` 为 true → 直接命中，patterns 不参与；
3. **参数化匹配**（:106-112）：无 args → fail-closed 不命中；`key = primarySpecifier(ruleTool)` 决定匹配函数——path 主参数用 `matchGlob`（路径有层级，段边界是安全性质：`*` 单段、`**` 跨段，作用域由锚点在归一化阶段声明，:98-101 注释），command 主参数用 `matchWildcard`（命令是平文本，`git *` 通配到结尾即够）；`patterns.some(...)` OR 语义；参数值非字符串 / 全不命中 → 不命中（**fail-closed：无参数可比即不命中，安全默认**，:96 注释）。

### 3.3 双分支之服务分支 mcpServerHit（permission.ts:62-74）

1. `identities?.get(tool)` 查注册表身份快照（agent 注入的提供者函数现取，manager.ts:33）——`id?.kind !== 'mcp'` → 不命中（内建工具走不到这分支）；
2. 查桶键 `mcp:${id.server}`（:70）——裸服务名键在加载期被拒绝，不存在回退形态（:69 注释）；
3. `rule.whole` → 整组命中（该服务下所有工具，不管内部名字）；否则 `rule.patterns.some((p) => matchWildcard(p, id.name))`——patterns 与**内部工具名**做平文本通配，**工具启用匹配，永不涉及执行参数**（permission.ts:37-38 立法）；
4. 匹配从不解析 LLM 可见名（哈希标签不透明也无妨）——服务名含任何字符都无歧义（:61 注释）。

### 3.4 会话提升层 sessionHit（permission.ts:78-89）

`rules?.get(tool)` 无记录 → false；patterns 空 → 整工具命中；有 args 则按主参数分派匹配（path 用 matchGlob、command 用 matchWildcard）——与配置规则同语义，但模式在落库时已是绝对形式（见 3.6）。

### 3.5 运行时归一化与豁免（agent/src/permission/manager.ts:31-43）

`PermissionManager.classify(tool, args, cwd)` 在调用 bridge 引擎前做两件事：

1. **参数侧归一**（:32, :91-94）：path 参数 → `realTargetPath`（:136-147）——目标存在用 `realpathSync`（OS 沿符号链接解析真实位置，含 Windows junction）；目标不存在（write_file 新建）用真实父目录 + 文件名；父目录也不存在则词法解析兜底。**权限按"真实位置"判定**：词法 resolve 会被符号链接欺骗——cwd 内的链接指向 cwd 外时词法路径在范围内而实际读取越界（:130-132 注释，ADR-0010 边界补全）；
2. **规则侧归一**（:99-113 的 normalizeRules）：主参数为 path 的内建键（`mcp:` 前缀键与 shell 跳过），patterns 按锚点解析为绝对 posix——`./`/`../` → resolve(cwd)、`~/` → resolve(homedir())、盘符或 `/` 开头 → resolve 折叠、`*` 开头保留原样（glob 从文件系统根匹配）（normalizePattern :122-128）。**作用域由锚点声明，归一化只做解析、不决定作用域**（:116-117 立法）；
3. **内置读豁免**（:37-41）：判定为 ask 且工具是 read_file 且目标在 `builtinReadDirs`（用户级 skills 目录，agent 管理的资产——系统提示引导模型读 SKILL.md 不应反复弹审批，:13-14 注释）内 → 自动 allow。仅作用于配置桶落 ask 的路径，reject/会话提升等更早判定不受影响。

### 3.6 会话提升生命周期（manager.ts:47-87 + derive.ts）

1. **推导**（derive.ts:15-39）：批准弹层前 `deriveAlwaysScope(tool, input, cwd)` 推导"最窄的可复用范围"——command 主参数取**首词前缀**（`git status` → `git *`，命令按程序名聚类是用户心里"这类命令"的边界；无参命令 → 精确名）；path 主参数取**所在目录** `./<dir>/**`（重复审批的痛点来自同一片区域反复改），文件在 cwd 根部时回退精确 `./<file>`（父目录即 cwd，给 `./**` 等于放行全项目）；参数即 cwd 本身或在 cwd 外 → undefined 保守不提供（derive.ts:33）；推导不出就返回 undefined，弹层退回三档（fail-safe，derive.ts:5-6 注释）；
2. **下发**（agent.ts:298-306）：scopePattern 随 `permission_request.alwaysScope` 发给 UI——UI 据此渲染第四档"对此范围不再询问"（agent-to-ui.ts:15）；
3. **挂起与决议**（agent.ts:299-306 + pending.ts:18-34）：requestPermission 注册 Promise 到 PendingPermissions；UI 决议经 `permission_decision` 消息 resolve `{ decision, scopePattern }`；
4. **落库**（tool-executor.ts:79 → manager.ts:47-58 的 apply）：`allow_always` → 整工具（patterns 空，覆盖已有窄范围——**提宽不提示**，/permissions 可见可撤）；`allow_always_scoped` → 追加范围模式（去重；已是整工具提升则忽略窄范围；path 模式在落库时解析为绝对，:55）；
5. **撤销**（:67-77 的 revoke）：不带 pattern 撤整工具；带 pattern 撤单条——**撤光即整条提升移除**（与配置桶"删光模式留整工具"刻意不同：这里每条模式是独立的授权事件，:65-66 注释）；撤后重推 permissions_list（agent.ts:484-488）；
6. **快照/恢复**（:80-87）：`snapshotPermissions()` 供落盘、配置编辑保留授权（agent.ts:334-337 重建 manager 时 snapshot→restore）、/permissions 展示三处共用；`restore` 按存档直接还原（resume 不清空，session/manager.ts:52-53 先 reset 再 restore）；
7. **会话隔离**：`newSession` 时 `permission.reset()`（session/manager.ts:40）——allow_always 只对当前会话生效；配置三桶持久、提升临时，两者独立。

### 3.7 加载期校验：两条 superRefine（bridge/src/contract/config.ts）

**第一条：作用域前缀校验**（permissionSchema，config.ts:89-112）：内建 path 工具（BUILTIN_PATH_TOOLS）的 patterns 必须显式声明作用域——锚点（`./` `../` `~/`）、盘符（绝对）、或以 `*` 开头（无锚点，从文件系统根匹配）。字面量打头的裸模式（`docs/**`、`test`）从根匹配只能命中盘根条目，必然是忘了写锚点 → **拒绝加载**（:92-96 立法注释）。三个细节：只对内建 path 工具生效（MCP 服务键的 patterns 是工具名选择器，无路径锚点语义）；shell 的 command 模式无作用域概念不校验；**patterns 无论 whole 与否都校验**——它们是规则的待命态（取消整选后生效），编写期就该正确（:96-97 注释）。错误在 /config 编辑时也会经 validate/回滚浮出。

**第二条：服务键强制前缀交叉校验**（configSchema 的 superRefine，config.ts:146-162）：permission 桶键若与 mcpServers 里的服务名同名但未加 `mcp:` 前缀——在前缀化立法下不作为服务键生效（**静默失配**），加载期直接拒绝并指明写法 `"mcp:<服务名>"`（:146-149 注释）。仅校验全局 mcpServers 名单；项目级服务的裸键由调用方按需校验（:145 注释）。

### 3.8 一次判定的完整走查（worked example）

配置样例（config.json 节选）：

```json
{ "allow": { "read_file": { "whole": true, "patterns": [] },
             "shell": { "whole": false, "patterns": ["git *", "npm run *"] } },
  "reject": { "shell": { "whole": false, "patterns": ["rm -rf *"] } },
  "ask": {} }
```

四次调用（cwd = /work/proj）的判定路径：

1. **read_file `{path:"src/a.ts"}`**：名字分支——allow 桶 read_file whole=true → 命中。但先过 reject/session/ask 检查（都未命中）→ **allow**。参数已被 normalizeArgs realpath 归一（若 src 是符号链接指向 /work/proj 外，真实位置失配 → 整工具 whole 不看参数，仍 allow——whole 规则无参数语义）；
2. **shell `{command:"git status"}`**：reject 桶 `rm -rf *` 通配不命中；会话提升无记录；ask 桶空；allow 桶 shell 的 `git *` matchWildcard 命中 → **allow**（规则合法性由加载期"便利而非安全边界"立法声明，见 INV-6）；
3. **shell `{command:"rm -rf build"}`**：reject 桶 `rm -rf *` 命中 → **reject**——硬拒绝优先于 allow 桶的任何模式，ToolExecutor 直接 tool_end denied 回填；
4. **write_file `{path:"docs/x.md"}`**：三桶无规则 → 兜底 **ask** → waiting_permission 挂起。UI 弹四档，用户选 scoped（alwaysScope 推导为 `./docs/**`）→ apply 落库 sessionRules `write_file → ['/work/proj/docs/**']` → 本次 trans allow 执行；下次同目录 write_file 走 sessionHit（matchGlob 命中）→ **allow** 不再弹。

第 4 步展示了"配置静态层"与"运行时提升层"的接力：前者管安全基线，后者管会话内的审批噪音消除。

## 4. 关键立法与不变量

- **INV-1 优先级**：reject > 会话提升 > ask > allow > 默认 ask（fail-closed 兜底）。
- **INV-2 fail-closed 匹配**：无参数可比、参数值非字符串、模式全不命中 → 不命中 → 落 ask。
- **INV-3 按真实位置判定**：参数与提升模式都归一到绝对 posix；realpath 防符号链接逃逸。
- **INV-4 服务键语法自明**：`mcp:` 前缀即语义，裸服务名键加载即拒。
- **INV-5 会话提升临时的**：随会话 reset/restore，不进配置；快照形态与会话文件同构。
- **INV-6 shell 参数化规则是"便利而非安全边界"**：通配会命中 `git status && rm -rf /` 命令链——命令链拆分器是独立后续批次，当前防线是 ask 桶显式压制 + 默认 ask（permission.ts:31-33 立法）。
- **INV-7 匹配函数按主参数分派**：path → matchGlob（段语义）、command/工具名 → matchWildcard（平文本）——同一函数族（bridge/src/contract/glob.ts）服务权限、glob 工具、grep 过滤三端，永不漂移。

## 5. 失败模式与恢复

- **无身份快照（identities 缺省）**：服务分支跳过，仅走名字分支（manager.ts:22, :33-36）——内建永远可判定，MCP 服务键规则失配落 ask（安全方向）。
- **realpath 全失败**（目标与父目录都不存在等极端）：词法解析兜底（manager.ts:142-145）——判定不因 IO 异常中断，方向是保守。
- **提升期间配置编辑**：onConfigChanged 重建 manager 前先 snapshotPermissions、重建后 restore（agent.ts:334-337）——授权不丢。
- **UI 未回决议**：cancel 消息触发 `pending.rejectAll(new CancelledError())`（agent.ts:392）——无 Promise 泄漏；单工具的 await 抛出走取消路径。
- **用户重复批准不同范围**：apply 去重（同模式不重复入列）；整工具提升后 scoped 不再追加（manager.ts:54）。
- **撤销不存在的提升**：revoke 静默（manager.ts:69）——UI 与 agent 状态短暂不一致时无副作用。
- **derive 推导异常**（参数缺失/形态异常/在 cwd 外）：返回 undefined → 弹层退回三档（fail-safe，derive.ts:5-6）——第四档永远只是便利项，缺席不损害安全语义。
- **手写裸服务名键**：加载期拒绝（config.ts:146-162）+ /config 编辑期校验回滚——静默失配不可能上线。

## 6. 与其它子系统的接缝

- **→ 02 轮次**：ask 桶触发 waiting_permission 态 + 挂起；决议后 apply 落库再执行（tool-executor.ts:74-88）。
- **→ 04 注册表**：identities() 提供者是服务键分支的事实源（agent.ts:74）。
- **→ 07 MCP**：服务键 `mcp:<名>` 与 McpManager 的服务命名一一对应（同名覆盖合并见《07》）。
- **→ 09 会话**：sessionPermissions 字段随会话存档 persist/restore（session/manager.ts:53）。
- **→ 11/12 前端**：PermissionDecision 四档渲染、permissions_list/revoke 消息、shared/permission.ts 的展示逻辑（详见《12》§4）。
