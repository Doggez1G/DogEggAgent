# 01 - 四包架构与消息契约

> 职责：定义 DogEggAgent 的物理拆分（四个 npm 包 + 两个组合根）、包间依赖立法，以及横跨所有传输的双向消息契约。本文回答三个问题：为什么拆四包、消息长什么样、同一份契约如何同时跑在"同进程同步"与"SSE+zod"两条通道上。
>
> **交互图**：[架构总览](./assets/architecture-overview.html)（四包/组合根/通道装配全景）。

## 1. 职责与边界

```
agent ←→ bridge ←→ ui
                ←→ server（WebUI 传输）
```

| 包 | 职责 | 依赖 | 关键入口 |
|---|---|---|---|
| `@dogegg/bridge` | 契约与通道：消息类型、zod schema、权限/glob/config 纯派生、Port 接口 | 零兄弟依赖（仅 `zod`） | `bridge/src/index.ts` |
| `@dogegg/agent` | 后端全部业务：轮次引擎、LLM、工具、权限、MCP、skills、会话、配置 | bridge | `agent/src/agent.ts`（门面） |
| `@dogegg/ui` | 两个前端：TUI（ink/React）+ WebUI（React DOM） | bridge | `ui/src/tui`、`ui/src/webui` |
| `@dogegg/server` | WebUI 传输层：HTTP 路由、SSE 通道、静态文件 serve | agent + bridge（**不** import ui） | `server/src/http/http-server.ts` |

只有**组合根**同时 import agent 与前端：

- TUI 模式：`bin/dogegg.ts`——`import { Agent } from '@dogegg/agent'`（bin/dogegg.ts:9）、`import { renderTui } from '@dogegg/ui'`（bin/dogegg.ts:11），装配 `InMemoryChannel` 后把 `channel.agentPort` 给 Agent、`channel.uiPort` 给 TUI（bin/dogegg.ts:64-67）。
- WebUI 模式：仓库根 `main-web.ts`（dev）与 bin/dogegg.ts:44-60（产物）——构造 `SseChannel`、`new Agent(channel, ...)`（main-web.ts:32）、`new HttpServer({ router: new Router({ channel }), staticDir, port })`（main-web.ts:41）。WebUI 前端是 Vite 构建出的**静态文件**被 server serve，不是代码被 import——这就是"server 不依赖 ui"立法成立的原因。

依赖方向由**架构测试**从约定升级为可执行断言：`bridge/test/architecture.test.ts`。它扫描四包源码的 import 语句，断言（architecture.test.ts:33-56）：

1. agent 与 ui 互不 import（:34-37）；
2. bridge 不 import 任何兄弟包（:38-42）；
3. server 不 import `@dogegg/ui`（:43-46）；
4. `ui/src/webui` 不 import agent 或 server，只依赖 bridge + shared（:47-51）；
5. `ui/src/shared` 不依赖 agent（:52-55）。

另外三组断言守模块内部立法：index.ts 纯 re-export（:58-85）、agent 域间依赖矩阵（:125-155，见下）、tui/webui 互不依赖且 features/components 不得 import 装配层 app/（:178-194）。

## 2. 核心数据结构：消息契约全清单

契约文件全部住 `bridge/src/contract/`，`bridge/src/index.ts` 是唯一对外脸面（纯 re-export，bridge/src/index.ts:1-13）。消息是**判别联合**（discriminated union on `type`），类型定义与 zod schema 一一对应成对出现：

- 上行（前端→后端）：`ui-to-agent.ts` 类型 + `ui-to-agent-schema.ts` zod；
- 下行（后端→前端）：`agent-to-ui.ts` 类型 + `agent-to-ui-schema.ts` zod。

### 2.1 下行 AgentToUiMessage（agent-to-ui.ts:7-46，schema 同序）

| type | 载荷要点 | 用途 |
|---|---|---|
| `state` | `from: State; to: State` | 状态机迁移广播（State 十态见 shared.ts:8-18） |
| `text_delta` / `thought_delta` | `delta: string` | 流式正文 / reasoning 增量 |
| `message` | `role: 'user'\|'assistant'\|'tool'; id: string` | 完整消息入库通知；id 与 tool_start 同源，供定位/折叠 |
| `tool_pending` | `name: string` | 模型流式生成工具参数期间的可见反馈（tool_call_start → tool_start 之间） |
| `tool_start` / `tool_end` | `id, name, input` / `output, error?` | 工具执行起止；**拒绝/失败也发 tool_end**（error 标原因，agent-to-ui.ts:14） |
| `permission_request` | `id, tool, input, alwaysScope?` | alwaysScope = agent 推导的第四档范围模式（agent-to-ui.ts:15） |
| `session_ready` | `id, messages, thinking?` | resume 后回放 |
| `session_list` | `sessions: { id, updatedAt, preview, cwd?, title? }` | 侧栏列表；cwd 供项目分组 |
| `session_deleted` | `id` | 删除后刷新列表 |
| `config_state` / `config_updated` | `config: Config` | 编辑器读/写响应 |
| `tools_list` | `tools: ToolListItem[]` | identity 随行（builtin / mcp·服务名），UI 按来源分组（agent-to-ui.ts:21） |
| `context_state` | `estimatedTokens, windowTokens, percent, breakdown?, lastTurn?, sessionUsage?, compactions` | /context 仪表盘：估算与真实用量并排（agent-to-ui.ts:23-34） |
| `system_state` | `path, content` | 生效系统提示词全文 |
| `status_state` | `sessionId, provider, model, cwd, state, estimatedTokens, windowTokens, usage?` | 状态栏单帧 |
| `log_state` | `path, tail` | /log 面板 |
| `history_cleared` | — | /clear 回执 |
| `notice` | `text, channel?: 'skills'\|'mcp'` | channel 让管理面板内联定位错误（agent-to-ui.ts:39） |
| `permissions_list` | `permissions: ToolPermission[]` | /permissions 响应（会话提升清单，agent-to-ui.ts:40） |
| `skills_list` / `skill_content` | 六字段含 `missing` 标孤儿 / 全文 | skills 面板 |
| `mcp_list` | servers 含 `transport` 明细 + 运行时 `status` | /mcp 面板（agent-to-ui.ts:43） |
| `compaction` | `before_tokens, after_tokens, source: 'manual'\|'auto'` | source 决定 UI 弹 overlay 还是插提示块（agent-to-ui.ts:44） |
| `finished` | `usage?` | 轮次收尾 |
| `error` | `{ message, name? }` | **可序列化错误形状**——JSON.stringify(Error) 丢 stack/name，进程内 Port 与 SSE 必须同构（agent-to-ui.ts:45-46） |

### 2.2 上行 UiToAgentMessage（ui-to-agent.ts:5-33）

按语义分四类（与 `agent/src/agent.ts` 的 `send()` 分发注释一一对应）：

- **轮次/工作集类**（运行中阻塞）：`submit`、`compact_request`（ui-to-agent.ts:11-12）；
- **会话生命周期类**（运行中阻塞）：`new_session{cwd?}`、`list_sessions`、`resume_session{id}`、`delete_session{id}`、`clear_history`、`rename_session{title}`（:9-23）;
- **控制类**：`cancel`、`permission_decision{id, decision}`、`permission_revoke{tool, pattern?}`（:12, 22, 27）；
- **查询/管理类**（查询任意时刻放行，管理写文件运行中阻塞）：`config_request/set/add/remove`、`tools_request`、`context_request`、`system_request`、`status_request`、`log_request`、`permissions_request`、`skills_request/manage`、`invoke_skill`、`mcp_request/manage`、`set_cwd`、`quit`（:13-33）。

`PermissionDecision` 四档 `'allow_once' | 'allow_always' | 'allow_always_scoped' | 'reject'`、`ToolPermission { tool, patterns }`、`ContextBreakdown { system, user, assistant, tool, tools }`、`Message`（OpenAI 线格式）都定义在 `bridge/src/contract/shared.ts`（shared.ts:22-50）。

### 2.3 契约内的跨端派生逻辑

bridge 的 contract/ 不只有类型，还有**对契约数据的纯派生函数**——它们被 agent 与 UI 共用，故必须在契约层而非某一端：

- `classifyPermission`（contract/permission.ts）——权限三桶求值，详见《06-权限引擎》；
- `globToRegExp / matchGlob / matchWildcard`（contract/glob.ts:18-68）——一份 glob 实现三端（agent 工具、权限匹配、UI 展示）永不漂移（glob.ts:1-3 注释）；
- `isConfigured`（contract/config.ts:169-175）——"能否提问"的完整性判定；
- `COMPACTION_THRESHOLD = 0.8`（shared.ts:6）——压缩阈值常量：**它是跨端显示策略**，后端 trigger 与前端 info-panel 变色共用，刻意放契约防两端漂移（shared.ts:4-5 注释）；
- `PRIMARY_SPECIFIER / BUILTIN_PATH_TOOLS`（config.ts:67-72）——权限主参数表，详见《06》《10》。

## 3. 关键流程走查

### 3.1 TUI 模式装配（同进程，同步投递）

1. `bin/dogegg.ts` 解析 argv，`isWeb = args.includes('-web')`（bin/dogegg.ts:14-15）；
2. `loadConfigOrExit()`（bin/dogegg.ts:20-39）：ConfigStore.load 失败时把 ZodError issues 逐条拼成人话（`i.path.join('.')：i.message`），指明待修文件 `store.sourcePath()`、恢复方式与本地存在的格式文档路径，`process.exit(1)`；
3. TUI 分支（bin/dogegg.ts:61-67）：`new InMemoryChannel()` → `new Agent(channel.agentPort, config, process.cwd(), { logger })` → `renderTui(channel.uiPort)`。

InMemoryChannel 的实现只有 30 行（bridge/src/channel/in-memory.ts:8-31）：两个 `Set` 监听器 + 对偶端口。关键在 `post` 的语义——`this.uiListeners.forEach((l) => l(msg))`（in-memory.ts:21）是**同步调用**，与旧版 agent.send/emit 的时序完全一致：`port.post()` 返回时监听器已执行完。这是刻意立法：TUI 依赖这个同步性保证焦点/状态切换的确定性时序（in-memory.ts:5 注释）。

Port 接口本身（bridge/src/channel/port.ts:7-19）只有 `onMessage`（返回退订函数）与 `post`（返回 `void | Promise<void>`）两个成员——把"两端如何互通"从具体传输中抽离的唯一抽象。

### 3.2 WebUI 模式装配与一次完整往返

1. `main-web.ts:22-32`：加载配置 → `new SseChannel()` → `new Agent(channel, config, process.cwd(), { logger })`。注意 `SseChannel implements AgentPort`（server/src/channel/sse.ts:15）——agent 拿到的仍是同一个 AgentPort 接口，对传输无感知；
2. UI 侧建立下行：浏览器 EventSource 连 `GET /api/events`，`sseHandler` 写 SSE 响应头（`text/event-stream` + no-cache + keep-alive）并把 `res` 加入 `sseClients` 集合（sse.ts:36-46）；
3. UI 侧上行：`POST /api/message`。`postHandler` 累积 body、超过 1MB 断流（`MAX_BODY_SIZE`，sse.ts:8 与 :52-58），`JSON.parse` 后过 `uiToAgentMessageSchema.safeParse`（sse.ts:68），失败返回 400 + issue 明细，成功则 `this.agentListeners.forEach((l) => l(result.data))` 触发 Agent 的订阅回调（sse.ts:74）；
4. Agent 处理后 `emit` → `port.post(msg)` → SseChannel 把消息 `JSON.stringify` 成 `data: {...}\n\n` 写入**所有**活跃 SSE 连接（sse.ts:28-33）——多标签页共享同一 Agent 事件流，都是观察者（sse.ts:14 注释）；
5. 客户端收到后过 `agentToUiMessageSchema` 校验（实现在 `ui/src/webui/channel/sse-client.ts`，详见《12》），失败则**丢弃**该条消息、不传给 listener（agent-to-ui-schema.ts:6-7 注释）。

路由表 `server/src/http/router.ts:23-47` 定义 `/api/events`（仅 GET）、`/api/message`（仅 POST）、`/api/fs`（目录浏览）、`/api/shells`（shell 检测，结果缓存）四个端点；未命中返回 false 交给静态文件 fallback（router.ts:50-55）。

### 3.3 Agent 构造：port 驱动一切

1. `Agent` 构造函数（agent/src/agent.ts:59-118）依次建 SessionStore、ToolRegistry.withBuiltins()、Conversation、SkillsManager、ctx（config/permission/assembler/machine/gate 五件套，agent.ts:72-78）、ConfigEditor、Compactor、AgentLoop、TurnRunner、SessionManager、ConfigController、McpManager；
2. `void this.rebuildMcp().catch(() => {})`（agent.ts:115）——启动即异步拉起已配置的 MCP server，不阻塞消息循环；
3. 最后一步 `this.port.onMessage((msg) => { this.send(msg).catch(() => {}) })`（agent.ts:117）——**Agent 只有消息这一个进出通道**：构造完成即进入纯消息驱动状态，无任何对外暴露的方法。

## 4. 关键立法与不变量

- **I1 四包解耦**：agent/ui 互不 import；bridge 零兄弟依赖；server 不 import ui。由 architecture.test.ts 持续断言，违反即测试失败。
- **I2 组合根唯一**：只有 bin/dogegg.ts（dev 另有 main-web.ts）同时 import agent 与前端；Agent 构造函数不 new 任何 UI 对象。
- **I3 index 纯 re-export**：所有 `index.ts(x)` 只含 import/export 行，禁止实现声明（architecture.test.ts:59-85 的检查逻辑：出现 `export const/function/class` 即违规）。
- **I4 跨域 import 只走一层门面**：允许 `../config`，禁止 `../config/editor` 深路径（architecture.test.ts:87-104）。
- **I5 agent 域间依赖矩阵**（architecture.test.ts:128-139 的 ALLOWED 表）：

  | 域 | 允许依赖 |
  |---|---|
  | turn | session, llm, tools, context, permission, shared, ROOT |
  | session | shared, ROOT |
  | config | ROOT |
  | tools / llm / permission / skills / shared | （无） |
  | context | tools |
  | mcp | tools |

  ROOT（agent.ts 门面 / ctx.ts / index.ts）依赖一切、不受矩阵约束（architecture.test.ts:146）。能力模块之间互不依赖、无回穿——所有编排都集中在 turn 与 ROOT。
- **I6 错误必须可序列化**：下行 error 是 `{ message, name? }` 而非 Error 实例（agent-to-ui.ts:45-46），因为同一份类型要服务进程内回调与 SSE JSON 两种传输。
- **I7 拒绝/失败也发 tool_end**：不静默塞消息（agent-to-ui.ts:14），UI 才能对每个 tool_start 收敛到唯一终态。

## 5. 失败模式与恢复

- **配置非法**：loadConfigOrExit 逐 issue 输出（ZodError 的 path + message），给出"改写为当前格式 / 整段删除回退出厂默认"两条恢复路径与本地文档路径，exit(1)（bin/dogegg.ts:24-38）。人话提示而非裸 zod 堆栈，是加载失败路径的产品立法。
- **WebUI assets 缺失**：bin/dogegg.ts:53-57 检查 `dist/web` 不存在则提示 `npm run build:web` 后退出；dev 模式（VITE_DEV=1）staticDir 为 null，非 API 路径 404，前端由 Vite dev server 代理（main-web.ts:35-38 注释）。
- **POST body 超限/非法**：413（tooLarge 后 `req.destroy()` 停读）、400（JSON.parse 失败）、400 + issue 明细（zod 校验失败）三档分流（sse.ts:59-81）。
- **SSE 客户端发坏消息**：下行 schema 校验失败即丢弃该条，不断流、不崩 UI；连接断开由 `res.on('close')` 清理 sseClients（sse.ts:45），`post` 的 write 异常被吞、留给 close 事件清理（sse.ts:31 注释）。
- **消息处理器抛错**：Agent 侧 `this.send(msg).catch(() => {})`（agent.ts:117）——单条消息处理失败不炸订阅循环；错误以 `error` 消息形式在业务路径内显式 emit。
- **架构回归**：任何 import 方向或 index 污染的改动会立即被 architecture.test.ts 的断言拦截，防止"先临时 import 一下"式的边界侵蚀。

## 6. 与其它子系统的接缝

- **→ 02 轮次引擎**：`send()` 的 submit/compact/cancel 分支是 TurnRunner/BusyGate/PendingPermissions 的唯一入口（agent.ts:346-397）。
- **→ 04/05 工具**：`tools_list` 的 ToolListItem 带 ToolIdentity，identity 由注册关口维护（contract/tools.ts:10-19）。
- **→ 06 权限**：`permission_request.alwaysScope` 与 `PermissionDecision` 四档、`permissions_list` 的 ToolPermission 形状都由本契约定义（shared.ts:22-29）。
- **→ 07 MCP**：`mcp_manage` 的 save/delete/toggle 走上行消息；transport 判别联合（stdio/http）是 config.ts 契约的一部分（config.ts:25-37）。
- **→ 09 会话**：`session_list` 载荷里的 `cwd`/`title` 支撑 WebUI 项目分组与手动命名。
- **→ 11/12 前端**：两个前端分别消费 `channel.uiPort`（TUI）或 SSE+fetch（WebUI），共享同一套消息语义；`ui/src/shared/` 是双前端共用的 reducer/展示层（详见《12》§6）。
