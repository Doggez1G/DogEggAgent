# 04 - 工具注册表与合规关口

> 职责：`agent/src/tools/registry.ts` 是一切工具（内建 7 个 + MCP 动态注册 + 未来任何来源）进入系统的**唯一关口**。注册那一刻同时完成三件事——合规转换、冲突可见失败、身份记录——此后系统的其余部分（LLM 请求、权限引擎、UI）都从注册表读取"工具 + 身份"的一致快照。

## 1. 职责与边界

注册表持有两张同步的 Map（registry.ts:30-31）：

```ts
private readonly tools = new Map<string, Tool>()            // 标签 → 工具
private readonly identityById = new Map<string, ToolIdentity>()  // 标签 → 身份
```

契约类型（bridge/src/contract/tools.ts:10-19）：

```ts
export type ToolIdentity =
  | { kind: 'builtin' }
  | { kind: 'mcp'; server: string; name: string }  // server=配置里的服务裸名；name=服务侧声明的内部工具名

export interface ToolListItem { name: string; description: string; identity: ToolIdentity }
```

身份住 bridge 的原因（tools.ts:1-4 注释）：权限匹配引擎（contract/permission.ts）与 tools_list 载荷（contract/agent-to-ui.ts）都消费它，属契约数据。`Tool` 接口本身在 `agent/src/tools/types.ts:19-25`：`name / description / schema(zod) / parameters(OpenAI JSON schema) / execute(args, ctx)`；`ToolContext`（types.ts:6-14）带 `cwd / signal / shellProgram? / shellTimeoutMs?`。

依赖矩阵中 `tools` 域依赖为空（architecture.test.ts:132-136）——它不 import 其它 agent 域，是最底层能力模块。

## 2. register 三动作逐行讲解（registry.ts:53-63）

```ts
register(tool: Tool, identity: ToolIdentity = { kind: 'builtin' }): string {
  const label = TOOL_NAME_RE.test(tool.name)
    ? tool.name
    : `h-${createHash('sha256').update(tool.name).digest('hex').slice(0, 12)}`
  if (this.tools.has(label)) {
    throw new Error(`工具注册名冲突：${label}（原名 ${tool.name}）已被占用——请调整来源命名（如 /mcp 中的服务名）`)
  }
  this.tools.set(label, label === tool.name ? tool : { ...tool, name: label })
  this.identityById.set(label, identity)
  return label
}
```

**动作一：合规转换（构造即合规）。** `TOOL_NAME_RE = /^[a-zA-Z0-9_-]{1,64}$/`（registry.ts:16）是 LLM 可见名的硬规定——供应商 API 对函数名的约束（OpenAI 系与 Anthropic 系一致：字符集 `[a-zA-Z0-9_-]`、长度 ≤64）。校验发生在 API 请求层且**拒绝整个请求**，所以注册表必须把住关口：任何来源的注册名不合格时，整体哈希为 `h-<sha256 前 12 位 hex>` 的确定性标签（:56）——sha256 保证**同名必同标签**（跨会话/跨重建稳定）。关键设计：**变换落在 Tool 对象本身**（:60 的 `{ ...tool, name: label }`），而不是只改 Map 的键——这保证 `schemas()` 发给模型的名字必然合规。若只改键不改对象，一次非法名会让每轮对话请求整体 400（:13-15 注释）。

**动作二：冲突可见失败。** 目标标签已被占用 → 抛错，错误消息含标签、原名与指引（"请调整来源命名（如 /mcp 中的服务名）"）（:57-59）。绝不静默覆盖——静默顶掉会让先注册的工具无声失联，且用户无从察觉（:25 注释）。MCP 侧的消费方式见《07》§3：单服务注册冲突时该服务整体落 error、半挂工具被清理，其余服务不受影响。

**动作三：身份记录。** `identityById.set(label, identity)`（:61）与工具注册同事务发生；identity 缺省为 `{ kind: 'builtin' }`（:53）——内建构造路径零改动接入。注册返回**最终标签**（:62），哈希情况下调用方（McpManager.syncRegistry）据此对接归属。

## 2. Tool 契约与 schemas() 的产物形状

`Tool` 接口（agent/src/tools/types.ts:19-25）的五个成员各自服务一个消费方：

| 成员 | 消费方 | 说明 |
|---|---|---|
| `name` | schemas() / get() | LLM 可见名（可能被关口改写为哈希标签） |
| `description` | schemas() / listTools() | 模型选工具的依据；MCP 适配器缺省补 `(MCP <server>) <tool>` |
| `schema`（zod） | ToolExecutor 参数校验（tool-executor.ts:53） | `schema.parse(JSON.parse(arguments))`，失败回填"参数校验失败" |
| `parameters`（JSON Schema） | schemas() → 请求体 tools | 暴露给 LLM 的参数说明书；MCP 透传服务端原生 inputSchema |
| `execute(args, ctx)` | ToolExecutor.runAndEmit | 返回 `{content}` 或 `{error}`，不抛错（见《05》INV-1） |

`schemas()` 的输出（registry.ts:104-109）正是 OpenAI tools 参数的形状：

```ts
[{ type: 'function', function: { name, description, parameters } }, ...]
```

每轮请求现算（loop.ts:126 传入 `this.services.registry.schemas()`）——MCP server 启停、/mcp 面板保存后的下一次模型请求立即携带新工具集，无需任何失效协议。

### 2.1 一次 MCP 工具名哈希的具体例子

假设配置了服务名 `文件搜索`（中文），服务侧声明工具 `search`：

1. syncRegistry 构造适配器名 `mcp__文件搜索__search`（mcp/manager.ts:153）；
2. `TOOL_NAME_RE.test()` 失败（含中文）→ label = `h-` + sha256("mcp__文件搜索__search") 前 12 位 hex（registry.ts:56）；
3. Tool 对象被浅拷贝改写 name（registry.ts:60）——模型看到的是 `h-3f9a…` 这样的合规名 + description 里的语义说明；
4. 身份仍是 `{ kind: 'mcp', server: '文件搜索', name: 'search' }`——权限服务键 `mcp:文件搜索` 的 patterns（如 `search`）照常按**内部原名**匹配（permission.ts:73）；调用回路 `callTool({ name: 'search' })` 发的也是内部原名（manager.ts:163）——哈希只影响 LLM 可见层，服务侧全程无感。

## 3. 关键流程走查

### 3.1 内建注册（启动时）

1. 组合根 `new Agent(...)` → `ToolRegistry.withBuiltins()`（agent/src/agent.ts:67）；
2. `withBuiltins()`（registry.ts:35-45）依次 new 七个工具实例：ReadFileTool / WriteFileTool / EditFileTool / ShellTool / LsTool / GlobTool / GrepTool；
3. 构造函数 `for (const t of tools) this.register(t)`（registry.ts:47-49）——缺省 identity = builtin。

### 3.2 MCP 动态注册与摘除（agent/src/mcp/manager.ts）

1. `syncRegistry`（manager.ts:114-147 区域）：先 `unregisterServerTools(name)`（:114）摘除该服务旧工具，再逐个 `registry.register(makeAdapter(serverName, rt, t), { kind: 'mcp', server: serverName, name: t.name })`（:132）——身份携带**服务裸名 + 内部原名**（与 LLM 可见标签无关）；
2. 摘除用 `registry.labelsWhere((id) => id.kind === 'mcp' && id.server === serverName)`（:146）按**身份谓词**找标签，再逐个 `unregister(label)`（:147）——**不按前缀字符串扫描**：哈希标签 `h-xxx` 不带 `mcp__` 之类前缀，前缀扫描会漏删（manager.ts:145 注释语义；这正是 labelsWhere 存在的原因，registry.ts:88-92）；
3. `unregister`（registry.ts:66-69）：工具与身份同步删除，不存在时静默（摘除幂等）。

### 3.3 消费路径

| 消费方 | API | 时机 |
|---|---|---|
| LLM 请求 | `schemas()`（registry.ts:104-109，组装 OpenAI tools 参数） | AgentLoop 每次请求模型时现算（loop.ts:126）——替代旧 import 期快照，注册表变化即时反映（registry.ts:19 注释） |
| 权限引擎 | `identities()` 只读快照（:84-86） | PermissionManager 构造时注入**提供者函数**（agent.ts:74）——注册表随 MCP 启停变化，classify 时现取永远新鲜（permission/manager.ts:18-20 注释） |
| 工具执行 | `get(name)`（:71-73） | ToolExecutor 查到即执行、查不到按"未知工具"回填（tool-executor.ts:43-48） |
| UI 分组 | `listTools()`（:95-101） | tools_list 广播（agent.ts:191-193）——identity 随行，UI 按内建/MCP·服务名分组标注 |
| /permissions | `identities()` | classifyPermission 的服务键分支判定 |

## 4. 关键立法与不变量

- **INV-1 凡注册必有身份**：`listTools()` 的 `?? { kind: 'builtin' }` 兜底仅为类型完备（:94 注释）；unregister 双 Map 同步删，不存在孤儿身份。
- **INV-2 LLM 可见名必合规**：TOOL_NAME_RE 不过关即哈希改写 Tool 对象本身——schemas() 产物永远合法。
- **INV-3 身份从不从 LLM 可见名解析**：哈希标签不透明也无妨；"工具从哪来"唯一事实源是 identityById（:27-28 注释）。
- **INV-4 schemas() 每次现算**：无缓存快照，注册/摘除对下一次请求立即可见。
- **INV-5 冲突抛错不覆盖**：冲突是调用方的 bug 或配置问题，必须显式暴露。
- **INV-6 注册顺序无关紧要**：schemas() 输出按注册序（Map 迭代序），模型对工具顺序不敏感；权限匹配按名不按序——无隐式顺序依赖。
- **INV-7 register 返回值契约**：返回最终标签（:62）——调用方（McpManager.syncRegistry）不重复推导合规结果，哈希逻辑单点存在。

### 为什么关口在注册表（失败模式对比）

- 合规转换放注册表而非各工具来源：未来任何新工具来源（MCP、插件、SDK 注入）自动被覆盖，不靠每个来源自觉转译；若放 MCP 侧，下一个非 OpenAI 名字约束的来源就会重新踩 400 坑。
- 身份放注册表而非 McpManager 侧：注册与摘除是同一关口，工具与身份天然一致；若身份散在 manager，任何绕过 manager 的注册路径都会产生"有工具无身份"的孤儿——权限服务键静默失配。
- 冲突检测放注册表而非事后校验：静默覆盖的失联是纯运行期现象，测试难以覆盖；抛错把问题提前到注册时刻（启动或 /mcp 保存），失败立刻可见。

**与"每来源自转"方案的具体失败对比**：若合规转换交给 McpManager（在 makeAdapter 里自己改 name），则——①下一个非 MCP 来源（SDK 注入、插件）注册非法名时无人兜底，每轮请求整体 400；②"对象 name 字段被改写"这一关键动作容易被实现成"只改 Map 键"，schemas() 仍吐非法名；③注册表的单测无法覆盖合规行为。三动作内聚在 register 一个函数里（15 行），行为可穷举测试（`agent/test/tools/registry.test.ts` 存在同域测试）。

## 5. 失败模式与恢复

- **注册名冲突**：register 抛错 → McpManager 捕获后该服务落 error 态、`unregisterServerTools` 清理半挂工具（mcp/manager.ts:138），其余服务照常（详见《07》）；内建路径冲突属编程错误，启动即崩（合理）。
- **MCP 工具名与内建同名**：如服务提供 `read_file`——首次注册即冲突抛错（标签已被内建占用），服务不可用而非内建被顶掉；恢复方式是改名服务或停用。
- **同名哈希碰撞**：12 位 hex（48 bit）冲突概率可忽略；即便碰撞也走冲突抛错路径，不会静默顶替。
- **模型调用已摘除的工具**：loop 内 registry.get 查不到 → ToolExecutor 回填"未知工具 X"（tool-executor.ts:43-48），模型下一轮改换工具——不炸轮次。
- **身份快照滞后**：PermissionManager 持有的是提供者函数而非快照，每次 classify 现取（manager.ts:33）——不存在"停服后权限还按旧身份放行"的窗口。
- **测试注入子集**：AgentOptions.registry（agent.ts:30）允许测试注入只含部分内建工具的注册表——工具行为测试不依赖全部 7 工具；注入路径同样走 register 关口，被测对象与生产同构。

### 5.1 UI 侧的身份消费（tools_list → 分组/标注）

`listTools()` 的 identity 随行让 UI 无需任何名字约定即可分组（agent-to-ui.ts:21 立法注释）：

- TUI：toolsList 镜像进 app.tsx（:45），既供 /tools 面板展示，又供 /config 权限树的 selectTool 选择器（build.ts 的 KNOWN_TOOLS 回退仅在未播种时使用——app.tsx:307 注释："空数组不是'无工具'而是'未播种'"）；
- WebUI：use-panel-data 的 toolsList 镜像 → Available Tools 卡按 `identity.kind` 分"内建 / MCP · 服务名"两组；use-turn-tracking 的 identitiesRef 按名建索引供 effectivePerm 判定服务键规则（use-turn-tracking.ts:27-29）；
- 两端都不解析工具名字符串——哈希标签 `h-xxx` 在 UI 上也只是"一个来源为某 MCP 服务的工具"。

## 6. 与其它子系统的接缝

- **→ 05 内建工具集**：withBuiltins 的 7 个实现。
- **→ 07 MCP**：makeAdapter 适配 MCP 调用回路为 Tool 契约；syncRegistry 的注册/摘除全走本关口。
- **→ 06 权限**：identities() 提供者注入 PermissionManager，服务键分支（mcpServerHit）按身份匹配。
- **→ 02 轮次**：schemas() 进每次 LLM 请求；get() 进工具执行。
- **→ 01 契约**：ToolListItem/ToolIdentity 定义在 bridge contract/tools.ts，UI 与 agent 共享同一形状。

### 7. unregister 与 labelsWhere 的契约细节（registry.ts:66-92）

摘除侧三个方法合起来构成"按归属管理"的完整 API：

1. `unregister(name)`：单标签删除，工具与身份双 Map 同步（:66-69）；不存在时静默——摘除的幂等性使"先摘后挂"的重建模式无需存在性检查；
2. `identityOf(name)` / `identities()`：单查与全量只读快照（:80-86）——identities 返回的就是内部 Map 的只读视图（零拷贝），PermissionManager 每次classify 现取的成本可忽略；
3. `labelsWhere(pred)`（:88-92）：按身份谓词反查标签列表——MCP 按服务摘除是唯一生产消费方（mcp/manager.ts:146），谓词 `id.kind === 'mcp' && id.server === serverName` 精确圈定本服务全部工具（含被哈希改名的），删除顺序无关。
